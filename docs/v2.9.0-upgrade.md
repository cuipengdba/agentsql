# v2.8.0 → v2.9.0 升级与恢复

**语言 / Language:** [简体中文](v2.9.0-upgrade.md) | [English](en/v2.9.0-upgrade.md)

状态：候选说明；正式包验收后补入对应 SHA 和恢复记录。

1. 用 v2.8.0 正式包执行 `agentsqlctl migrate --check`，确认合并元数据为 22 或分库 metadata 为 21、独立 audit 为 6，且没有未完成迁移。停止所有网关的登录和 MCP 流量。
2. 对 metadata、audit（若分库）、`AGENTSQL_SECRET`、审计链密钥和部署配置制作同一时点的成套备份。不要只备份 metadata；审计 outbox 与审计链的恢复点必须一致。保留 v2.8.0 正式包以供回退。
3. 用 v2.9.0 目标包执行只读 `agentsqlctl migrate --check`，核对仅有预期新增迁移：合并库 22→23；分库 metadata 21→22；独立 audit 保持 6。然后显式执行 `agentsqlctl migrate`，再次运行 `--check`，要求全部 `current=latest`。如有多网关，同步停止旧节点并更新所有节点，避免混合版本承接策略写入。
4. 在隔离恢复副本和正式候选上分别检查原有 Agent、数据源、策略、审批、审计链；新建一个无 B2 绑定的表策略提案，异人审批并应用，验证 `approved` 状态、真实 MCP 允许/拒绝和管理审计 outbox 投递。随后用单条策略 API 制造漂移，应只显示 `drifted`；业务执行仍按现有授权与审计合同运行。
5. 回退时停止全部 v2.9.0 网关，把 v2.8.0 正式包与升级前同一时点的 metadata、audit、密钥和配置整体恢复，再运行 v2.8.0 `migrate --check`、审计链校验、登录和真实 MCP 烟测。不能在保留新 schema 或新策略变更的情况下仅替换旧二进制。

外部审计见证文件和 Ed25519 密钥不应存在于这些数据库备份内。见证已对外签发后，恢复旧数据库不能撤销外部证据；应将恢复事件和新的链头明确记录在下一份外部留存材料中。本版见证仅证明归档字节与签署声明，不是不可篡改存储或可信时间服务。
