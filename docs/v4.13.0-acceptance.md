**语言 / Language:** [简体中文](v4.13.0-acceptance.md) | [English](en/v4.13.0-acceptance.md)

本报告记录同一精确生产签名候选的自验，不是第三方认证。正式下载、镜像摘要、官网和模拟模型 Demo 的发布后复验，以 [v4.13.0 Release](https://github.com/cuipengdba/agentsql/releases/tag/v4.13.0) 为准；候选通过不等于公开发布流程已经完成。

## 真模型、真网关、真数据库

- 最终签名包的相同 ELF 分别运行 ChatBI 与 Gateway；固定真实 ONNX、实际 Qwen3-4B、本地 PostgreSQL **17.11**。夹具含 128 张显式受权合成表，本轮问题明确点名 `public.systemvar_rows` 的三行数据。
- ChatBI 2 CPU / 4 GiB、Gateway 2 CPU / 2 GiB、PostgreSQL 2 CPU / 2 GiB、Qwen 4 CPU / 8 GiB。元数据和审计库使用 D 盘 SSD 上的原生 Linux ext4；运行服务与故障注入工具逐项核对为同一数据库 inode。
- 原版浏览器单表问数返回三行，两个已观测界面耗时 **54.828 秒、51.008 秒**。这是共享主机、已预热条件下的观测，不是冷首问、p95、吞吐或生产 SLA；不能证明无提示的 128 表选表。
- 未修改的官方 SQLBot Community v1.10.3 静态页面与其固定镜像内 Python MCP SDK，均接此候选。镜像固定为 `dataease/sqlbot@sha256:ff9012a95e6ac0e7921aa74e96c73de33550af61615fe850edb27b322c342288`。
- Ask 夹具的网关 B2 为 feature-off。本轮不计联合列授权、脱敏和撤权的完整 Q5 场景，不由此提升任何数据库生产支持等级。

## 结果与安全行为

原版客户端的两项指标实际展开六条绘图记录、两条图例，默认柱图为堆叠展示；原生页面为六根分组柱。两边均实际展示双折线的六个点；原生页面可切换表格、柱、条形、折线和合法单指标饼图，选择维度与指标。手动选择不产生新受控查询，重开历史重新授权和受控重查，并恢复问题指定的默认图表。

真实模型与 PostgreSQL 通过全零、正值饼图、负值饼图回表格、HTML 外观标签按文本显示。**当前网关将 SQL NULL 与数据库空字符串都表示为空字符串，无法证明为数值的这一列保守保留表格，不画成零。结构化 JSON null 的折线断点通过了确定性渲染测试，本轮真实网关不宣称这一正向路径通过。** 先前将该夹具误期望为折线的失败已保留，后续按实际数据合同复核原表和缺失单元格。

图表使用前 20 个受权结果行，最多四个指标；严格数值与精度边界、不可信标签、超限选择和缺失点另有确定性测试。真实集成展示两个指标，不外推任意图表或任意脚本。

以下在最终同包实际通过：

- 新规则生效后旧历史去除 SQL/数据，记录数据入口返回 `200` 且 `data:null`，CSV/XLSX 返回 `404`；旧图消失且没有新增受控查询。新问题在当前行规则下只见 east 和两个正确指标。
- 服务重启前后，两种页面历史重开和实际 CSV/XLSX 下载正确；解析文件确认三行原值，公式外观字符串保持文本。
- 导出回执提交时改变规则、回执写入故障、网关审计写入故障均不释放文件；故障恢复后有效导出恢复。无可见列、禁用成员、跨用户、跨工作空间、在途删除和绑定撤销均按当前边界拒绝。
- 真实多轮追问保持前一轮 west 条件；原版 Python SDK 非流式和流式问数、无效令牌拒绝；基本助手及 Type 4 原版浏览器嵌入的真实问数和撤销；模型停机不释放结果且无新数据查询，恢复后重新问数正确。
- 绑定撤销后重启 ChatBI，重新登录仍不能读取旧历史、文件或继续旧问数，网关没有新查询。

浏览器采集曾遇到 CDP 读取事件流正文限制、异步渲染等待不足、历史名称碰撞以及旧协议状态码假设错误。失败与修正后重跑分别保留；没有改写原版请求、响应或数据来取得通过。

## 断网安装、升级与回滚

AMD64 与 QEMU ARM64 的 Debian 12、PID1 systemd、`--network none` 容器，各通过最终签名包新装、正式 v4.12 升级和注入首次启动失败后的健康回滚，共 **6/6**。检查两项主服务 active/enabled、独立助手服务默认禁用后可启用、版本/健康、模型哈希、SQLite 标记/完整性及回滚旧文件哈希。**QEMU 不代表 ARM 实机。**

最初 Docker 所在 H 盘 overlay 测试出现 OpenSSL 30 秒超时及旧服务审计提交超时；两次失败不计通过。随后只为本任务创建 D 盘上的新虚拟磁盘和原生 ext4，保持签名、审计和查询安全超时不变，新容器完整重做六项。没有重启 Docker/WSL，也没有改动其它服务。

## 容器交付方法

容器封装独立公钥验真的生产原生包 ELF/CLI/Yashan 库，采用固定 Debian 运行层以及仓库 Dockerfile 相同的用户、权限、配置、启动和健康设置。[实际配方](assets/release-v4.13.0/Dockerfile.signed-native) SHA-256 为 `58e24578a358169a2cd500a3f6d4dabcfa146918b65a871f1fa5f1455016941c`。避免重复的 ARM Go 编译；不称根 Dockerfile 的另一次源码编译通过。发行镜像还须匿名回拉两架构、与签名原生 ELF/CLI 逐项比较，再做真实运行检查。具体接受的摘要与发布后结果见 Release。
