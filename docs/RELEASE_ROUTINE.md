# AgentSQL 每版交付流程

本流程适用于功能版和修复版。版本负责人负责设计、实现、验证、发布、官网与 Live Demo 的完整闭环；不能把 GitHub Release 创建视为交付结束。所有结果必须注明提交 SHA、环境和未测边界。

v1.1.0–v1.4.0 按产品负责人确定的分阶段节奏逐版创建正式 GitHub Release，官网、Live Demo 与 GHCR `latest` 保持 v1.0.0；各版验收仍须完成独立升级、客户端、真库及精确版本资产验证。v1.5.0 完成后一次性更新这三个默认入口并做公网复验。

## 1. 设计与范围

1. 对照上一正式版、真实用户反馈、竞品和现有代码，写明用户问题、非目标、兼容影响、数据库支持边界与验收用例。
2. 涉及身份、权限、执行、脱敏、审计、故障关闭的变更，画出端到端调用链并列出负向用例。无法证明的能力只标为未验证。
3. 版本号按实际兼容性选择；数据库协议兼容和单实例合成数据通过不等于完整生产支持。

## 2. 开发与回归

1. 在隔离分支实现后端、控制台、配置、文档与必要的迁移。所有正式发布代码从同一提交构建。
2. 运行 Go、前端类型检查和测试、网站校验、SQL 安全负向集。真实客户端和数据库测试只记录实际完成的版本、协议、模式及环境。
3. 审计故障、令牌撤销、跨租户、权限变更、断线重试和回退是安全功能的发布阻断项。若失败，先修复并重跑受影响用例。
4. 用上一正式版的安装包与数据备份演练升级；有 schema 变化时同时演练成套备份恢复。新代码不得暗中迁移生产数据。

## 3. 发布与交付

1. 合入前审查 diff、依赖、敏感信息及发布说明。合入后以目标 SHA 的绿色 CI 为发布依据。
2. 从该 SHA 创建正式 tag 和 GitHub Release，构建并校验双架构资产、SHA256 清单及签名；验证 GHCR 精确 tag 的多架构摘要与匿名拉取。
3. 官网文案、兼容矩阵、下载命令和 PDF 与正式 Release 对齐；部署后从公网读取并核对版本及资源链接。
4. Live Demo 先备份并在隔离候选环境完成迁移、启动、合成场景和安全负向烟测，再切换公网。核对 `/healthz` 版本、登录、允许与拒绝场景、脱敏和持久审计。
5. 官网和 Demo 均通过后，把 `latest` 提升到已验收的主镜像摘要并再次匿名拉取；Release 正文和验收记录补齐 CI、资产/签名、镜像摘要、官网、Demo、客户端与数据库证据，以及任何未完成项。无证据的事项不能写成已通过。

若任一发布阻断项失败，保留已完成的代码和测试记录，停止对外宣称该版本已发布；先恢复官网和 Demo 到上一已验证版本，再修复问题。
