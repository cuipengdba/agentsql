# AgentSQL v4.12.0 current authorization for history and exports

## Goal

AgentSQL continues to provide an independent AI data Q&A agent and an independent MCP Server database security gateway. Based on formal v4.11.0, this release focuses on historical reads, file exports and conversation lifecycle, closing gaps between positive slices and complete acceptance. The frozen 25-scenario SQLBot Community v1.10.3 contract remains unchanged; the strict v4.11.0 baseline is Q1, H1 and I1, or 3/25 (12%).

## Delivery scope

- After the controlled requery, file encoding and durable receipt commit, CSV/XLSX export rechecks current identity attributes, row/column rules, datasource binding and conversation revision. Any change or verification failure prevents file bytes from being sent; a receipt records an export preparation attempt, not proof of client delivery.
- Verify history, downloads and conversation deletion through the unchanged original Chinese page and AgentSQL's native Chinese page. Errors must not leave actionable stale results; readable data always comes from the current controlled gateway.
- On the same final signed package, recheck Q1/H1/I1 with a real local model, PostgreSQL and controlled gateway, and complete applicable H2/H3/H4 positive and negative matrices. Only fully accepted scenarios score; incomplete scenarios remain zero.

## Security and acceptance

1. Deterministic regressions cover row rules, column rules and identity attributes changing during export receipt commit; neither CSV nor XLSX may release stale files. Audit or receipt write failures also close. Formula-like text remains literal.
2. Record the first historical read and first export after restart separately; both pages, file values and controlled audit must agree. Other users, other workspaces, disabled members, rule changes, datasource revocation and conversation deletion must reject stale history, exports or follow-ups.
3. Record real model/database versions, resources and original exit codes; single-request latency is not production p95. Keep bounded regression coverage for the original SDK, basic and Type 4 embedding without expanding database support levels.
4. All five CI checks must pass for the exact final commit. Independently verify production signatures on formal assets and the outer offline archive; on AMD64 and QEMU ARM64, rehearse disconnected fresh install, upgrade from formal v4.11.0 and rollback after initial startup failure.
5. Publish GitHub Release and exact GHCR tags, anonymously pull them, update the website and explicitly simulated Demo, and pass public smoke tests before promoting latest. Synchronize the canonical main checkout with clean origin/main.

## Limits

This release does not promise 80% compatibility, complex joins, real cloud-model inference or arbitrary datasource creation. The user's real business system has not been tested; no zero-change migration claim is made. QEMU ARM64 is not physical ARM testing; the public Q&A Demo uses simulated results.
