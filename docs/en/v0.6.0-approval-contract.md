# v0.6.0 Common SQL to approve and execute the contract

**Language:** [English](v0.6.0-approval-contract.md) | [Simplified Chinese](../v0.6.0-approval-contract.md)

Status: A single execution path has been implemented, and upgrade and release acceptance are being completed; it does not belong to B5 transaction approval.

## Application and storage

`request_approval` only saves the application and does not execute SQL. Record the bound tenant, Agent, data source ID and connection configuration summary, SQL original text and normalized SQL, application instructions and trigger reasons, and set a 24-hour validity period. HMAC archive key fields. The approver, approval notes and decision time are saved separately and do not cover the application content. Old records do not have a sealed field and can be viewed but not executed.

Currently, ordinary MCP SQL tools do not have parameter array input, so this path can only seal literal SQL; parameterized approval needs to be designed separately, and additional parameters during execution are not accepted.

## single execution

After the administrator approves, the original Agent calls `execute_approved` and only transmits `approval_id`. The storage layer is claimed atomically by tenant, agent, status and validity period, and `approved` is changed to `claimed`. Only one concurrent call can succeed; `claimed`, failure or unknown result records after process restart cannot be automatically retried.

After claiming, first verify the seal, current Agent identity and audit availability, and then use the original SQL to re-pass the data source configuration, parsing, policy, risk rules, database execution and masking. If the current policy rejects the request, it will still be rejected; manual approval only eliminates the wait for "approval required" this time and does not elevate Agent permissions. The B2 column-level authorization SELECT path does not currently accept ordinary approval execution to avoid bypassing its independent execution contract.

`completed` is successfully submitted; `failed` is explicitly rejected; `unknown` is requested when the database or audit results cannot be determined and manual verification is required. Claim audits and execution audits are associated with approval records, and the execution audit ID is visible in the management API and MCP query results. If the final state persistence fails, the record stays at `claimed` and replay is prohibited.

## Verified and pending verification

The SQLite persistence layer has covered claim, replay, restart, expiration, Agent mismatch and old order rejection. G100 Build 9 PG mode MCP real database test has covered application, approval, single execution, masking, data source change rejection and withdrawal policy rejection. The restricted accounts of PostgreSQL 18 and MySQL 8.4, and the synthetic table MCP real database test all confirmed that no writing is done during the application stage, writing is done once after approval, the audit can be performed, and repeated calls are rejected. Web type checking, 54 tests and build passed; full Go fast regression still needs to be re-run under isolated load. Metadata and audit shard failures, real client interfaces, and deployment upgrade rollbacks are still release thresholds; gaps in these use cases cannot be regarded as production acceptance passes.
