# AgentSQL v1.2.0 MCP OAuth protected resource design

**Language:** [English](v1.2.0-design.md) | [Simplified Chinese](../v1.2.0-design.md)

## target

Provide optional OAuth 2.1 protected resource access for the MCP 2026-07-28 HTTP portal, reusing the authenticated user, agent, and tenant dual identity control chains of v1.1.0. AgentSQL, as a resource server, uses an external OIDC/OAuth authorization server; the console's existing OIDC login is not automatically equivalent to the MCP OAuth access token. The Agent Key entries of old `/mcp` and `/mcp/2026-07-28` remain compatible.

## protocol boundaries

- The OAuth MCP path is `/mcp/oauth`, which requires the resource URI to be configured exactly, such as `https://mcp.example.com/mcp/oauth`; only native loopback addresses are allowed to use HTTP in testing. `/.well-known/oauth-protected-resource/mcp/oauth` publishes metadata containing `resource`, `authorization_servers`, and minimum `scopes_supported`. 401 returns the Bearer `WWW-Authenticate` challenge pointing to it, and insufficient scope returns 403.
- The OAuth Access Token is only read from `Authorization: Bearer`, and the Agent Key is read from `X-AgentSQL-Agent-Key`. Each request checks both credentials, agent status, user mapping, tenant consistency, and permissions, and rejects any one that cannot be proven. Refuse to submit the old `X-AgentSQL-User-Authorization` at the same time to avoid mixing the two sets of personnel identities. Console session tokens, other resource tokens, ID Tokens, or URI query tokens must not be treated as MCP Access Tokens.
- This version only accepts RS256 JWT Access Token issued by the designated external issuer; verifies the authorization server metadata and issuer, JWKS signature, `iss`, `aud`/resource, `exp`, `nbf`, `iat`, and necessary scope. Reject if the JWKS is missing or the rotation is abnormal; the cached valid public key can continue to be verified within the 5-minute cache period. If the IdP is unavailable after the cache expires, the request will be rejected. The issuer and tenant of MCP OAuth must be consistent with the enabled console OIDC identity source to prevent cross-identity source cross-use with the same name `sub`. User mapping uses a locally managed OIDC subject to confirm active status and `query.execute` permissions on a per-request basis. The token does not extend the Agent's SQL permissions. Opaque token/introspection and non-RS256 algorithms are outside the scope of this release.
- The OAuth authorization client is responsible for PKCE, `resource` parameters and pre-registration with the IdP; AgentSQL does not implement authorization server or dynamic client registration in this version. The client also needs to support configuring the fixed Agent Key request header. Formal support statements only cover measured IdP, client and deployment combinations.
- The MCP session is bound to dual identities; approval, B5, and auditing continue to use the user+Agent+tenant constraint of v1.1.0. Old clients are not silently upgraded or downgraded by the new path.

## Acceptance

1. Official MCP Inspector Real OAuth Authorization and Tool Invocation: Discovery Metadata, Allow Queries After Login, R010 Denials, Masking, and Personnel Auditing. Dify uses the old entrance to verify compatibility; mark whether it supports the OAuth flow according to actual capabilities.
2. True IdP and local negative matrix: Error issuer, audience, signature, expiration, scope, user/Agent/tenant, reused console token, lack of independent Agent Key, cross-user session renewal are all rejected before SQL execution.
3. There is no expected schema migration in this version. It is still necessary to verify the upgrade, recovery and configuration of SQLite and PostgreSQL sub-databases from the v1.1.0 official package to disable rollback. Go/Web CI, official releases and signatures, and GHCR accurate tags all pass; according to user requirements, the official website/Demo/`latest` remains v1.0.0.
