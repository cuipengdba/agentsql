# v2.9.0 → v3.0.0 Upgrade and recovery

**Language:** [English](v3.0.0-upgrade.md) | [Simplified Chinese](../v3.0.0-upgrade.md)

Status: candidate procedure. After official package acceptance, use the SHA and environment in the [acceptance record](v3.0.0-acceptance.md).

1. Use the official v2.9.0 `agentsqlctl migrate --check` to confirm combined SQLite metadata schema 23, or separated PostgreSQL metadata schema 22 and independent audit schema 6. Stop administrative and MCP writes on every gateway and wait for B2 leases to expire.
2. Make a complete set of backups at the same point in time for metadata, audit (if branched), `AGENTSQL_SECRET`, audit chain key and configuration; record the hash. Don't just back up the metadata, because the audit outbox and the chain head need to be at the same recovery point.
3. Check the target configuration as v3.0.0 formally `agentsqlctl doctor --config ... --format json`. Expected exit code 0, `current=latest` for all configured storage; no schema migration in this release. Exit code 2 or 1 will stop switching. Check the configuration, history and backup first. `doctor` is read-only and does not equal recovery drills.
4. Start v3.0.0 on the quarantine replica and verify the Agent, data sources, policies, allow and deny queries, masking, and persistent auditing. Check that the newly added `support` in `list_datasources` is only visible to authorized data sources; the actual authorization will not be relaxed due to changes in the statement. After confirmation, the official service will be changed to a unified version. Dual gateways cannot mix versions to accept traffic.
5. When rolling back, stop all v3.0.0 gateways, restore the metadata, audit, keys and configurations backed up at the same point as a whole, use the v2.9.0 official package to execute `migrate --check`, and then verify the login, audit chain and real MCP allow/deny. You must not just replace the binary while retaining the business changes resulting from the upgrade.

This step is only for existing controlled capabilities and designated environments; it does not claim that all database adapters have the same level of production support.
