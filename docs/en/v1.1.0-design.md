# v1.1.0 dual identity control chain design

**Language:** [English](v1.1.0-design.md) | [Simplified Chinese](../v1.1.0-design.md)

## Goals and release boundaries

Each MCP HTTP request simultaneously verifies the active human delegation token and Agent Key. v1.0.0 has covered ordinary queries; this version extends the same identity constraints to approval applications, approval executions and B5 cross-request sessions. Old single-agent deployments retain the original behavior. v1.1.0 individually tested, merged, tagged and created an official GitHub Release. According to the requirements of the product owner, the official website and public network Demo will remain v1.0.0, and will be updated once after v1.5.0 is completed.

## safe invariants

1. The delegation token is issued from the server session and is bound to the user, agent, tenant, token ID, validity period and active console session; the MCP portal is re-authenticated each time. The console can revoke a single token with the original token, and the remaining delegation and login sessions will continue to be valid. Requests are rejected when the user deactivates, logs out, revokes the session, Agent deactivates, tenant changes, or task authorization expires.
   v1.0.0 Issued delegation credentials without a token ID retain their original validity period of up to 30 minutes and can be revoked by exiting the parent session; individual revocation is only supported for new tokens.
2. The entrusted approval form saves the requesting user ID and adds it to the immutable HMAC seal; only the same user, the same Agent, and the same tenant can read and receive it. The claim predicate checks the user in an atomic update to the database, and rejection does not consume the approval ticket. Old approval slips cannot be collected through entrustment requests.
3. The B5 session principal contains an auditable user ID and a digest derived from the user, agent, tenant triplet authenticated by the server. This principal participates in persisting sessions, key AAD, continuation proof, and plan digest. Different users or single Agent requests cannot continue the session even if they hold the session ID and continuation secret. User IDs that exceed the upper limit of B5 identity length are directly rejected.
4. The approval of B5 begin must match the plan digest containing the above principal; the audit still records the original transaction ID, session ID, plan digest and Agent, and the ordinary approval audit also records the entrusting user. Unknown authorization, audit failure and identity mismatch are all rejected before obtaining the business write connection.
   The DML grant is still retrieved according to the authenticated Agent, and then mapped to the authenticated delegation principal for binder verification; the delegated user will not obtain a grant that the Agent does not originally have.
5. When an audit occurs during approval execution or the database has an uncertain result, the `claimed`/`unknown` final state semantics are retained and the write is not automatically replayed.
6. The console password and LDAP login limit the number of attempts per minute by tenant and account to avoid directly exposing the existence of the account; the MFA challenge remains a one-time consumption. This current limit currently belongs to the single-instance boundary, and multi-instance shared current limit is reserved for v1.4.0.

## acceptance matrix

| path | Must verify |
|---|---|
| Delegate approval | Persist the applicant and seal; another user and a request without delegation cannot read or claim it. The correct user may claim it only once; an invalid token cannot enter a tool. |
| B5 session | The principal can establish a session; the same user can continue; changing the user, Agent or tenant fails; the old single-Agent session is not taken over by the principal |
| B5 plan | The plan principal is consistent with the session principal; the plan digest binds the identity; reject if authorization, auditing, or connection status cannot be proven |
| Compatibility | The original approval and B5 test of non-entrusted deployment continue to pass; upgrade and migration pass in SQLite and PostgreSQL |

Evidence of real databases, MCP clients, upgrades and rollbacks, CI and release signatures are documented in the Release Acceptance Report. Combinations that have not yet been tested must be clearly marked, and the scope of production support cannot be expanded based on this.
