# v4.5.0 design and release acceptance contract

[Simplified Chinese](../v4.5.0-design.md) | [English](v4.5.0-design.md)

Status: candidate design, not released. The formal comparison baseline is the unmodified client, server, and public interfaces of [SQLBot Community v1.10.3](https://github.com/dataease/SQLBot/releases/tag/v1.10.3). If the latest official version changes before release, pin the new baseline and repeat acceptance for its changes. Earlier v1.10.2 evidence can identify regressions but cannot establish a v1.10.3 pass.

## User objective

AgentSQL implements a complete data Q&A product with its own Go service, Web pages, and database security gateway. v4.5.0 compares the public pages, API, MCP, and embedding modes of SQLBot Community and delivers a downloadable offline archive with trusted verification and one-command installation. The pages use AgentSQL branding and an independent implementation; original static assets are used only for isolated acceptance. The user will arrange cutover and rollback of their actual business system after v4.5.0 ships; issues found during that integration will be planned separately.

## Scope and acceptance units

| Scope | Implementation contract | Evidence required for release |
| --- | --- | --- |
| Pages and management | Own Chinese and English pages cover the original community-visible login, Q&A, datasource, model, assistant, workspace, user, permission, terminology, training, prompt, and settings tasks | Complete the same save, reopen, revoke, and error flows in both the unmodified original browser and AgentSQL's own browser; list every uncovered entry by page |
| API and sessions | Preserve community paths, methods, authentication, request and response shapes, stream events, error codes, and session lifecycle | Compare every route using the pinned original image and candidate in the same environment; runtime OpenAPI inventories locate differences but their counts are not compatibility percentages |
| MCP and embedding | Preserve original MCP clients, assistant calls, API keys, iframe/SDK behavior, navigation, callbacks, and integration modes | Run unchanged original clients and synthetic third-party callers through allowed, revoked, expired, cross-user, and cross-workspace cases; retain request and audit evidence |
| Data and Q&A | Check the community data sources, files, charts, analysis, prediction, exports, and multi-turn context connector by connector | Execute against a real local model and databases; compare original outcomes and failure semantics for the same input, and record versions, roles, and support boundaries |
| Security gateway | Enforce identity, workspace, datasource, table/column, row rule, masking, approval, controlled execution, and durable audit across every entry | Show no unauthorized row escapes on forged identity or schema, old-result reads after revocation, concurrent change, model-generated forbidden SQL, database failures, and audit failures |
| Offline delivery | Authenticate the complete archive with a trusted key and verifier obtained outside the archive before checking inner assets and installing; fail closed on missing database extension or runtime-role privileges | Formal same-commit assets, production-key signatures, disconnected amd64 and arm64 installation, upgrade, failed-start rollback, startup, and downloaded-asset checks; development keys and older assets do not count as formal acceptance |

Cutover of the user's actual business system is not a v4.5.0 release gate. The unchanged original clients and synthetic third-party callers still require the compatibility checks above. Release notes must say that the user's business system has not been validated; they must not claim zero-change replacement of that system or 100% compatibility.

## Open retrieval-parameter and knowledge-recall gap

On 2026-11-02, valid administrator sessions compared `GET /api/v1/system/parameter` on unchanged SQLBot Community v1.10.3 and the Go candidate at commit `c3fd043c`. The original returned 18 parameters; that candidate returned 9. Its missing keys were `embedding.enabled`, `embedding.table_enabled`, `embedding.terminology_similarity`, `embedding.terminology_top_count`, `embedding.data_training_similarity`, `embedding.data_training_top_count`, `embedding.table_count`, `embedding.table_alpha`, `embedding.keyword_enabled`, and `embedding.datasource_count`. The original settings page edits these values, and its service loads the effective settings at the start of each question task. Evidence: `D:\CodexLS\outputs\agentsql-v450\parameter-gap-v1103-20261102.md`. The candidate has since added the ten API parameters in stages; table and datasource behavior parity remains unverified.

Acceptance requires actual behavior: save, reopen, restart, input bounds and concurrent updates; switches and thresholds must affect terminology, training-example, table and datasource retrieval. Compare the same flows in the unchanged original client and AgentSQL's own page. AgentSQL must retrieve only currently gateway-visible schema and authorized knowledge for the active identity; revocation must invalidate old vectors and prompt caches. Model, vector-store or audit failures must not fall back to unauthorized schema. Ten inert response fields or display controls do not close this gap. v4.5.0 cannot claim complete Q&A parity until it passes.

Further inspection of the original v1.10.3 terminology and training retrieval code confirmed that `embedding.enabled=false` disables only vector search: lexical matches still return. The two `top_count` values limit vector candidates only. Earlier candidate commits `3482f54b` and `8085a63d` applied the switch and counts to lexical results. Focused tests and CI passed, but that behavior differed from the original, so a following commit withdraws it. The correct implementation must retain authorized lexical matching while adding real vector candidates, similarity thresholds, and count limits, then compare the same inputs against the original and candidate. This gap still blocks a complete Q&A parity claim.

An isolated local prototype loaded the same Apache-2.0 text2vec ONNX model from the original image using the native Go backend of Apache-2.0 Hugot v0.6.0. Three Chinese inputs produced 768-dimensional vectors. Normalized cosine similarity between the revenue and sales-income questions was 0.816023 in Go versus 0.816024 in the original Python runtime; similarity between the revenue and weather questions was 0.313403 in both. Initial Go load took about 6.2 seconds and the three-input run about 7.6 seconds. The exact inputs, model SHA-256, environment, and commands are recorded in `D:\CodexLS\outputs\agentsql-v450\embedding-go-prototype-v1103-20261102.md`. This establishes inference feasibility, not an integrated product feature. Authorized knowledge indexing, effective settings, invalidation and revocation, concurrency, fail-closed behavior, and dual-architecture model delivery in the signed offline archive remain open.

## Local vector retrieval implementation in this candidate

The candidate can now load a local ONNX model from the absolute `embedding_model_path`; it does not download weights at runtime. Terminology and training examples are first filtered by current workspace, datasource, and enabled state. Training SQL is also checked against currently visible tables and columns and the read-only parser. Lexical matches remain available; cosine ranking is applied only to the remaining authorized vector candidates and duplicate results are removed. The system parameters endpoint exposes `embedding.enabled` and the similarity and vector candidate limits for terminology and training. Administrator changes use the existing audited transaction. An inference failure rejects that knowledge retrieval. The pinned local Go model comparison and focused tests for parameter authorization and invalid values, datasource isolation, invisible SQL, and inference failure passed. This is partial candidate acceptance.

This branch also adds table preselection. It builds candidates only from currently authorized columns, scores the question and table schema with the local model, and optionally blends lexical scores using `embedding.table_alpha`. `embedding.table_count` limits ordinary candidates while explicitly mentioned table names and comments remain. A longer name wins at the same mention, and an unknown full quoted name cannot select a substring. The system parameters endpoint persists `embedding.table_enabled` and `embedding.keyword_enabled`, and both affect the current question. If the model is unavailable or vectors are incomplete, all currently authorized tables remain; permission revocation during inference must stop before generation. Existing saved settings gain new defaults during upgrade. Focused local tests cover persistence, invalid values, limits, switches, and revocation. This stage did not yet reproduce the original's keyword extraction. The later persistent-index implementation and its limited acceptance are described below; unchanged-client end-to-end comparison remains open.

The third-party datasource catalog MCP assistant path now applies `embedding.datasource_count` to candidate preselection. It first checks the registered catalog and currently authorized mappings, then uses the local model to rank catalog names against the question by cosine similarity. It narrows candidates only when the limit is smaller than the set. Missing or invalid vectors preserve all candidates and still require an explicit model choice. A single shortlisted source still requires selection audit, model lease, and catalog mapping rechecks; the model cannot choose an excluded ID. The original ordinary `/api/v1/chat/start` requires an explicit datasource. The original assistant `/api/v1/chat/assistant/start` may start without one, then choose from the assistant's available datasources on the first question. The third-party MCP catalog indexes only catalog names, while the embedded assistant uses schema content visible under current permissions. The candidate now encrypts and persists vectors with content fingerprints scoped to workspace and user. Changed content, pinned model, or user forces recomputation. Each request still obtains current visible content and rechecks authorization after selection; damaged cache entries preserve the full authorized candidate set. The original precomputation lifecycle, behavior beyond 32 candidates, and production-scale performance remain unverified, so full parity is unproven. The signed offline model archive is not formally published.

The candidate branch now has source-less conversation creation, selection from currently authorized candidates on the first question, atomic binding, and revocation rechecks. A single candidate bypasses the selector model; with multiple candidates, an invalid or revoked model-picked ID is rejected. An empty question cannot bind a source. Local vector preselection for an embedded assistant now uses the datasource description, currently gateway-visible tables and columns, and remarks attached to those visible objects. Invisible metadata does not enter the vector input; oversized content preserves all candidates. Data-permission rules are rechecked after inference, and a change stops source binding. The original assistant page produced a database-verified count of 2400 orders using the local 4B model; the unchanged original SDK against the candidate produced a real-model result, history reload, and guest-revocation denial on a different synthetic sales table. Those questions and datasets differ, so that SDK test is not result equivalence. A separate candidate compatibility API call used the same orders database, question, and model and returned 2400 with an allowed gateway audit; its SQL uses `pg_catalog.count(*)` under the security contract. The unchanged original page was then connected to candidate APIs through a local static proxy. On the same orders database, question, and model, it displayed `row_count=2400`. A local binary from exact commit `c92f63ac`, with all five CI checks passing, repeated the page result and historical reload at 2400 with no failed HTTP responses. After revoking the isolated datasource alias, the old chat returned 404 and the original page no longer displayed the old result. The security contract that rejects the whole history list when the gateway is unavailable remains intact. This proves one page-level numeric and history-reload comparison only; stream termination, parity with the original persistent vectors, full behavior, failure, and concurrency acceptance remain open.

A local Go test with networking disabled loaded the pinned ONNX model, first checked the original sentence-vector scores, and then ran datasource and table preselection on synthetic Chinese questions and names. Both selected the expected candidate. This covers a local amd64 machine only; arm64, the unchanged original client, and large-scale indexing remain release gates.

The inference loader checks every pinned SQLBot v1.10.3 model file digest and rejects missing, altered, or symlinked files. This runtime check does not replace external-key signature verification, installation checks, or rollback for the offline archive.

The embedded `internal/chatbi/pinned_embedding_model.json` is now the shared file inventory for the runtime and `scripts/package-chatbi-model.py`. The builder checks the entire pinned directory, creates a deterministic archive containing the model card and file inventory, and verifies every archive member after writing. Two builds with the same input and timestamp both produced SHA-256 `cea4c870ccd49d0551aaec8ee713fe2b2a991537138b82658142dc311ac193af`. The local archive and checksum sidecar are not yet part of a formally signed Release, nor have installation, upgrade, and rollback been accepted.
The builder's `--verify` mode can independently check an existing archive against the pinned inventory without extracting it. A formal offline installer must verify the outer signed release manifest before calling this check.

The v4.5.0 release inventory grows from 15 to 17 assets by adding the pinned ChatBI model archive and its SHA-256 sidecar. The Go release verifier, offline transport bundle, and offline installer's asset inventory check the versioned set; older releases still use 15 assets. The model and sidecar must appear in signed `SHA256SUMS` and provenance. Production assembly requires an explicit pinned local model directory and Python executable, and rechecks archive members and hashes.

The offline installer now verifies release signatures, validates and safely extracts each model archive member, then asks the authenticated release binary to check the pinned model again with `chatbi verify-embedding-model`. The installation script checks the model before stopping ChatBI, verifies it again after copying, places it in a managed directory, and configures the service path. Failure restores the previous directory and configuration from backup. An offline local Linux amd64 container completed a `no-start` fresh installation using the real pinned model and verified the installed directory with the new command. A separate isolated fault injection verified that a failed initialization rolls back a fresh install. Fresh install, upgrade, old-version rollback, and service startup from a genuinely signed air-gapped bundle on both architectures still require acceptance; these two narrow tests do not pass the release gate.

History response endpoints now check each prior answer against the current permission, datasource binding, and identity fingerprint. After a rule change, or when an old record lacks a fingerprint, only the user-authored question and lifecycle metadata remain; old SQL, charts, model analysis, results, and query re-execution are suppressed. New records under the current policy remain readable. Rules are checked again before returning the response.

## Security and deployment boundaries

Client-supplied users, workspaces, database settings, rules, and model output are inputs to validate. The Go Q&A service uses current server-side identity and bindings and rechecks authorization before and after model prompts, historical reads, previews, exports, API, MCP, and embedded queries. Actual SQL executes only through the AgentSQL controlled gateway. When authorization, policy, binding, or audit proof is unavailable, no result is returned; an old cached result cannot stand in for current authorization.

The branch now retains the data-permission snapshot from schema discovery and checks it again after vector knowledge retrieval, before model generation, and after generation, before the controlled query. If a rule is revoked during retrieval, stale table and column metadata does not reach the generator; if revoked during generation, the SQL does not reach the query. Historical SQL must pass the current visible-table and column check, and its separately encrypted permission, user, and binding fingerprint must match the current turn. Older turns without a fingerprint are omitted from the model prompt. Local tests passed for dropping old history after a new row rule, retaining new history under an unchanged rule, and conservatively omitting legacy records. Original-client and real concurrent-environment acceptance remain open.

The offline archive installs application components by default. The native PostgreSQL binder runs on the database server and needs trusted database-side delivery or explicit preinstallation. For PostgreSQL, the installer must connect to the target database as the actual reader and check binder capability and grants before changing the application installation. The public Demo offers only clearly labeled simulated model interaction and has no real model configured or called; real-model acceptance takes place locally.

## Release decision

On 2026-11-04, the pinned real ONNX model ran in a disconnected Linux AMD64 container limited to 2 CPUs and 4 GiB. First indexing and selection of 32 synthetic authorized sources took 23.18 seconds; reuse after a new model instance took 2.22 seconds. For 32 authorized tables, the corresponding times were 30.93 and 2.14 seconds. Both real-model tests passed in a 99.84-second process; the measurements exclude model-instance loading. Evidence: `D:\CodexLS\outputs\agentsql-v450\persistent-index-real-model-32-20261104.md`. This small synthetic slice still needs production-scale, concurrent, real-schema and failure-performance acceptance.

Under the same limits, 128 synthetic authorized tables took 1 minute 57.02 seconds to index and select cold, while reuse after a new model instance took 2.13 seconds. The real-model test exited successfully. This exposes a first-question latency risk to resolve before release or accept against an explicit production performance target and real-scale evidence. The 500-table limit, concurrency and actual customer schemas remain untested. Evidence: `D:\CodexLS\outputs\agentsql-v450\persistent-index-real-model-128-20261104.md`.

A second run requiring selection of the expected `weather` table took 1 minute 57.73 seconds cold and 2.76 seconds after restart. It selected the correct table and passed, but does not close the production performance gate.

Timed stages confirm the bottleneck. At 2 CPUs and 4 GiB, cold indexing of 128 tables took 1 minute 58.69 seconds: the question vector took 2.23 seconds, and the four 32-table inference batches took 28.44, 28.11, 28.31, and 31.29 seconds. At 4 CPUs and 4 GiB, cold indexing took 1 minute 13.62 seconds: the question vector took 1.82 seconds, and the four batches took 17.25, 17.73, 18.47, and 17.98 seconds. Warm-index runs took 2.29 and 1.97 seconds, and both selected the expected table. Cold inference is the bottleneck; more CPU still leaves a substantial first-question delay. Authorized index prewarming, concurrency, and an explicit production performance target need further acceptance.

Concurrent cold builds in one process now share one table-vector inference only when the user, source, model, and ordered authorized schema match. A waiting request can cancel independently. The in-memory flight key is HMAC-protected; changed columns have separate keys and still require each request's later permission-snapshot recheck. Focused tests cover cancellation, duplicate-build sharing, and changed-schema isolation. Real-model concurrent load, cross-process coordination, and index-failure acceptance remain open. This does not shorten a single first question's cold inference.

If the request that owns a shared build is canceled, a still-live waiter attempts one new build under the same authorized key rather than using the canceled result; a focused race test covers this path. A waiter whose own context is canceled exits promptly, and retry does not grant access.

The fixed real ONNX model also passed a two-request cold-build slice with the same user, source, and 32 authorized tables in a disconnected 2-CPU/4-GiB container.
