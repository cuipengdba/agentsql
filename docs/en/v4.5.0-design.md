# v4.5.0 design and release acceptance contract

[Simplified Chinese](../v4.5.0-design.md) | [English](v4.5.0-design.md)

Status: candidate design, not released. The formal comparison baseline is the unmodified client, server, and public interfaces of [SQLBot Community v1.10.3](https://github.com/dataease/SQLBot/releases/tag/v1.10.3). If the latest official version changes before release, pin the new baseline and repeat acceptance for its changes. Earlier v1.10.2 evidence can identify regressions but cannot establish a v1.10.3 pass.

## User objective

AgentSQL implements a complete data Q&A product with its own Go service, Web pages, and database security gateway. v4.5.0 compares the public pages, API, MCP, and embedding modes of SQLBot Community and delivers a downloadable offline archive with trusted verification and one-command installation. The pages use AgentSQL branding and an independent implementation; original static assets are used only for isolated acceptance. The user will arrange cutover and rollback of their actual business system after v4.5.0 ships; issues found during that integration will be planned separately.

## Scope and acceptance units

| Scope | Implementation contract | Evidence required for release |
| --- | --- | --- |
| Pages and management | Own Chinese and English pages cover the original community-visible login, Q&A, datasource, model, assistant, workspace, user, permission, terminology, training, prompt, and settings tasks | Complete the same save, reopen, revoke, and error flows in both the unmodified original browser and AgentSQL's own browser; list every uncovered entry by page |
| API and sessions | Preserve community paths, methods, authentication, request and response shapes, stream events, error codes, and session lifecycle | Compare every route using the pinned original image and candidate in the same environment; runtime OpenAPI inventories locate differences but their counts are not compatibility percentages |
| MCP and embedding | Preserve original MCP clients, assistant calls, API keys, iframe/SDK behavior, navigation, callbacks, and integration modes | Run unchanged original clients and synthetic third-party callers through allowed, revoked, expired, cross-user, and cross-workspace cases; retain request and audit evidence |
| Data and Q&A | Check the community data sources, files, charts, analysis, prediction, exports, and multi-turn context connector by connector | Execute against a real local model and databases; compare original outcomes and failure semantics for the same input, and record versions, roles, and support boundaries |
| Security gateway | Enforce identity, workspace, datasource, table/column, row rule, masking, approval, controlled execution, and durable audit across every entry | Show no unauthorized row escapes on forged identity or schema, old-result reads after revocation, concurrent change, model-generated forbidden SQL, database failures, and audit failures |
| Offline delivery | Authenticate the complete archive with a trusted key and verifier obtained outside the archive before checking inner assets and installing; fail closed on missing database extension or runtime-role privileges | Formal same-commit assets, production-key signatures, disconnected amd64 and arm64 installation, upgrade, failed-start rollback, startup, and downloaded-asset checks; development keys and older assets do not count as formal acceptance |

Cutover of the user's actual business system is not a v4.5.0 release gate. The unchanged original clients and synthetic third-party callers still require the compatibility checks above. Release notes must say that the user's business system has not been validated; they must not claim zero-change replacement of that system or 100% compatibility.

## Open retrieval-parameter and knowledge-recall gap

On 2026-11-02, valid administrator sessions compared `GET /api/v1/system/parameter` on unchanged SQLBot Community v1.10.3 and the Go candidate at commit `c3fd043c`. The original returned 18 parameters; that candidate returned 9. Its missing keys were `embedding.enabled`, `embedding.table_enabled`, `embedding.terminology_similarity`, `embedding.terminology_top_count`, `embedding.data_training_similarity`, `embedding.data_training_top_count`, `embedding.table_count`, `embedding.table_alpha`, `embedding.keyword_enabled`, and `embedding.datasource_count`. The original settings page edits these values, and its service loads the effective settings at the start of each question task. Evidence: `D:\CodexLS\outputs\agentsql-v450\parameter-gap-v1103-20261102.md`. Commit `704d354a` added five of those settings; the other five remain open.

Acceptance requires actual behavior: save, reopen, restart, input bounds and concurrent updates; switches and thresholds must affect terminology, training-example, table and datasource retrieval. Compare the same flows in the unchanged original client and AgentSQL's own page. AgentSQL must retrieve only currently gateway-visible schema and authorized knowledge for the active identity; revocation must invalidate old vectors and prompt caches. Model, vector-store or audit failures must not fall back to unauthorized schema. Ten inert response fields or display controls do not close this gap. v4.5.0 cannot claim complete Q&A parity until it passes.

Further inspection of the original v1.10.3 terminology and training retrieval code confirmed that `embedding.enabled=false` disables only vector search: lexical matches still return. The two `top_count` values limit vector candidates only. Earlier candidate commits `3482f54b` and `8085a63d` applied the switch and counts to lexical results. Focused tests and CI passed, but that behavior differed from the original, so a following commit withdraws it. The correct implementation must retain authorized lexical matching while adding real vector candidates, similarity thresholds, and count limits, then compare the same inputs against the original and candidate. This gap still blocks a complete Q&A parity claim.

An isolated local prototype loaded the same Apache-2.0 text2vec ONNX model from the original image using the native Go backend of Apache-2.0 Hugot v0.6.0. Three Chinese inputs produced 768-dimensional vectors. Normalized cosine similarity between the revenue and sales-income questions was 0.816023 in Go versus 0.816024 in the original Python runtime; similarity between the revenue and weather questions was 0.313403 in both. Initial Go load took about 6.2 seconds and the three-input run about 7.6 seconds. The exact inputs, model SHA-256, environment, and commands are recorded in `D:\CodexLS\outputs\agentsql-v450\embedding-go-prototype-v1103-20261102.md`. This establishes inference feasibility, not an integrated product feature. Authorized knowledge indexing, effective settings, invalidation and revocation, concurrency, fail-closed behavior, and dual-architecture model delivery in the signed offline archive remain open.

## Local vector retrieval implementation in this candidate

The candidate can now load a local ONNX model from the absolute `embedding_model_path`; it does not download weights at runtime. Terminology and training examples are first filtered by current workspace, datasource, and enabled state. Training SQL is also checked against currently visible tables and columns and the read-only parser. Lexical matches remain available; cosine ranking is applied only to the remaining authorized vector candidates and duplicate results are removed. The system parameters endpoint now exposes five effective settings: `embedding.enabled` and the similarity and vector candidate limits for terminology and training. Administrator changes use the existing audited transaction. An inference failure rejects that retrieval. The pinned local Go model comparison and focused tests for parameter authorization and invalid values, datasource isolation, invisible SQL, and inference failure passed. This is partial candidate acceptance. Table and datasource vector retrieval, the other five settings, full original-client comparison, production indexing performance, and the signed offline model archive remain open.

The inference loader checks every pinned SQLBot v1.10.3 model file digest and rejects missing, altered, or symlinked files. This runtime check does not replace external-key signature verification, installation checks, or rollback for the offline archive.

History response endpoints now check each prior answer against the current permission, datasource binding, and identity fingerprint. After a rule change, or when an old record lacks a fingerprint, only the user-authored question and lifecycle metadata remain; old SQL, charts, model analysis, results, and query re-execution are suppressed. New records under the current policy remain readable. Rules are checked again before returning the response.

## Security and deployment boundaries

Client-supplied users, workspaces, database settings, rules, and model output are inputs to validate. The Go Q&A service uses current server-side identity and bindings and rechecks authorization before and after model prompts, historical reads, previews, exports, API, MCP, and embedded queries. Actual SQL executes only through the AgentSQL controlled gateway. When authorization, policy, binding, or audit proof is unavailable, no result is returned; an old cached result cannot stand in for current authorization.

The branch now retains the data-permission snapshot from schema discovery and checks it again after vector knowledge retrieval, before model generation, and after generation, before the controlled query. If a rule is revoked during retrieval, stale table and column metadata does not reach the generator; if revoked during generation, the SQL does not reach the query. Historical SQL must pass the current visible-table and column check, and its separately encrypted permission, user, and binding fingerprint must match the current turn. Older turns without a fingerprint are omitted from the model prompt. Local tests passed for dropping old history after a new row rule, retaining new history under an unchanged rule, and conservatively omitting legacy records. Original-client and real concurrent-environment acceptance remain open.

The offline archive installs application components by default. The native PostgreSQL binder runs on the database server and needs trusted database-side delivery or explicit preinstallation. For PostgreSQL, the installer must connect to the target database as the actual reader and check binder capability and grants before changing the application installation. The public Demo offers only clearly labeled simulated model interaction and has no real model configured or called; real-model acceptance takes place locally.

## Confirmed compatibility gap

In an isolated SQLBot v1.10.3 original API with a simulated model and real synthetic PostgreSQL rows, two nonstream `mcp_question` calls each returned two rows, `success=true`, a `title`, and a table `chart`, with Base64 SQL and a numeric `datasource` inside `data`. The original still returns chart configuration when `return_img=false`; that flag only skips the rendered image. The candidate now fills these JSON fields and persists a 20-character question-derived title after the first successful question. Focused tests cover the absence of a repeated title on the next question, chart JSON when images are off, and the controlled audited query. The original model can generate its own title and richer charts; the candidate currently supplies a truncated question title and table configuration. Those behaviors, full error responses, and the unchanged original client still need comparison. Isolated original evidence: `D:\CodexLS\outputs\agentsql-v450\original-v1103-mcp-stubbed-model-data-20261101.md`; it is not local real-model acceptance.

In an isolated environment at commit `aefb8897`, the MCP Python SDK inside the original v1.10.3 image used the candidate SSE endpoint to complete both nonstream and stream questions against local Qwen and a real synthetic PostgreSQL table; both controlled gateway queries returned two rows and were audited. This covers one SDK client path, not an unchanged SQLBot application or zero-change business-system cutover. Invalid-input comparison with the original service also confirmed HTTP 400 for an inaccessible chat and a nonnumeric string datasource ID, while a list-valued datasource ID returned 422. The candidate now uses those statuses without running a query. The original returned 200 for some invalid-token `mcp_start` and `mcp_model_list` calls and 500 for an empty question; the candidate continues to reject these requests under its gateway authentication and input-validation requirements. Remaining error responses still need comparison. Evidence: `D:\CodexLS\outputs\agentsql-v450\original-image-sdk-real-qwen-pg-aefb8897-20261102.md`.

SQLBot Community v1.10.3 accepts `lang` on `POST /api/v1/mcp/mcp_question`: `zh-CN`, `zh-TW`, `en`, `ko-KR`, and `th-TH` temporarily override the language for that request, and the Q&A task uses it to choose the model prompt language. The original `get_user` resets the transient MCP user language to Simplified Chinese before every request, so omission, `null`, and unsupported strings use Simplified Chinese; an isolated original API probe confirmed these branches. The candidate Go handler now parses the field and passes a request-scoped language to the SQL generation model prompt; the streamed record heading also uses the five original locale resources, while MCP assistant responses use the original fixed Simplified Chinese heading. Focused tests cover the five languages, default, invalid value, and account-language non-persistence. This closes only part of the semantic gap: the other streamed explanations, charts, and analysis output have not been compared with the original language behavior. The unchanged original SDK has now exercised these language-input branches for one question shape. Full streamed content, revocation races and more questions still need comparison; do not claim complete MCP compatibility before they pass.

A concurrent HTTP fixture now lets two separate MCP chats for the same user reach the model phase simultaneously with English and Thai request languages, then releases them individually. Each model call received its own language, each streamed record heading used the corresponding locale, the stored account language stayed unchanged, and each request performed one controlled gateway query. Focused standard and `-race` tests passed under Go 1.26.10. This proves request isolation only in the candidate fixture; unchanged original MCP clients, concurrent real-model behavior, and the remaining localized output still require comparison.

The unchanged SQLBot v1.10.3 Python MCP SDK from the pinned official image then opened two independent SSE sessions and sent English and Thai `mcp_question` calls to the current candidate concurrently. Local real Qwen and PostgreSQL 16 returned the two synthetic east/west rows in both calls, with English and Thai streamed record headings respectively; gateway audits 2055 and 2058 each allowed two rows without error. The script exited 0 and the isolated candidate container was removed. Evidence: `D:\CodexLS\outputs\agentsql-v450\mcp-v1103-concurrent-language-real-qwen-20261102.md`. This compares two languages, one question and the original SDK only; original-server concurrent output, all localized content, revocation races and business-system zero-change cutover remain unverified.

The same original SDK then checked the other three supported values, `zh-CN`, `zh-TW` and `ko-KR`, in separate new chats. Local Qwen and PostgreSQL 16 returned the two synthetic east/west rows in each case, with the corresponding streamed record heading; gateway audits 2065, 2072 and 2079 each allowed two rows. All five supported languages have now passed this one original-SDK question shape. Further questions and complete localized output still need comparison; see the same evidence report.

The unchanged MCP SDK in the same official v1.10.3 image then sent omission, explicit `null`, and unsupported `xx-XX` through a binary extracted from the current v4.5.0 candidate package. Local Qwen and PostgreSQL 16 returned the two east/west rows and Simplified Chinese record heading in every call; gateway audits 2086, 2093 and 2100 each allowed two rows. This remains one question shape through the SDK, not full output, other clients or revocation-race acceptance.

One model ID in SQLBot Community v1.10.3 can map to multiple workspaces; an administrator can list, replace, append, and remove mappings. An isolated original API probe confirmed that the first model automatically becomes the **global default** even with no workspace mappings; removing every mapping leaves the model and global default flag intact. Original source also includes the global default in each workspace's available model list. An earlier candidate stored a model separately in one workspace and rejected cross-workspace mapping; this branch now has a global catalog and explicit mappings, with full release acceptance still pending. A compatible implementation must preserve stable model IDs, shared configuration and credentials, independent mappings, and an administrator-controlled global default pointer. Mapping changes must check current identity, authorization, audit, and revisions in one transaction; a revoked mapping must not reuse an old model or return an old result. Global model availability grants no database or data permission. The unmodified client must pass all four mapping operations, model edits and key rotation, concurrent revocation, and upgrade migration. The presence of a route or a static route count is not behavioral evidence.

The candidate question path records the selected model's revision and encrypted-body digest and re-reads it before generation, before and after the controlled query, and before return. Until catalog activation it continues to use the workspace-local default. Synthetic negative tests rotate that key during generation or gateway execution and confirm that the old request returns neither SQL nor rows. A new catalog read branch, exercised with a manually constructed active state in tests, resolves the same global default in another workspace and rejects an old lease after catalog cutover, default-pointer change, or credential rotation; rotation during generation also prevents a gateway call. All four mapping HTTP routes, global model list/detail/create/edit/delete, global default switching, the original default probe, and the model connectivity probe use the new catalog in a synthetic active state; the connectivity probe checks the model revision again before returning. AgentSQL's own model page APIs for read, list, create, edit, delete, set default, and connectivity check also use the catalog; a new workspace mapping selector appears only when the catalog is active. A real-browser preview with mocked APIs checked the Chinese and English controls, the mapping PUT request, and hiding the selector while the catalog is inactive; an isolated Go HTTP handler with a synthetic control store subsequently passed a browser mapping round trip; production and original-client acceptance remain incomplete. The assistant page and MCP workspace model lists use explicit mappings, excluding the unmapped global default as the original `by_ws` route does; focused tests cover both lists after mapping revocation. Other tests cover administrator restrictions, mapping counts, credential redaction, preserving or rotating a key on edit, old-request revocation, default deletion denial, and rollback on audit failure. Legacy workspace-local model writes check the activation marker in the same control-store transaction and reject writes after cutover to prevent a fork between model stores. Formal catalog activation, production browser acceptance, remaining MCP/embed entries, complete original-client behavior comparison, and historical-result revocation remain unfinished.

Multi-source MCP assistant selection now resolves its model through the same model path. In a synthetic active catalog it uses the global default and rejects the query if the model key rotates during selection or a subsequent request check. The original chat and MCP question `custom_model` field can select the global default or a model explicitly mapped to the current workspace; revoking a mapping during a question clears SQL and results and prevents the gateway query. Assistant configuration saves also validate current mappings; an embedded assistant automatically uses its configured mapped model at runtime, rejects a client override, and stops answering after mapping revocation. Focused tests cover active catalog selection, unmapped denial, and revocation during execution; advanced assistants and end-to-end comparison with the original client remain incomplete.

A read-only control-store preflight for the future migration scans workspace-local models, detects conflicting configurations or credentials under one model ID, counts prospective mappings, and requires an explicit decision when workspace defaults differ or only non-default models exist. Its report omits model endpoints and keys. An administrator can stage the old models as an encrypted global catalog, explicit mappings, and a default pointer in one control-store transaction with a management audit. An audit failure rolls back every staged object; a changed source snapshot makes a retry fail. Internal mapping transactions can now append, replace, and remove multiple workspaces for one model; they check the administrator, model revision and target workspaces, then update mappings, model revision and audit in one transaction. Focused tests cover cross-workspace mapping, stale revisions, duplicate or missing targets, audit rollback, and cleanup after workspace deletion. An internal activation transaction rechecks the old model snapshot digest and staged catalog, then writes the active marker and audit in the same transaction. Focused tests cover revoking old requests and writes, a wrong digest, a non-admin caller, changed source or target state, and audit rollback. Administrator-only preflight, stage, and activate APIs now complete an HTTP cutover on synthetic data. An isolated browser saved and reloaded mappings in both languages; the local evidence is D:\CodexLS\outputs\agentsql-v450\model-catalog-live-browser-20261101.md. The production catalog is **not active**; formal upgrade and rollback rehearsal, the installer upgrade gate, and original-client comparison remain unfinished.

## Release decision

The latest formal version is v4.4.0; v4.5.0 remains a draft PR. Completed slices of original-page, PostgreSQL/MySQL, local-model, and script testing establish only their recorded environments and actions. Complete page and API function coverage, the full security-negative matrix, original MCP and embedded clients, the final dual-architecture signed offline archive, and public deployment acceptance remain open. Publish the v4.5.0 Release, website, and Demo together only after these gates have reviewable evidence. Actual business-system cutover follows the release; avoid claims of "100% compatible" or completed zero-change replacement of the user's system.
