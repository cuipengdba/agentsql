# v4.5.0 design and release acceptance contract

[Simplified Chinese](../v4.5.0-design.md) | [English](v4.5.0-design.md)

Status: candidate design, not released. The formal comparison baseline is the unmodified client, server, and public interfaces of [SQLBot Community v1.10.3](https://github.com/dataease/SQLBot/releases/tag/v1.10.3). If the latest official version changes before release, pin the new baseline and repeat acceptance for its changes. Earlier v1.10.2 evidence can identify regressions but cannot establish a v1.10.3 pass.

## User objective

AgentSQL implements a complete data Q&A product with its own Go service, Web pages, and database security gateway. Existing SQLBot Community integrations should switch services without changing business-system URLs, requests, authentication, callbacks, or embedding code. Delivery also requires a downloadable offline archive with trusted verification and one-command installation. The pages use AgentSQL branding and an independent implementation; original static assets are used only for isolated acceptance.

## Scope and acceptance units

| Scope | Implementation contract | Evidence required for release |
| --- | --- | --- |
| Pages and management | Own Chinese and English pages cover the original community-visible login, Q&A, datasource, model, assistant, workspace, user, permission, terminology, training, prompt, and settings tasks | Complete the same save, reopen, revoke, and error flows in both the unmodified original browser and AgentSQL's own browser; list every uncovered entry by page |
| API and sessions | Preserve community paths, methods, authentication, request and response shapes, stream events, error codes, and session lifecycle | Compare every route using the pinned original image and candidate in the same environment; runtime OpenAPI inventories locate differences but their counts are not compatibility percentages |
| MCP and embedding | Preserve original MCP clients, assistant calls, API keys, iframe/SDK behavior, navigation, callbacks, and integration modes | Run unchanged original clients and synthetic third-party callers through allowed, revoked, expired, cross-user, and cross-workspace cases; retain request and audit evidence |
| Data and Q&A | Check the community data sources, files, charts, analysis, prediction, exports, and multi-turn context connector by connector | Execute against a real local model and databases; compare original outcomes and failure semantics for the same input, and record versions, roles, and support boundaries |
| Security gateway | Enforce identity, workspace, datasource, table/column, row rule, masking, approval, controlled execution, and durable audit across every entry | Show no unauthorized row escapes on forged identity or schema, old-result reads after revocation, concurrent change, model-generated forbidden SQL, database failures, and audit failures |
| Offline delivery | Authenticate the complete archive with a trusted key and verifier obtained outside the archive before checking inner assets and installing; fail closed on missing database extension or runtime-role privileges | Formal same-commit assets, production-key signatures, disconnected amd64 and arm64 installation, upgrade, failed-start rollback, startup, and downloaded-asset checks; development keys and older assets do not count as formal acceptance |
| Zero-change cutover | Point the existing business client at the candidate unchanged and retain rollback | Record before/after requests, responses, data, permissions, audit, and rollback in an isolated business environment; without this evidence do not claim complete zero-change replacement |

## Security and deployment boundaries

Client-supplied users, workspaces, database settings, rules, and model output are inputs to validate. The Go Q&A service uses current server-side identity and bindings and rechecks authorization before and after model prompts, historical reads, previews, exports, API, MCP, and embedded queries. Actual SQL executes only through the AgentSQL controlled gateway. When authorization, policy, binding, or audit proof is unavailable, no result is returned; an old cached result cannot stand in for current authorization.

The offline archive installs application components by default. The native PostgreSQL binder runs on the database server and needs trusted database-side delivery or explicit preinstallation. For PostgreSQL, the installer must connect to the target database as the actual reader and check binder capability and grants before changing the application installation. The public Demo offers only clearly labeled simulated model interaction and has no real model configured or called; real-model acceptance takes place locally.

## Confirmed compatibility gap

SQLBot Community v1.10.3 accepts `lang` on `POST /api/v1/mcp/mcp_question`: `zh-CN`, `zh-TW`, `en`, `ko-KR`, and `th-TH` temporarily override the user's language for that request, and the Q&A task uses it to choose the model prompt language. Unsupported values retain the user's language. The candidate Go handler now parses the field and passes a request-scoped language to the SQL generation model prompt; the streamed record heading also uses the five original locale resources, while MCP assistant responses use the original fixed Simplified Chinese heading. Focused tests cover the five languages, default, invalid value, and account-language non-persistence. This closes only part of the semantic gap: the other streamed explanations, charts, and analysis output have not been compared with the original language behavior. Formal acceptance must use the unchanged original MCP client to compare every branch and verify concurrent requests cannot contaminate one another or bypass authorization. Until then, MCP question handling cannot count as zero-change compatible.

One model ID in SQLBot Community v1.10.3 can map to multiple workspaces; an administrator can list, replace, append, and remove mappings. An isolated original API probe confirmed that the first model automatically becomes the **global default** even with no workspace mappings; removing every mapping leaves the model and global default flag intact. Original source also includes the global default in each workspace's available model list. An earlier candidate stored a model separately in one workspace and rejected cross-workspace mapping; this branch now has a global catalog and explicit mappings, with full release acceptance still pending. A compatible implementation must preserve stable model IDs, shared configuration and credentials, independent mappings, and an administrator-controlled global default pointer. Mapping changes must check current identity, authorization, audit, and revisions in one transaction; a revoked mapping must not reuse an old model or return an old result. Global model availability grants no database or data permission. The unmodified client must pass all four mapping operations, model edits and key rotation, concurrent revocation, and upgrade migration. The presence of a route or a static route count is not behavioral evidence.

The candidate question path records the selected model's revision and encrypted-body digest and re-reads it before generation, before and after the controlled query, and before return. Until catalog activation it continues to use the workspace-local default. Synthetic negative tests rotate that key during generation or gateway execution and confirm that the old request returns neither SQL nor rows. A new catalog read branch, exercised with a manually constructed active state in tests, resolves the same global default in another workspace and rejects an old lease after catalog cutover, default-pointer change, or credential rotation; rotation during generation also prevents a gateway call. All four mapping HTTP routes, global model list/detail/create/edit/delete, global default switching, the original default probe, and the model connectivity probe use the new catalog in a synthetic active state; the connectivity probe checks the model revision again before returning. AgentSQL's own model page APIs for read, list, create, edit, delete, set default, and connectivity check also use the catalog; a new workspace mapping selector appears only when the catalog is active. A real-browser preview with mocked APIs checked the Chinese and English controls, the mapping PUT request, and hiding the selector while the catalog is inactive; an isolated Go HTTP handler with a synthetic control store subsequently passed a browser mapping round trip; production and original-client acceptance remain incomplete. The assistant page and MCP workspace model lists use explicit mappings, excluding the unmapped global default as the original `by_ws` route does; focused tests cover both lists after mapping revocation. Other tests cover administrator restrictions, mapping counts, credential redaction, preserving or rotating a key on edit, old-request revocation, default deletion denial, and rollback on audit failure. Legacy workspace-local model writes check the activation marker in the same control-store transaction and reject writes after cutover to prevent a fork between model stores. Formal catalog activation, production browser acceptance, remaining MCP/embed entries, complete original-client behavior comparison, and historical-result revocation remain unfinished.

Multi-source MCP assistant selection now resolves its model through the same model path. In a synthetic active catalog it uses the global default and rejects the query if the model key rotates during selection or a subsequent request check. The original chat and MCP question `custom_model` field can select the global default or a model explicitly mapped to the current workspace; revoking a mapping during a question clears SQL and results and prevents the gateway query. Assistant configuration saves also validate current mappings; an embedded assistant automatically uses its configured mapped model at runtime, rejects a client override, and stops answering after mapping revocation. Focused tests cover active catalog selection, unmapped denial, and revocation during execution; advanced assistants and end-to-end comparison with the original client remain incomplete.

A read-only control-store preflight for the future migration scans workspace-local models, detects conflicting configurations or credentials under one model ID, counts prospective mappings, and requires an explicit decision when workspace defaults differ or only non-default models exist. Its report omits model endpoints and keys. An administrator can stage the old models as an encrypted global catalog, explicit mappings, and a default pointer in one control-store transaction with a management audit. An audit failure rolls back every staged object; a changed source snapshot makes a retry fail. Internal mapping transactions can now append, replace, and remove multiple workspaces for one model; they check the administrator, model revision and target workspaces, then update mappings, model revision and audit in one transaction. Focused tests cover cross-workspace mapping, stale revisions, duplicate or missing targets, audit rollback, and cleanup after workspace deletion. An internal activation transaction rechecks the old model snapshot digest and staged catalog, then writes the active marker and audit in the same transaction. Focused tests cover revoking old requests and writes, a wrong digest, a non-admin caller, changed source or target state, and audit rollback. Administrator-only preflight, stage, and activate APIs now complete an HTTP cutover on synthetic data. An isolated browser saved and reloaded mappings in both languages; the local evidence is D:\CodexLS\outputs\agentsql-v450\model-catalog-live-browser-20261101.md. The production catalog is **not active**; formal upgrade and rollback rehearsal, the installer upgrade gate, and original-client comparison remain unfinished.

On 2026-11-01, an exact-head Linux binary ran administrator preflight, stage, and activation against an isolated online backup of the v4.4 PostgreSQL control store. A wrong source digest returned 409; one model and mapping survived the correct activation, and restaging or activating after restart returned 409. Local Qwen then used the original chat API to query real PostgreSQL test tables, returning two rows and a gateway audit ID. The unchanged SQLBot v1.10.3 page logged in and displayed the migrated model. Its Workspace page created a second test workspace, and its model page used the original POST and DELETE mapping routes to add and remove it; a reload showed only the original mapping. A forged workspace mapping returned 404, anonymous mapping read returned 401, and the original mapping remained. The browser console had no errors. Evidence: `D:\CodexLS\outputs\agentsql-v450\model-catalog-v440-copy-upgrade-20261101.md` and `D:\CodexLS\outputs\agentsql-v450\v1.10.3-original-model-mapping-after-cutover-20261101.md`. This accepts one isolated control store and test dataset; formal package upgrade and rollback, remaining original-client workflows, and zero-change business-system cutover remain open.

## Release decision

The latest formal version is v4.3.0; v4.4.0 and v4.5.0 remain draft PRs. Completed slices of original-page, PostgreSQL/MySQL, local-model, and script testing establish only their recorded environments and actions. Complete page and API function coverage, the full security-negative matrix, original MCP and embedded clients, unchanged business-system cutover, the final dual-architecture signed offline archive, and public deployment acceptance remain open. Publish the v4.5.0 Release, website, and Demo together only after these gates have reviewable evidence. Until then, keep the draft status and avoid a "100% compatible" claim.
