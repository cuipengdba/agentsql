# AgentSQL v1.5.0 Specifies in-depth acceptance of domestic databases and default entry switching design

**Language:** [English](v1.5.0-design.md) | [Simplified Chinese](../v1.5.0-design.md)

## User scenarios and scope

For teams that already use domestic databases and need to allow Agents to read controlled data, this version verifies the existing "specified instance base closed loop" as repeatable evidence of permissions, execution, masking, auditing, and fault closure. The real customer pilot is still scheduled separately after the user finds a partner; this version only uses isolated instances and synthetic data.

The acceptance objects are strictly limited to: Dameng DM8 Pack3 `dm8_20241022_x86_rh6_64_single` (COMPATIBLE_MODE=0); KingbaseES KingbaseES V009R001C010B0004 (PG mode); Vastbase G100 V3.0 Build 9 commit 30156 (PG mode). Record the image or installation package summary, server return version, mode, license status, account permissions and test time respectively. The approval of the manufacturer's temporary license does not equal production authorization.

## must be delivered

1. Each database uses independent instances, minimal privilege business accounts, clear table-level permission policies and sensitive column masks. Verification of the same synthetic data allows queries, unauthorized table/column rejection, dangerous SQL rejection, sensitive fields not leaked, persistent auditing and result correlation. Only tested within a subset of existing proven SQL, wider dialect support not deduced from test results.
2. Inject policy revocation, business account permission revocation and database disconnection respectively, and review availability, masking and auditing after recovery; sensitive results must not be delivered in case of failure. Database-by-database query timeout/cancellation and independent audit storage failures are listed as items for continued retesting; "unverified" is not clearly recorded before stable injection into the same manufacturer's environment. Shared Pipeline test or simulation results shall not be used to replace real database evidence, nor shall it be claimed that the fault scenario has received full production support.
3. Complete at least one real allow and deny tool call in MCP Inspector and Dify for each database, record the client version, entry, request ID, audit ID and output masking; retain the capability boundaries that the client cannot cover. There is no Claude account, and Claude Desktop is not listed as the actual test version of this version.

In both cases formal packages are used to verify that the configuration is compatible with persistent data.

## Database support statement

The acceptance report uses the expression "the specified version, the specified mode, and the specified read-only subset passed". Dameng, KingbaseES and Vastbase will not be automatically upgraded to full production support for all scenarios due to this version. Formal production license, TLS, vendor HA, long-term load, more SQL dialects, cross-version compatibility and real customer environment all require additional evidence; unfinished items are clearly stated in the support matrix and official website.

## Failure closure checklist

| border | Allow delivery conditions | behavior on failure |
| --- | --- | --- |
| Identity and tenants | Agent Key, tenant, data source and authorization are consistent | Rejected and no business inquiry |
| Table/column permissions | SQL objects and column usage are within proven subsets and valid strategies | Reject, not fall back to easing strategy |
| Business read-only execution | Minimum permission account, number of rows and return within time limit | Reject/Abort, not deliver some sensitive results |
| mask | Sensitive columns are converted according to policy before output | Reject, do not output the original text |
| Audit and final fence | Persistent auditing and control plane snapshots work | Refusal of delivery; documented verifiable failure |
| Disconnect and restore | Actual database and audit backend restored and chain verification available | Continue to reject before recovery and do not automatically rewrite historical audits. |

## Release threshold

v1.5.0 cannot be declared complete for the basic authorization, controlled query, masking, rejection, persistent auditing, shutdown and recovery of injected faults, failure of any key link of the two clients, or failure of the official website/Demo candidate to be retested on the public network of the three real libraries. Unvalidated timeouts/cancellations with independently audited storage failures shall not make their way into the manifest or full production support statement. v1.1.0–v1.4.0, which are officially released in stages, retain the exact version that can be directly downloaded; the default entry will only be updated after the completion of this version.
