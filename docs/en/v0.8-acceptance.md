## Functional and safety boundaries

| Project | Current implementation and checks | Still needs to be completed before publishing |
| --- | --- | --- |
| Mission authorization request | The applicant submits a single precise SELECT, Agent, data source, maximum validity period of 24 hours and idempotent key with `query.execute`; the tenant comes from the login identity. SQL is encrypted into the database using paired keys, and only SHA-256 is provided for list and management auditing. | The target environment still requires complete backup and recovery pairing `AGENTSQL_SECRET`. |
| Approval and collection | Another user with `strategy.manage` and `query.execute` in the same tenant can view the exact SQL, approve or reject it after verification; the original applicant receives the Key in one go. Issuance and management audits are committed in a metadata transaction; the old direct issuance API returns 410. | Isolation injection has been completed for independent audit library failure and recovery; production deployment must monitor the outbox backlog. |
| Decision audit | Authorization ID is associated with management actions and execution/denial of entering the SQL pipeline; the audit page can be queried by authorization ID. Management audit does not include Key and SQL original text. | Standalone audit library relay failure retries are done in isolated topologies. |
| Access troubleshooting | The wizard adds authentication, permissions, protocols, databases and audit fault code location. | The console dual account process has been reviewed; the real new user operation experience has not yet been obtained. |
