# AgentSQL v2.9.0 Design: Strategy Review and External Audit Witness

**Language:** [English](v2.9.0-design.md) | [Simplified Chinese](../v2.9.0-design.md)

Status: Under development; this document describes the implementation boundaries of this version, and release evidence will be recorded separately.

## User tasks

An administrator would export the policy from the current tenant, review the impact of the change once, have it approved by another administrator, and then apply it all at once. Operations and maintenance personnel should be able to detect direct policy changes that bypass review, and save the integrity certificate exported by the audit outside the database.

## Strategy package contract

- `/api/v1/policy-bundles/current` Exports the current tenant policy snapshot and specification SHA-256 digest. The package includes policy IDs, agent and data source IDs, objects, actions, revision numbers, and existing B2 bindings, column permissions, and staging metadata; database passwords, user credentials, and business rows are not included.
- `plan` Performs an optimistic concurrency check on the current summary of the same tenant and returns create, update, and delete differences. Grant authority to new allow, changed allow, and deleted deny conservative tags. Accepts up to 128 strategies and 32 exact table playback cases. The playback only shows the table level `deny`, `candidate` or `unknown`; `candidate` does not mean that SQL can be executed. It does not connect to the business database.
- `proposals` Saves the specification target package, source summary, and originator. The initiator cannot approve; the approver must have both policy management and audit viewing rights. The app accepts only approved proposals and original approvers, rechecks source summaries, target summaries, tenant references and revisions, and writes all policies, approval baselines, and management audit outboxes in the same metadata transaction. If any step fails, it will roll back.
- This version of **only allows modification of the table-level allow/deny policy** without B2 relationship binding, column permissions, column staging, row filtering, and legacy exception flags. There are already other policies present in the export package, but they must be left intact. Maximum of 128 items per package and 32 changes per proposal; beyond scope will be rejected. Restoring the old strategy also requires resubmission and approval by another person. The original single policy management API can still be used.
- `status` Compares the current specification summary with the most recently approved summary, returning `uninitialized`, `approved`, or `drifted`. Drift caused by direct CRUD will be displayed on the console; this version does not automatically block business traffic due to drift. True execution is still determined by existing per-agent/tenant authorization, database least privileges, masking, and persistent audit chains.

Call chain: `管理员身份/租户/RBAC → 规范快照及摘要 → 离线差异/保守回放 → 发起提案 → 异人审批 → 应用时重新验证 → 策略/基线/outbox 原子提交 → 网关逐次读取当前策略`.

## Audit external witness

`agentsqlctl audit checkpoint-create` first verifies the list of compliant ZIPs and each file summary, and then uses the Ed25519 private key saved externally by the operation and maintenance personnel to sign the ZIP byte summary, archiving time, signing time, declared audit chain ID/header number/header summary and the previous witness summary. `checkpoint-verify` needs to be kept independently of the public key, expected last witness digest and acceptable time limit; it rechecks the ZIP, signature, byte digest and time window. Keys and witness history are kept outside the AgentSQL metadata and audit repository by the operator.

The signature proves that the key holder recognizes this ZIP and the filled-in chain header statement; the tool **cannot infer the complete audit chain header** from the filter report, nor does it provide WORM, trusted timestamps or automatic replay protection. The chain head must first be physically checked with `agentsqlctl chain verify`, and the last witness summary must be provided from an independent trusted record. Verification and external retention of the complete audit chain are the responsibility of the deployer.

## Compatibility and acceptance

SQLite merge metadata schema 22→23; SQLite/PostgreSQL sub-database metadata 21→22; PostgreSQL merge metadata 22→23; independent audit schema 6 remains unchanged. Old instances are restored using an explicit upgrade process and paired backups. SQLite/PostgreSQL proposals with transaction rollback, cross-tenant invisibility, expired proposals, self-audit rejections, direct CRUD drift, signature/ZIP/preamble digest/timeline tampering, console builds, official package upgrade recovery, true MCP allow/deny, and fully signed delivery, public website, and demo acceptance must be covered before release.

The existing support level of the database adapter will not be improved with this version; the authorization and audit boundaries of real SQL are based on the actual measured evidence of the corresponding version of each database.
