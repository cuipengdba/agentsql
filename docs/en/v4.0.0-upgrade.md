# AgentSQL v4.0.0 upgrade and rollback

**Language:** [Simplified Chinese](../v4.0.0-upgrade.md) | [English](v4.0.0-upgrade.md)

This release adds no schema migration. Targets are SQLite 27 and separated PostgreSQL metadata 25/audit 7. Older baselines may require intermediate migrations; do not simply replace binaries and depend on runtime auto-repair.

## Upgrade steps

1. Check the database product/version/topology and current capability evidence; rehearse with sanitized configuration in isolation. Upgrades do not automatically expand database support.
2. Stop writes on all gateway instances and resolve pending approvals and B5 transactions. Preserve configuration, the original SECRET, metadata, audit, B5 WAL/recovery data, certificates and instance IDs. Use consistent SQLite backups and paired PostgreSQL backups in one stopped-write window.
3. Verify the complete release directory with an independently trusted key and retain the original binaries and backup hashes. Run `agentsqlctl doctor` and `migrate --check`, distinguishing pending, blocked and ahead states.
4. Run `agentsqlctl migrate --config <config>` using a migration owner, recheck, then start using the least-privilege runtime account. Do not retain migration permissions for normal production operation.
5. Check identities, permissions, masking rules, encrypted configuration fields, audit history and new allowed/denied requests; verify readiness, notifications and external clients. Do not restore full traffic before acceptance.

## Rollback rules

Stop writes, restore SECRET, configuration, metadata, audit and applicable transaction recovery data together to the pre-upgrade point, then start the matching old binaries. Restore discards data written after the backup, so the deployment owner must establish the rollback window and acceptable data loss beforehand. Do not run old binaries against newer schemas or mix stores and keys from different points in time.

```powershell
pwsh ./scripts/v4.0-upgrade-matrix.ps1 -FromVersion v3.0.2 -PackageDirectory '<official-package-directory>' -CandidateDirectory '<v4-binary-directory>' -FixtureRoot '<new-isolated-fixture-root>'
```

The rehearsal script creates only fixed-prefix isolated containers and new directories with synthetic records; it does not accept customer production DSNs. Input packages are checked against their downloaded SHA-256 sidecars; source authenticity is established separately by release signature verification. Checks cover old startup, migration, new startup, preserved records, backup restore, old-binary rollback startup and SECRET-file consistency. See [acceptance](v4.0.0-acceptance.md) for actual results.
