# AgentSQL v3.1.0 upgrade and recovery

**Language:** [Simplified Chinese](../v3.1.0-upgrade.md) | [English](v3.1.0-upgrade.md)

## Versions and migrations

| Layout | v3.0.2 | v3.1.0 |
| --- | --- | --- |
| Combined SQLite / PostgreSQL stream | 23 | 24 |
| Separate metadata | 22 | 23 |
| Separate audit | 6 | 6 |

The new `sqlbot_bindings` table stores tenant, external workspace/user, internal user and read-only Agent, datasource, credential digest and binding revision. Existing API Keys, human delegation, database policies and approvals retain their original contracts.

## Procedure

1. Stop writes and back up metadata, audit, configuration and keys together. Retain the v3.0.2 binary. Use the SQLite backup API or copy complete database state only after all processes stop.
2. On an isolated copy, run `agentsqlctl migrate --check --config /path/config.yaml` with v3.1.0 and verify pending changes.
3. Run `agentsqlctl migrate --config /path/config.yaml` as the migration owner, then repeat the check and run `doctor`. Do not grant extra DDL privileges to the runtime account.
4. Start the service and verify existing Agent allow/deny, masking, approval and audit flows before configuring SQLBot managed v2 mappings.
5. Install the adapter into a fresh SQLBot v1.10.2 base image. Check the installation manifest and diagnostics before verifying current-user identity, real queries and read-only approval.
6. To roll back, stop the new version and restore the matched pre-upgrade data, configuration, keys and old binary. Recheck health and business flows. Never open the new schema directly with the old binary.

## Legacy configuration and failures

SQLBot v1 configuration retains its workspace-level mapping boundary. Migration to v2 requires an individual mapping and connector credential for each person. Plaintext credentials appear only on creation/rotation and cannot be retrieved from lists or exports. Disable a binding to stop that integration; revoke the Agent Key to stop all access by the Agent.

Binding changes invalidate old tokens and their sessions. Clients resolve and initialize again; queries are not automatically retried. After an audit failure, verify restored durable audit with synthetic data before resuming business calls. Actual rehearsal results belong in the [acceptance record](v3.1.0-acceptance.md).
