## Per-page completion rule

For each row, record the visible entry point; create/read/update/delete; pagination and search; errors and permissions; persistence; restart/rollback; and differences from original client responses. Static pages, route counts and simulated data do not prove completion. Test real model behavior locally. The public Demo labels model interaction “simulation only; no real model connected.” Before release, confirm the Chinese/English website, current GitHub descriptions and docs, Web, Demo, packages and Release all identify the same actual version.

### Identity contract for the original assistant SDK

The pinned SDK packs `assistant_id`, time, page origin, browser flags, User-Agent and timezone into JSON and encrypts it with the public RSA key from `/api/v1/system/config/key` before sending `SQLBOT-EMBEDDED-SIGN`. Public-key encryption lets the server read the payload; anyone with the public key can create this header, and a non-browser client can assert an arbitrary `Origin`. Decryption, a ten-second time window, domain matching and browser attributes therefore do not establish a business user's identity and cannot alone authorize a query token.

There are two server-authorized integration modes. Private data for an existing business user requires a trusted host service to issue a short-lived grant using an application secret or a verified user session. The grant binds the application, workspace, user, datasources and token revision; browser `virtual` and `userFlag` values remain display parameters. Public guest mode, which can retain the original browser SDK unchanged, requires an administrator to explicitly publish each datasource and bind a dedicated non-admin guest identity to current gateway permissions. Its data must be treated as public to anyone who can make a network request; it cannot inherit an administrator's or ordinary user's private bindings. The management API can now set `public_guest_user` for a basic assistant only when an enabled local non-admin user in the same workspace has a separate binding for every listed datasource; creation generates a server-side secret. The internal verifier now accepts an `Assistant` token signed with that secret only when it has a visitor scope and expires within one hour, while data reads recheck the application list, visitor identity, current user and datasource binding. An internal issuer now generates a fresh random visitor scope for each call and binds the application and guest account revisions in the token; changing the application invalidates old tokens. Restricted `info` now issues a token only when the app explicitly names a public guest and the origin and original RSA header pass validation; unconfigured apps receive no token. This has isolated server-side tests and a successful public-guest `info` handshake in the unmodified original SDK browser; full embedding remains unaccepted. Without a safe authorization configuration, `info` must refuse to issue a token.

The server generates an unguessable identity for each guest session. History, charts and exports are visible only to that identity. Existing page-embed tokens now support an optional 128-bit visitor scope, checked when reading and listing chats and recent questions: two scopes under the same app and account cannot read one another, while older unscoped tokens retain their existing boundary. Server-side issuance of public guest identities and tokens now exists behind restricted `info`; safe session continuity after refresh and real embedding remain unverified.
