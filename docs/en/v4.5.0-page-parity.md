# v4.5.0 page and positioning acceptance matrix

[Chinese](../v4.5.0-page-parity.md) | [English](v4.5.0-page-parity.md)

Status: acceptance scope, not yet complete. The reference is an unmodified local image and browser of [SQLBot Community v1.10.2](https://github.com/dataease/SQLBot/releases/tag/v1.10.2). These are entry points and workflows actually observed on 2026-10-26; each still needs operation, response, permission and error comparison. AgentSQL designs and implements its own interface and does not copy the other product's page source, icons or branding.

## Two product modes

| Mode | AgentSQL responsibility | Evidence required for public claims |
| --- | --- | --- |
| SQLBot security gateway | Keep the existing SQLBot Q&A interface while routing business database access through AgentSQL identity mapping, table/column and row rules, read-only execution, masking and durable audit | Test the original SQLBot and real database in isolation for allow, deny, revocation, masking, fail-closed behavior and audit; state tested versions and databases |
| Standalone Q&A product | AgentSQL itself provides Q&A, datasource, chart, dashboard, assistant, embedded and administration pages, plus compatible API/MCP | With SQLBot stopped, run the same original client and business program at unchanged addresses, paths, identifiers, SDKs and callbacks; no missing page or empty endpoint |

Use one accurate description on the website, GitHub and AgentSQL Web: AgentSQL is an independently implemented database security and Q&A product that can secure SQLBot as a gateway and can also provide Q&A on its own. Claim each mode only after its respective acceptance passes. Zero-change replacement of the user's existing business system additionally needs before/after evidence in their actual isolated environment. Pages, code and assets use AgentSQL's own brand, and current-distribution licensing text presents Apache-2.0 only.

## Per-page completion rule

For each row, record the visible entry point; create/read/update/delete; pagination and search; errors and permissions; persistence; restart/rollback; and differences from original client responses. Static pages, route counts and simulated data do not prove completion. Test real model behavior locally. The public Demo labels model interaction “simulation only; no real model connected.” Before release, confirm the Chinese/English website, current GitHub descriptions and docs, Web, Demo, packages and Release all identify the same actual version.

## Current verification record

On 2026-10-27, outdated promotional copy and broken links were removed from the historical GitHub v0.4.0 and v0.5.0 Release descriptions; an API readback confirmed their removal. The fact that v0.4.0 was published under GNU AGPLv3 remains accurate, and historical tags and assets were not changed. The current branch passes the website, README and documentation license-copy scan. The public website and formal release are still v4.3.0 and must be updated together only after complete v4.5.0 acceptance.

On the same day, the unchanged SQLBot Community v1.10.2 frontend was connected to the AgentSQL Go candidate locally. Its administrator login, Q&A parameter save and reload, and user creation and reload on the original user-management page completed. For the original login-parameter and initial-password requests, AgentSQL hides the shared-initial-password hint and returns no fixed password to the browser. The isolated test used a configured initial-user password; the original proprietary frontend scripts were used only for local comparison and were not added to AgentSQL product assets. This evidence does not cover the other pages, a real model, existing business-application integration or unchanged replacement.

The original model page opens its default-model card and edit form using the pinned baseline's Generic OpenAI supplier ID 15 and LLM model-type ID 0. It can save the current workspace's existing default model and reload the changed name. The original browser encrypts its endpoint and optional key with the installation login key; Go decrypts them only for the current model and commits the edit with audit. The post-save request probes only the saved model and never executes generated SQL. A local Qwen probe returned `Model reachable` within 60 seconds. In a separate isolated empty workspace, the unchanged original Add Model form created an HTTPS configuration: POST returned 200 and its default-model card survived reload. A non-loopback HTTP address was denied by the security rule; the test HTTPS address was intentionally unreachable during the later connectivity probe. A global model catalog, a second model, delete, default switching, original-client key rotation and the full real-model Q&A matrix remain unaccepted. The original API Key dialog completed create, disable and delete in the isolated environment, but its full-account-permission wording exceeds the actual bounded AgentSQL key scope; complete integration compatibility remains unaccepted.

The same candidate also served one local Qwen question from the unchanged original Q&A page over a synthetic datasource: “list regions and amounts, at most two rows.” The controlled response returned `east/10`, `west/20` and audit ID 735. After reload, the original history-data route fetched the same rows again under new gateway audit ID 749. This proves one workspace, datasource, question and administrator path only; it does not establish the full Q&A, revocation, failure-recovery or zero-change business replacement matrix.

The original user-management page completed disable, re-enable and “restore initial password” for a local user in isolation. Disable and reset invalidated old tokens with 401 responses. A temporary password stopped working after the original reset, while the deployer-configured initial-user password logged in again. The original system-variable page created, edited, reloaded and deleted a text variable. Its edit and delete requests use a string ID and a string-ID array respectively; the Go adapter now strictly parses canonical decimal strings or JSON integers and rejects noncanonical or out-of-range values. Original delete returned 200 and reload showed an empty list. Variables are not yet evaluated by row permissions, so this does not prove effective variable rules.

The original workspace Add Member dialog requests candidate page `1/1000000`; the adapter accepts that exact request only for candidates and rejects a response when the candidate count exceeds 10,000. The isolated original page added a test user as a regular member, promoted the user to administrator, removed the user, and showed zero members for that workspace after reload. Normal member pages and other oversized requests remain limited. This evidence does not cover original bulk actions or all membership permission rules.

The original page also renamed a workspace and read back the new name after reload; it created and deleted a separate empty workspace. Deletion of a workspace containing a test model was rejected and left its resources intact; the service now returns an explicit resources-or-members conflict. Cascading deletion of linked resources as described by the original dialog is not implemented, so deleting an empty workspace does not establish full deletion compatibility.

Although the original default-model card exposes Delete, the page first shows its default-model restriction and sends no request. A direct backend request returns 409 and retains the model and its encrypted key; unauthorized callers and other model IDs are rejected. The original Authorized Workspaces dialog previously showed zero and now correctly displays one current workspace. Its Add action sends `POST` and removal sends `DELETE`: re-adding the current workspace is a no-op, while cross-workspace sharing or removal of the only mapping is explicitly rejected. Service tests cover these paths. With no second model yet, nondefault deletion, default switching and complete model mapping remain unaccepted.

The unchanged original Q&A results page used the real local Qwen model to analyze two synthetic rows, and its event stream and page displayed the generated text. Initially that text disappeared after reload because the original page fetched conversation metadata only. The candidate now returns historical analysis or prediction text only after a newly authorized and audited query matches the saved result digest. After rebuilding the candidate, the unchanged browser reloaded and reopened the conversation, displaying the historical analysis. Focused service tests also hide old text when results change and close the entire historical read when the datasource binding is revoked. Other analysis prompts, the complete prediction flow and permission combinations remain unaccepted.

The same two-row synthetic result triggered Prediction in the unchanged original page. Local Qwen returned prose describing its input range, uncertainty and inability to extrapolate reliably. Because the sample is not an ordered numeric or time series with at least three rows, no numeric forecast points were produced. The text remained visible after the browser reloaded and reopened the conversation. This verifies one bounded prose path, not the entire original prediction page or numeric charts. AgentSQL Web overview and Q&A gateway settings now describe standalone Q&A and SQLBot gateway deployment separately; the public Demo also states that it shows simulated pages and synthetic data without calling a real model.
