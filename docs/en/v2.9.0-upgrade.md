# v2.8.0 → v2.9.0 Upgrade and recovery

**Language:** [English](v2.9.0-upgrade.md) | [Simplified Chinese](../v2.9.0-upgrade.md)

Status: Candidate description; the corresponding SHA and recovery record will be added after the official package is accepted.

1. Use the v2.8.0 official package to execute `agentsqlctl migrate --check` and confirm that the merged metadata is 22 or the branch metadata is 21, the independent audit is 6, and there is no incomplete migration. Stop login and MCP traffic for all gateways.
2. Make a complete set of backups at the same point in time for metadata, audit (if branched), `AGENTSQL_SECRET`, audit chain key, and deployment configuration. Don't just back up metadata; the recovery points of the audit outbox and the audit chain must be consistent. Keep the v2.8.0 official package for fallback.
3. Use the v2.9.0 target package to execute read-only `agentsqlctl migrate --check`, and check that only the expected new migrations are: merged library 22→23; sub-library metadata 21→22; independent audit remains 6. Then execute `agentsqlctl migrate` explicitly, run `--check` again, and ask for all `current=latest`. If there are multiple gateways, stop the old node and update all nodes synchronously to avoid mixed versions taking over policy writes.
4. Check the original Agent, data source, policy, approval, and audit chain on the isolated recovery copy and the official candidate respectively; create a new table policy proposal without B2 binding, approve and apply it by another person, verify the `approved` status, real MCP allow/deny, and manage audit outbox delivery. Then use a single policy API to create a drift, and only `drifted` should be displayed; business execution still runs according to the existing authorization and audit contract.
5. When rolling back, stop all v2.9.0 gateways, restore the v2.8.0 official package and the metadata, audit, keys and configuration at the same point in time before the upgrade, and then run v2.8.0 `migrate --check`, audit chain verification, login and real MCP smoke test. You cannot just replace the old binary while preserving the new schema or new policy changes.

The external audit witness file and Ed25519 key should not exist within these database backups. After the witness has been issued to the outside world, restoring the old database cannot revoke the external evidence; the recovery event and the new link head should be clearly recorded in the next external retention material. This version of the witness only certifies archived bytes and signed statements, not immutable storage or trusted time services.
