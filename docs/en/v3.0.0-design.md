# AgentSQL v3.0.0 Design: Capability Statement and Reviewable Delivery

**Language:** [English](v3.0.0-design.md) | [Simplified Chinese](../v3.0.0-design.md)

Status: Under design and development. The baseline is released v2.9.0; no major version number implies that all 30 registered databases have the same execution capabilities.

## User issues and trade-offs

The console currently labels all relational data sources as `relational` and all other data sources as `nosql-connect`. This does not tell an administrator or MCP Agent which types only have connection previews and which have controlled read tools with specified instances, nor does it show that real queries are still subject to versions, switches, accounts, object policies, and audit availability. Although operation and maintenance personnel can run `check-config` and `migrate --check` respectively, they lack a structured, read-only and automatically determined pre-delivery inspection entry.

Bytebase's [ official MCP page ](https://www.bytebase.com/database-mcp-server/) and [ access document ](https://docs.bytebase.com/integrations/mcp) have integrated identity, permissions, masking, auditing and client access as a unified product experience. This version of AgentSQL clearly expresses its proven capabilities and provides reviewable pre-checks and client smoke tests for operation and maintenance; it does not inherit the marketing claims of competing websites about the number of databases or the scope of cross-engine management.

## Delivery scope

1. Establish a capability directory of 30 data sources maintained by the server. The four tiers are `controlled_sql` (a subset of existing controlled SQL for PostgreSQL/MySQL), `bounded_sql` (bounded SQL read-only for a specified instance), `controlled_read_tool` (standalone controlled read tools for MongoDB, Redis, Valkey, ClickHouse, Milvus), and `connection_preview` (connection or management preview for the remaining types). Each item has Agent tool entry, acceptance scope and evidence documentation. The statement only describes possible entry paths, and is by no means an authorization commitment; each call is still determined by the existing identity, policy, execution, masking, and audit links.
2. The Management API's `/api/v1/datasource-types` uses the same capability directory as the console Data Sources page. MCP `list_datasources` only attaches the same statement to the data sources for which the current Agent is authorized and does not disclose unauthorized data sources, connection credentials or internal addresses. Retain the original `capability` field as a legacy client compatibility field and make it clear that its semantics are not sufficient to determine executability.
3. Added `agentsqlctl doctor --config ... --format json|text`. It only reads configuration and metadata, audits library migration history, and does not do DDL, create SQLite libraries, or modify runtime identities. Reports the current/target schema, `ready`, `pending`, `blocked` status and next action for each storage role; returns exit code 2 for pending migration, 1 for damage, future schema, or unreachable. The output does not contain DSNs, passwords, or keys.
4. MCP client acceptance scripts and steps providing fixed inputs: tool discovery, synthetic data allow and deny, masking and audit IDs. API Key is only read from the environment, the script does not print the original line or key, and supports the 2 QPS limit of the Demo. MCP Inspector and Dify continue to verify independently with real clients.
5. Perform a package upgrade and recovery of SQLite and PostgreSQL from the v2.9.0 official package to the v3.0.0 candidate package; if there is no schema migration for this version, it should be proven that the version remains unchanged. Complete signature assets, two-architecture GHCR, official website, Live Demo and public network re-inspection.
6. The release tool chain is uniformly upgraded to Go 1.26.10; CI, Rocky Linux official packages and GHCR builds must use the repaired tool chain and pass govulncheck.

## Security and Compatibility Boundaries

- Capability catalogs cannot bypass authorization, nor are they automatically promoted to "Full Production Support" based on connectivity. The existing MCP tool name and management API fields are retained; new fields are only expanded.
- The API and MCP do not generate optimistic tool lists for unknown registration types or missing capability declarations; directory coverage testing prevents this state from entering release.
- `doctor` does not call the configuration load path that persists the instance ID; SQLite passes the read-only connection check, and PostgreSQL only performs read-only queries. Diagnose errors using fixed codes and next step prompts, and do not echo third-party driver errors and credentials.
- Client smoke testing can only use explicitly labeled synthetic data and does not send real user data. Whether real results are deliverable is still determined by persistent audit success and existing fault closure logic.
- This version does not add database drivers, does not release writing, does not automatically migrate or roll back production data, and does not declare vendor certification, HA, or complete production support for all databases.

## Release blocking use case

The directory covers all 30 types, four levels are mutually exclusive, and the evidence is readable; the management API and MCP declare the same type consistently, and unauthorized data sources do not appear; tool calls are still rejected after permissions are revoked. `doctor` remains read-only and gives the correct exit code for missing SQLite, pending migration, historical gaps, future schema, unreachable independent audit library and password-containing DSN. Public network client permission, R010 rejection, masking and persistent audit pass; v2.9.0 official package upgrade and same-point recovery, GitHub CI, official assets, GHCR, official website and Live Demo must have real evidence.
