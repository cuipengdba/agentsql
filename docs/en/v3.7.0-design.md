# AgentSQL v3.7.0 Controlled MongoDB and Key-Value Reads

**Language:** [English](v3.7.0-design.md) | [Simplified Chinese](../v3.7.0-design.md)

Status: implementation design. Actual versions, topologies, and final acceptance determine the support claim.

## User problem and scope

The existing `find_documents` path verifies exact collections, top-level fields, string equality filters, and at most 100 rows on a specified MongoDB 7.0 standalone instance. Row count, response size, and time already have limits, but replica-set failover and index-constrained scan cost remain unverified. The existing `read_key` path reads string keys only on specified Redis 8.2.9 and Valkey 8.1.10 TLS/ACL standalone instances. Hash fields and Sentinel are outside the verified scope.

This release aims to let administrators grant minimal access to explicit collections and Hash fields while retaining authorization, masking, and durable audit during failures in specified high-availability topologies. Arbitrary MongoDB commands, aggregation, and writes remain closed, as do arbitrary Redis/Valkey commands, bulk enumeration, and writes. The public Demo continues to show only its deployed synthetic PostgreSQL/MySQL scenarios.

## Product flow and configuration

1. A MongoDB administrator registers an explicit replica-set name, seed nodes, test CA, and member certificate identities. Only discovered members of that replica set are accepted; arbitrary connection URIs, SRV discovery, and disabled TLS verification are unavailable. The administrator approves an equality-filter index for each controlled collection. Requests must match an approved indexed field combination and remain within row, response-byte, batch, and execution-time limits.
2. A Redis/Valkey administrator registers an explicit Sentinel master name and address list, with separate TLS/ACL identities for Sentinel and data nodes. A discovered master must remain within the allowed network scope and pass certificate verification; Sentinel-provided addresses are not trusted by default. Invalid discovery, unsettled failover, certificate mismatch, or an unsupported server version fails closed.
3. An Agent reads Hash values through a separate controlled tool with one exact key and a small explicit field list. Authorization binds the Agent, tenant, datasource, logical database, exact key, and each field. A prefix key grant does not implicitly grant Hash fields. A fixed read-only `EVAL_RO` script checks the type, field presence, and total bytes on the server before returning data. This avoids an unbounded response caused by a write between separate `HSTRLEN` and `HMGET` requests. `HGETALL`, `HKEYS`, `SCAN`, and dynamic scripts remain closed.
4. Field-source masking and final durable audit precede MCP delivery. Preflight, denial, execution errors, and audit failures retain traceable outcomes; a failed terminal audit prevents value delivery.

Replica-set metadata lives in datasource `read_control_json` without credentials. Before a read, AgentSQL runs `executionStats` with the approved index hint. The actual `IXSCAN` key set must match the approval, and both keys and documents examined must be at most `min(requested rows × 10, 1000)`. The subsequent `find` uses the same hint and rejects a removed or replaced index. The three-member allowlist runs before network dialing, and each certificate is checked against its own hostname.

Sentinel JSON contains only the master name, three Sentinel addresses, approved master addresses, and a separate ACL username. Operations supplies its password through a gateway environment variable whose name is derived from the SHA-256 digest of tenant ID and datasource ID and shown read-only in datasource details. Administrators cannot select an arbitrary environment variable or put a password in JSON. Discovery addresses pass the exact allowlist before TLS and ACL authentication. The test topology uses a separate peer account between Sentinel nodes; AgentSQL uses a restricted Sentinel discovery account and a read-only data account.

## Security and failure contract

| Path | Required behavior | Failure behavior |
| --- | --- | --- |
| MongoDB read | Current Agent identity, tenant, exact collection/field grants, index constraint, bounded time/batch/rows/bytes, and read-only database account. | Reject missing or changed indexes, uncertain plans, excessive scans, untrusted members, and revoked grants; never fall back to an unbounded scan. |
| Hash field | Exact key and field grants, bounded field names/count and per-value/total bytes, with only the fixed read-only script and minimum ACL. | Return no value on changed key type, unauthorized field, malformed response, or master discovery failure. |
| High availability | MongoDB connects only to the trusted replica set; Sentinel discovers only a trusted master. Request timeout and retries are bounded. | Old connections and caches cannot bypass current identity, policy, certificate, or ACL checks; credentials never go to an unknown address. |
| Audit and masking | Durable preflight and terminal audit, field-source masking, and no raw secrets in logs. | Audit or masking dependency failure closes the path; a successful database read alone does not authorize delivery to the Agent. |

## Acceptance criteria

- On a specified MongoDB 7.0 three-member replica set, use real TLS and a least-privilege account to verify indexed reads, primary failover, wrong certificates, unauthorized collections/fields, index removal, and scan limits. Record member versions, image digests, and observed plans. Sharded clusters remain outside this release.
- On specified Redis 8.2.9 and Valkey 8.1.10 Sentinel test topologies, use real TLS/ACL to verify allowed/denied Hash fields, primary failover, substituted discovery addresses, invalid certificates, revoked ACLs, oversized values, and wrong key types. Cluster remains outside this release.
- Complete real allow and deny calls from the two selected MCP clients, plus independent audit-database and business-database fault/recovery checks for masked results and durable audit. Record any vendor or topology boundary not tested.
- Rehearse upgrade and restore from the prior official package and paired backups, then pass Go/Web/bilingual-doc CI, signed assets, dual-architecture GHCR, GitHub Release, website, and public Demo gates.

This release does not claim MongoDB sharding, Redis/Valkey Cluster, automatic coverage of other versions, a long-term production SLA, or vendor certification.
