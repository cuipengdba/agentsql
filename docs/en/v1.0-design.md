# AgentSQL v1.0.0 Design and Acceptance Scope

**Language:** [English](v1.0-design.md) | [Simplified Chinese](../v1.0-design.md)

## target

v1.0.0 is based on the existing evidence scope of PostgreSQL/MySQL, tightening SQL column authorization and MCP personnel identity boundaries, and enabling operation and maintenance personnel to determine why it is rejected and how to recover. The version number indicates that the product interface and delivery process have entered a stable stage, and does not mean that all registered databases have received full production support.

The real customer pilot will be scheduled separately after obtaining customers willing to participate and test authorization. DM8, KingbaseES V9, and Vastbase G100 only use the bounded conclusions of their respective specified versions and synthetic data; the support level will not be upgraded.

## security contract

| scene | expected behavior |
| --- | --- |
| PostgreSQL has column strategy, B2 binder available | Hand over SELECT projections, predicates, JOIN/self-join references, etc. to database-supported column binding paths; still must go through table policies, rules, controlled execution, masking, and auditing. |
| There is a column strategy, but B2 is not available or the target dialect lacks an equivalence proof | Fail to close and write audit before execution; cannot fall back to the old path that only verifies the table name. MySQL/Vastbase column-level strategies continue to be explicitly unsupported. |
| HTTP MCP dual identity mode | Agent Key determines the machine identity and tenant; another user delegation token valid within 30 minutes and bound to the specified Agent proves the person's identity. Each request checks the original console session, user status, and `query.execute` permissions. Cross-tenant, wrong Agent, wrong task authorization issuer or invalid credentials are rejected. |
| Console login token | For console use only; cannot serve directly as an MCP user delegation token. Delegation tokens also cannot access the console API. The issuing action is written to manage the audit, and the token is not delivered in case of failure. |
| Stateful MCP session | The transfer session binds the Agent and the user at the same time; changing either identity must be reinitialized. Stateless ingress is verified on a request-by-request basis. |
| B5/approval execution | When the existing B5 plan and `execute_approved` do not carry a complete dual-identity contract, they are closed in dual-identity mode; the normal mode maintains the original behavior. |

Dual identity is an optional switch `mcp.delegation.require_human_token`, which is turned off by default to maintain compatibility with existing MCP clients. When enabled, the console is required to be open; all HTTP MCP requests carry two independent credentials, stdio does not use this HTTP contract. Existing ordinary agents can still call basic tools according to the original policy; the task key is additionally subject to the original SQL, budget and issuer.

## Console and documentation

The "Task Authorization" page of the console provides the issuance of personnel tokens by Agent and one-time display in dual-identity mode. The permissions page clearly lists the actual operating boundaries of the policy to avoid mistaking the "table-level candidate passed" of the offline pre-check for execution permission. The access guide provides examples of double request headers, credential invalidation, and client compatibility instructions; the release notes list upgrade impacts and recovery methods.

## Post block

1. The column policy negative set covers JOIN, self-join, wildcard projection, predicate reference and B2 is not available; business SQL is not executed when rejected, and the audit is recorded.
2. Delegation tokens cover issuance, incorrect Agent/tenant, expiration, logout, user disabling, permission revocation, task key issuer mismatch and stateful session identity replacement; do not leak tokens to audits or logs.
3. Go, Web, and official website automatic tests passed; MCP Inspector’s two HTTP entrances and Dify compatible paths have real call evidence.
4. The upgrade, recovery, and audit failure closure of the SQLite merge library and PostgreSQL metadata/audit sub-library passed; DM8, KingbaseES, and Vastbase only record retests that have been completed.
5. Submit CI, signature assets, dual-architecture GHCR, GitHub Release, official website and Live Demo all passed the public network smoke test, and record the evidence according to [ each version delivery process ](RELEASE_ROUTINE.md).
