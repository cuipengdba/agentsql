# v4.2.0: Multi-turn data Q&A and business semantics

**Language:** [Simplified Chinese](../v4.2.0-design.md) | [English](v4.2.0-design.md)

Status: design and development in progress, unpublished. Baselines are AgentSQL v4.1.0 and the pinned SQLBot Community v1.10.2 comparison environment. Any compatibility claim requires differential tests with the original client requests and responses.

## Goals and scope

| Capability | Delivered behavior | Required acceptance boundary |
| --- | --- | --- |
| Multi-turn follow-ups | Retain limited completed questions and SQL context within one conversation, using the datasource selected for that conversation | Recheck identity, current authorized schema and binding on every turn; failed turns, other conversations and result rows never reach the model; final SQL still passes through the controlled gateway |
| Recommended questions | Administrators configure questions per datasource; ordinary users read recommendations only for datasources they may use | Recommendations are text only; selecting one re-executes under current user permissions; unauthorized datasources return none |
| Terminology and SQL examples | Create, enable, disable and query business terms and examples within workspace and datasource scope | Ownership, length and count limits apply; examples do not bypass parsing, column authorization or audit |
| Authorized retrieval | Retrieve context only from currently visible tables, columns and authorized business terms | Revocation takes effect immediately; no row data, keys or cross-user material enters the model |
| File data | Import synthetic CSV/XLSX into an isolated managed datasource for controlled Q&A | Limit file size, type, rows, columns and formula risks; isolate import, query, deletion and audit by owner |
| Complex SQL and row/column rules | Add explicitly allowed read-only forms with granular rules per database adapter | Validate binding for JOINs, aggregates, aliases and wildcards by category; deny uncertain cases without broad authorization fallback |
| History migration and offline operation | Migrate verifiable conversation metadata from the pinned SQLBot version; run a configured model in a disconnected local environment | Preserve provenance, failures and rollback points; identity import alone is not full history migration; list model weights and runtime explicitly in offline contents |

## Managed file-data contract

- `parseExcel` only parses and stages a file. It cannot create a queryable table or widen permission. At most one encrypted staged file is retained per workspace/user for a limited time; client `filePath` only matches the current staged record.
- `importToDb` reauthenticates an administrator and reparses each selected sheet from the stored bytes. Requested column names, order, and types must match the staged headers exactly. Integer conversion uses decimal half-up rounding with signed 64-bit bounds. Candidate implementations of the original route and narrow gateway endpoint now reparse the original bytes rather than trusting client rows or table names.
- Table creation must use a preconfigured, isolated managed PostgreSQL datasource and dedicated schema. Client connection details cannot select a target, and no DDL may reach an existing business datasource. ChatBI holds no arbitrary business SQL handle; a narrow gateway management operation must own table creation, column-policy enrollment, and durable audit.
- A PostgreSQL staging primitive now exists inside the controlled database capability domain: server-generated random table names, fixed `agentsql_files` schema, typed values, at most eight sheets and 16 MiB of converted data, with all tables and rows committed in one transaction. Only the schema owner may use it; superusers and roles allowed to create databases or roles, bypass row security, or replicate are rejected. It grants no SELECT access, rejects unexpected non-owner default grants, and checks the reader role's effective SELECT privilege to prevent inherited owner access. Isolated PostgreSQL 16 tests use a separate unprivileged writer and cover hidden staging, default-grant and role-inheritance denial, followed by read grant, formal column binding and audited publication.
- Before physical staging, the control store journals a random operation ID and file digest in `preparing`, then commits exact table mappings, `staged`, and management audit together. Candidate publication grants SELECT to the dedicated reader role, enrolls database-bound column policies per table, checks the current SQLBot binding and policy evidence, and commits `policy_ready` and `published` with separate management audits. Query and schema discovery still check the delegated human, binding ID, Agent, datasource and table ownership; unpublished tables stay invisible. Startup recovery for an explicitly configured tenant and datasource removes hidden tables and orphan policies in `preparing`, `staged`, `policy_ready`, `deleting`, and `cleanup_needed`. Published deletion first verifies the owner and current binding, commits `deleting` with an audit to stop gateway reads, then drops physical tables and policies; failures remain retryable.
- A new table stays invisible until data loading, current-user column-policy enrollment, and audit succeed. Failures across the control and managed databases must leave it unqueryable, with a recoverable operation record to clean provisional tables. Queries, revocation, and deletion continue through the gateway's identity, column protection, result sealing, and audit chain.
- Release acceptance must compare the original SQLBot client's `parseExcel`, `importToDb`, `datasource/add`, Q&A, and deletion requests and responses, including cross-user isolation, formulas and decompression bombs, duplicate headers, numeric overflow, fail-closed behavior, and restart recovery. Candidate endpoints now give each import a distinct child binding and claim a one-use Excel datasource ID; isolated PostgreSQL 16 tests proved child-binding isolation, publication, injected deletion failure, and recovery. Complete original-client calls, complex sheet selection, cleanup after a successful import response is lost, and end-to-end process-restart acceptance remain release blockers.
- Each imported child binding records its parent's revision at creation. Parent rotation, disablement, update, or deletion immediately denies child token resolution, runtime validation, new imports, policy publication, and gateway ownership of published tables. Omitting hidden parent fields in a management update cannot bypass revocation. An isolated PostgreSQL 16 test confirmed that recovery audits the deletion state before dropping the physical table; an actual process-restart rehearsal remains open.
- If ChatBI persisted the import receipt but the browser lost the `importToDb` response, a retry by the same user with the same file and sheet configuration rechecks the child binding and visible tables, then returns the original result without creating another table. A changed selection or claimed receipt is denied. Cleanup when the gateway published but its response never reached ChatBI remains a release blocker.
- The gateway now has a candidate stable import identity for the same staged file. It derives the child binding name and connector token from the server secret, current parent revision, tenant, user, and staged-file ID; plaintext tokens are never stored in the control database. A unique request key and hashes of the original file and selected content bind one operation to that child. After a lost gateway response, a retry reparses the original file and checks the published operation, child binding, table ownership, and sheet row counts, then durably audits credential replay before returning the original result. Changed selections and deleted or unfinished operations cannot reuse the key. In a local HTTP test against isolated PostgreSQL 16, the server closed the network connection after the first publication and the client received a transport error. The original runtime closed and a separate process retried against the same control database: the same operation returned, only one physical table remained, and a changed valid column type received a conflict. Full comparison with an unmodified SQLBot client remains open.

## Release gates

### Current implementation and reference evidence (unreleased)

- The same-chat context retains at most three completed question/SQL turns. Datasource recommendations and recent-question reads are implemented. A local Qwen3 4B test followed up on synthetic sales data, changing `LIMIT 3` to `LIMIT 2`.
- The pinned SQLBot Community v1.10.2 OpenAPI contains 114 paths and 135 method/path pairs. Registered-route counts identify gaps; they are not a functional compatibility rate.
- The reference confirms terminology and SQL-example page fields, a numeric ID on create, and null data on delete. The Go implementation provides workspace-admin create, list, enable/disable and atomic bulk delete with durable audit.
- Business vocabulary is now retrieved by current workspace, bound datasource and question text, with at most eight hints and 4 KiB of text for the locally configured model. The gateway's current visible schema is fetched again on every turn.
- A SQL example enters the prompt only when it matches the current question, parses as one read-only SELECT, references one currently visible table and visible columns, and uses only a narrow function allowlist. At most four examples and 6 KiB are sent as illustrative text. Samples never execute directly; newly generated SQL still passes through gateway authorization, execution and audit.
- In an isolated local Qwen3 4B generation test, the term `GMV = sum of amount` produced `SELECT pg_catalog.sum(amount) AS gmv FROM public.sales LIMIT 20`. This verifies model generation only; it is not gateway execution, a data result, or end-to-end compatibility acceptance.
- A local Qwen3 4B generated an aggregate query over synthetic sales data with `pg_catalog.sum`, `GROUP BY`, and `LIMIT 3`. PostgreSQL `NATIVE_C_V1` column-policy enrollment now uses two phases with the same column-lineage checks: discovery, then locked revalidation through the control-plane commit, without executing the SELECT during enrollment. After enrolling `name,price` on `public.products`, the isolated Quickstart candidate gateway returned three rows for a qualified aggregate; audit 317 allowed it with four column-use details. Bare `SUM` was denied and audited as 318, and unauthorized `stock` was denied and audited as 319. The test policy was removed and the isolated gateway restored to v4.1.0. This proves only that synthetic PostgreSQL query shape; row-level rules, other aggregates, and business-system compatibility remain unverified.
- Added read-only metadata export from pinned SQLBot v1.10.2 and original-ID import. Old SQL, result rows, charts and credentials are excluded. The target user and personal datasource binding must already exist. Imported turns cannot replay or enter model history. A batch is capped at 1,000 chats and 200 questions per chat, and commits with one audit record. The local pinned SQLBot instance exported 10 chats and 10 questions, which passed AgentSQL format validation; full history and original-client acceptance remain outstanding.
- Added SQLBot `check/{id}`, `getTables` and `getFields` reads that check only the user's bound datasource through the controlled gateway and return currently visible tables and columns. Identity and binding are checked again after the remote read; revocation, binding changes and unknown tables release no metadata. Table and field comments are currently empty, and original-client response comparison remains outstanding.
- Added the SQLBot `previewData/{id}` path. It ignores submitted columns and SQL, builds a read-only query for at most 100 rows from currently gateway-visible table columns, requires a gateway audit ID, and rechecks identity and binding before returning rows. Original SQLBot table ID mappings and original-client preview data type parity are not yet preserved or accepted; route presence does not establish zero-change compatibility.
- Terminology and SQL examples now offer Excel templates, exports and bounded `.xlsx` uploads to workspace administrators. A management audit must persist before export bytes are released; each successful imported row commits with its management audit. Cells are literal strings, and formulas, macros and external links are refused. Archive, sheet, row, column and cell limits apply. A locally pinned SQLBot export template passed the parser check. Imports report successful, duplicate and failed rows. Failed rows produce an error workbook downloadable through SQLBot's original path, encrypted and isolated per user with an audited download. Only the latest workbook per user is retained for seven days. Legacy `.xls` and more complex workbook formats remain unsupported.
- `parseExcel` now provides bounded CSV/XLSX previews and encrypted staging scoped to the workspace and user. Staging and a management audit containing the actor, row count, and file digest commit together; audit failure rolls back staging. Paths, duplicate headers, oversized files, and XLSX formulas are rejected. The actual SQLBot v1.10.2 response to a synthetic CSV matched parsed field names, types, preview values, and row count. The original `importToDb` path now reparses original bytes through a dual-credential gateway and stages, grants, enrolls column policy, and publishes under a distinct child binding. ChatBI encrypts a one-use import receipt. Candidate implementations of the original `datasource/add`, `get/{id}`, `list`, and `delete/{id}/{name}` paths recheck the child's visible columns, return a JavaScript-safe numeric ID, and close gateway visibility before removing the local alias. Isolated PostgreSQL 16 proved that the base binding cannot see the child's table and that deletion failure closes visibility before recovery; targeted HTTP tests cover a synthetic CSV from import through add, get and delete. The reference SQLBot container has an existing adapter layer that rejected datasource creation for a missing mapping, so it cannot prove the complete unmodified-client flow. Complex sheet selection, lost-response cleanup, process-restart acceptance, and legacy `.xls` remain open.
- Using the pinned SQLBot v1.10.2 browser request shapes, a local isolated PostgreSQL 16 test now exercises synthetic CSV `parseExcel`, `importToDb`, AES-configured `datasource/add`, `get/list`, `getTables/getFields`, `previewData`, and deletion through ChatBI, HTTP gateway, MCP identity, and controlled execution. A two-sheet XLSX follows the same flow while selecting only its second sheet; changing the selection to the first sheet for the same staged file returns a conflict without another physical table. Publication pairs a narrow exact-table grant for each managed table with its database-bound column policy; deletion and failed-publication recovery remove both, with durable management audit. The B2 closed parser accepts only literal positive integer `LIMIT` values from 1 to 1,000; `OFFSET`, expressions, and unbounded forms remain denied. Preview returned two rows with a query audit. Replaying these synthetic request shapes does not establish full acceptance of an unmodified SQLBot browser or the user's business application.
- The unmodified SQLBot v1.10.2 image completed browser login, CSV upload, sheet selection, datasource save, schema view and data preview locally. Its actual detail page calls `tableList/{id}` and `fieldList/{id}/{tableID}`, and the preview response Base64-encodes SQL. The candidate adds these routes using only the current gateway-visible schema, derives stable table IDs from the datasource and qualified table name, denies revoked or unknown IDs, and encodes preview SQL as the original protocol does. This establishes original request shapes; it does not establish that the original browser has passed directly against the candidate.
- The same original browser fetches `system/config/key` before submitting RSA-encrypted account credentials, then reads `user/info` and `user/ws`. The candidate serves a public PKIX key when the original login private key was imported, fails closed without that key, and returns workspaces only from the current valid identity. The original startup also calls license, version and chat-parameter endpoints; their behavior has not yet been compared, so login-route coverage cannot establish whole-page replacement.
- Safe retrieval of more complex examples and further SQLBot endpoints remain outstanding. Full compatibility and release acceptance have not passed.

- Pin SQLBot Community request samples, response shapes, errors and permission behavior, reporting pass, difference or missing for each item. Static route counts are not a compatibility percentage.
- Compare original SQLBot and AgentSQL clients against synthetic PostgreSQL/MySQL data for single-turn, multi-turn, revocation, denial, masking and fail-closed behavior.
- Test a real local model. The public website offers only an explicitly labelled simulation and neither deploys nor calls a model. Each turn independently passes SQL authorization, execution and durable audit.
- In disconnected Linux, verify installation, startup, upgrade, rollback and data preservation. If weights or model runtime are excluded, claim only the corresponding base installation capability.
- Independently accept final-commit CI, signed assets, dual-architecture images, GitHub Release, website and Demo. Zero-change replacement of the user's actual business system still requires its isolated environment and remains a separate v4.5.0 gate.
