# AgentSQL v4.11.0: conversations, export, and embedding

> Development contract. A scenario earns credit only after complete positive and negative acceptance on the same final signed package with real clients, model, gateway, and database.

## Baseline and target

AgentSQL is both an independent AI data Q&A agent and an independent MCP Server database security gateway. SQLBot Community v1.10.3 is a pinned optional client, not a runtime dependency of AgentSQL's Q&A service. The released v4.10.0 passed Q1, I1, and H1 under the frozen [25-scenario contract](sqlbot-community-chatbi-score-v1103.md): **3/25 (12%)**. Q2, H2, H3, and I3 have real positive slices but lack complete original-page or security-negative coverage. One first CSV request after a ChatBI restart failed closed with HTTP 403; its cause remains unknown.

v4.11.0 prioritizes closing Q2, H2, H3, and I3, and examines H4. If all five pass alongside a same-version rerun of the existing three, the maximum is **8/25 (32%)**. This is a work target, not a release promise. Incomplete scenarios remain at zero; old-version evidence is never inherited as a pass. The goal is broader proven user workflows without relaxing authorization.

## Functional and security contract

| Scenario | Positive acceptance | Required denial and failure behavior |
| --- | --- | --- |
| Q2 authorized single-table expression | The unchanged original Q&A page and AgentSQL's own page use a real local model, PostgreSQL, and a same-source gateway to verify filtering, grouping, ordering, and limiting against SQL, values, and order | Reject unauthorized tables/columns, model-generated non-read-only SQL, excess result budgets, and in-flight row/column rule or binding changes without releasing stale values; inspect controlled audit |
| H2 restarted history | Both pages log in again and reopen the same history after a ChatBI process restart, showing SQL and values only under current authorization | Another user, disabled member, revoked/replaced binding, or changed row/column rule cannot recover old SQL or values through list, detail, or follow-up |
| H3 history export | Original-page Excel and AgentSQL-page CSV/XLSX match the current authorized gateway result; observe the first request after restart separately | Old exports are denied after revocation; gateway audit or local receipt failure releases no file; formula-like cells remain literal. Diagnose the occasional first-request 403 instead of counting a retry as stable first-request success |
| H4 conversation lifecycle | Create, list, title display/update, delete, and list after login remain consistent and isolated | Deleted conversations cannot be read, exported, or continued; cross-user/workspace IDs reveal nothing; in-flight deletion cannot release stale results |
| I3 basic and Type 4 embedding | The original `assistant.js` basic guest and Type 4 page embedding complete real Q&A, refresh, and history recovery from allowed origins | Reject disallowed Origin, missing/malicious Referer, forged/cross-frame messages, disabled guests, revoked apps, and revoked sources without issuing a token, old result, or new controlled query |

Each Q&A, historical re-query, and export derives authority from current server-side identity, workspace, source binding, and permissions. Model SQL, browser parameters, stored SQL, download URLs, and embedding messages confer no authority. Check before execution and before response; fail closed when current permissions, gateway audit, or durable export receipt cannot be established. Preserve and diagnose transient 403 evidence; do not blindly retry a rejected query or weaken audit requirements.

## Boundaries

This version does not promise accurate 128-table selection, joins, arbitrary SQL dialects, real cloud-model inference, arbitrary datasource creation, role/multi-user active rules, Type 1 advanced assistants, or zero-change migration of the user's business system. Preserve safer refusal when the original client allows unsafe behavior, and leave the scenario at zero. QEMU ARM64 is not physical ARM acceptance. The public Demo uses synthetic data and a simulated model.

## Release gates

1. All five GitHub CI jobs succeed for the exact final commit. Behavior changes have deterministic tests and relevant negative cases; raw evidence names the source, client, model, database, resource limits, and exit codes.
2. Recheck Q1/I1/H1 on the final signed package and publish the result or zero for every one of the 25 frozen scenarios. Authorization bypass, unaudited execution, stale result disclosure, or dangerous SQL execution blocks release. A safe version may ship below the scoring target if the actual score is disclosed.
3. Build and independently verify the production-signed dual-architecture assets and outer offline archive. On AMD64 and QEMU ARM64, rehearse disconnected fresh install, upgrade from formal v4.10.0, and injected startup-failure rollback; check services, health, model hashes, and metadata integrity.
4. Merge, publish GitHub Release and multi-architecture GHCR tags with anonymous pullback; update the website and explicitly simulated Demo, pass public health/allow/deny/masking/audit smoke tests, and leave canonical `main` equal to `origin/main` and clean.

Release notes must state the actual score, absence of validation on the user's real business system, QEMU limits, and any open reliability limitation. Do not claim 80% or 100% compatibility, zero-change migration, or a production latency SLA.
