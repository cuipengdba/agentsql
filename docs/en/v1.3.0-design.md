# AgentSQL v1.3.0 MySQL column strategy SELECT subset design

**Language:** [English](v1.3.0-design.md) | [Simplified Chinese](../v1.3.0-design.md)

## Goals and Commitment Boundaries

Based on v1.0.0's existing "column policy rejects unsupported MySQL paths", a column-level authorization execution path with **turned off by default and explicitly defined syntax** is added for MySQL 8.0 and 8.4. Only statements that can prove that objects, field references, column strategies, masking plans, and execution objects are consistent in the same business connection can be released. Other MySQL SQL continues to fail to close and write audits; this version is not called MySQL full dialect column-level authorization.

## First executable syntax

- A single entry, `SELECT`, only refers to an explicitly named InnoDB base table in the current data source. Optional single table alias. The projection must be an unambiguous reference to the underlying column, using a unique output alias.
- `WHERE` is limited to comparisons of supported columns with constants, `IS [NOT] NULL`, bounded `IN`, `AND`/`OR` combinations of these predicates; `ORDER BY` only accepts base columns qualified with table names or table aliases to avoid MySQL output alias masking; `LIMIT` is a bounded non-negative integer. The existing MCP query entry does not have a SQL parameter array, and the first batch does not promise external binding parameters.
- Each projection, predicate, and sorting column goes into a unified column usage set. Table permissions, column permissions, Agent permissions, rules, masking, row/time/response budgets, auditing, and final control plane fences are all executed as usual.
- Reject before execution when all conditions are not met: `*`, cross-table JOIN, subquery, CTE, UNION, view, derived table, generated column, expression projection, function/UDF, JSON_TABLE, user variable, window/aggregation, locked read, optimizer hint, statement stacking and undocumented dialect expansion. Subsequent expansion of the subset requires new authentic evidence.

## proof chain

1. Only when `column_authorization.enabled: true` and the new switch `column_authorization.mysql_single_table_enabled: true` are set, the MySQL data source is allowed to enter the new path; the static AST check first classifies the statements into a provable subset, and unknown AST nodes are rejected. Existing table-level paths are not automatically upgraded with new features. Column policy already exists but is still rejected when the switch is off.
2. Created and closed for each request**new physical connection**, to prevent the historical session temporary table from obscuring the base table; use business read-only credentials to open a read-only transaction on the connection, bind the target base table and read precise column metadata. Confirm versions, storage engines, object types, column definitions, and case patterns; don't rely on "look-alike" catalog results from a separate inspector. It must be proven through concurrent DDL experiments that the metadata lock covers the entire window from pre-binding to execution and Fpost; if it cannot be proven, this version of the syntax will not be open. MySQL`INFORMATION_SCHEMA.INNODB_TABLES.TABLE_ID`Table ID is available, but reading this table requires instance level`PROCESS`Permission; this permission is not silently granted to the business query account. If you use an independent metadata account, you must prove that the ID it reads is the same as the object holding the MDL for the business transaction, and include the account and database instance identity in the deployment contract.
3. Each column reference in the AST must be uniquely bound to a normal column of the current base table; unknown columns, ambiguous columns, generated columns, and catalog inconsistencies all fail to close. Form a standardized object/column identity, usage location, output location and Fpre summary and hand it over to the column policy and identity masking plan. Denials must also leave a lasting audit after the controlled business transaction ends.
4. Execute the original statement **** on the same connection and transaction, with a time limit and a row limit. After returning, re-read the directory to form Fpost. Inconsistencies between Fpost and Fpre, transaction shutdown failures, invalid control plane snapshots, audit failures, or final fence failures shall not deliver results to the client. The lock is not released before the data is committed; the control plane audit and final fence are performed only after the transaction is completed.
5. The audit must include SQL decisions, object/column identities, rejection reasons, Fpre/Fpost and final delivery status, the original sensitive results are not saved. Single-instance/multi-instance shared control plane failures continue to use the existing fail-closed behavior.
6. Provides operable two-stage registration for MySQL column policies: first discover basic tables and columns from the real database, and the control plane seals the table ID, directory fingerprint, column serial number, and type after passing the second real database revalidation; both policy editing and execution must read the registered identity under the same tenant. The existing universal column permissions data structure does not automatically treat manually filled column names or old CSVs as registered permissions.

MySQL identity probe credentials explicitly configure the account name and password environment variable names in `column_authorization.mysql_metadata_accounts` according to the data source ID. This account is only responsible for reading `INNODB_TABLES.TABLE_ID`, and business queries continue to use the read-only credentials of the data source; when starting the probe, you must verify that the two credentials are indeed connected to the same MySQL instance UUID. The data source fails to close when credentials are missing, `PROCESS` is missing, the instance is inconsistent, or the account mistakenly has business write permissions. The configuration does not save plain text passwords and does not lend metadata accounts to business SQL.

## Acceptance threshold

| Category | must pass |
| --- | --- |
| syntax matrix | Supported single-table SELECT and all column usage locations are passed one by one; the above exclusion syntaxes are all rejected before business SQL. |
| Policy registration | Real database discovery, second-stage re-inspection, administrator configuration, policy revision and revocation; the same name table must be invalidated after reconstruction, column position or type change. |
| MySQL real database | Restricted accounts, column allow/deny, masking, real MCP calls, and persistent auditing for MySQL 8.0 and 8.4; logs exact image digest and server version. |
| Competition and glitches | DDL and query concurrency, column rename/deletion, permission revocation, directory unavailability, transaction/connection failure, auditing unavailability, and control plane final fence failure must not leak data. |
| Compatibility and upgrade | Existing MySQL paths without column policies, PostgreSQL B2, and other databases maintain the existing behavior; upgrade/restore SQLite and PostgreSQL sub-databases from the v1.2.0 official package. |
| Delivery | Go/Web/security CI, signed release, GHCR accurate version dual-architecture anonymous pull, GitHub official release; official website, public network Demo and `latest` continue to maintain v1.0.0. |

If any authentic database proof or failure closure threshold fails, the original rejection status of the MySQL column policy will be maintained, and no syntax relaxation or table-level authorization rollback will be required in exchange for release.

MySQL's read-only transaction and metadata lock design basis: [MySQL 8.0 START TRANSACTION](https://dev.mysql.com/doc/refman/8.0/en/commit.html), [MySQL 8.0 Metadata Locking](https://dev.mysql.com/doc/refman/8.0/en/metadata-locking.html), [InnoDB TABLE_ID and PROCESS permission ](https://dev.mysql.com/doc/mysql-infoschema-excerpt/8.0/en/information-schema-innodb-tables-table.html). Whether it can meet the requirements of this version of the proof chain is still subject to the actual concurrency measurement of the real database.

The isolation MySQL 8.0.46 and 8.4.11 probes on 2026-10-18 both confirmed: the read-only account cannot read `TABLE_ID`; the explicit read-only transaction holding `SELECT ... LIMIT 0` orders concurrent `ALTER TABLE` to wait until the end of the transaction; the table with the same name is rebuilt to generate a new `TABLE_ID`. These only validate primitives and do not yet constitute an AgentSQL request-level secure link.
