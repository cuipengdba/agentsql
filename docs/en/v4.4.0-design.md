# v4.4.0 Design: Management, Datasources and Integration Matrix

**Language:** [English](v4.4.0-design.md) | [Simplified Chinese](../v4.4.0-design.md)

Status: design in progress, unpublished. The fixed comparison is SQLBot Community v1.10.2 (`aa41fc1033bb974a703df9200a98ec8b9eec5f25`); AgentSQL uses its own Go service, Web pages and branding. A static comparison against v4.3.0 code finds 65 same-shaped registrations among 135 upstream method paths and 70 paths not registered by the native Q&A service; the AgentSQL gateway provides some integration paths separately. Route counts identify work, not behavioral compatibility.

## User goal and scope

v4.4.0 covers Community datasource, user, workspace, membership, model, system variable, permission rule, table relation, language and MCP management flows, plus the local data-migration and offline deployment matrix. Each flow requires the original client and AgentSQL's own page to complete the same user task. Full functionality and zero-change replacement of a real business application remain the final v4.5.0 gates.

| Workflow | Implementation contract | Release acceptance |
| --- | --- | --- |
| Datasource management | Own page and original API for connection, test, table selection, schema sync, table/field annotations, file import and deletion; confirm workspace, ownership and backend database support on every access | Compare the original and own pages operation by operation; reject or clearly fail cross-workspace IDs, changed connection parameters, database disconnections and managed-file faults |
| Users and workspaces | User search, creation, disablement, password rotation and language; workspace creation, edits, member grants and revocation; preserve original IDs and relationships during migration | Original and own administration pages complete CRUD and restart recovery; test non-admin, cross-scope, disabled-user and old-token denials |
| Models and variables | Workspace model list, default model, connectivity and audited changes; validate, persist and restore system variables by scope | Use a real local model for allowed and failure cases; public cloud shows labeled simulation only and never stores or calls a cloud model key |
| Permissions and table relations | Datasource rule groups, user grants, row/column permissions and table relations; Q&A, preview, chart, export, API, MCP and embedding use current authority | Revocation blocks old histories, charts and embeddings; audit failure, uncertain rules and connection loss fail closed |
| Integration and migration | Compare Community API/MCP identity, session, error and event shapes one by one; read-only preflight, isolated import, paired backup and restore | Original client completes selected flows without edits; offline installation, v4.3.0 upgrade, failure rollback, dual-architecture packages and signature verification |

## Security call chain

Browser, original API/MCP and embedded SDK requests enter the Go Q&A service. It verifies token, user and workspace state, then application or membership scope and current datasource/table/column/row rules. Metadata access and generated SQL pass through the AgentSQL controlled gateway; results are masked and durably audited. Failure of a required step releases no result. Client-supplied user, workspace, rule, model or connection values are request parameters, not authority. Management writes require revision control and transactional audit.

## Database and language boundaries

Record connection protocol, vendor version, TLS, metadata, least privilege, query, revocation and fault results for every datasource category in the fixed SQLBot Community baseline. Existing AgentSQL gateway database capabilities do not automatically establish complete Q&A service support; the v4.4.0 compatibility matrix lists only measured combinations. Check the original language entry points against the pinned baseline. Translation must cover own pages, errors, help and model prompts without changing source text, numbers or audit data when the language switches.

## Release blockers

Each workflow needs reproducible browser and API evidence, Go/Web/bilingual-document CI, negative security cases, a real local model and specified databases, offline installation, upgrade and paired restore. Signed artifacts, dual-architecture images, GitHub Release, website and public Demo align to one source commit. Unverified entrances cannot be marked supported with empty responses or simulated data. Full v4.5.0 page, integration and business-application replacement conclusions require separate acceptance.

## Current implementation record

The branch now has an independent account settings page, password changes and persisted language preference, plus an administrator user page with listing, filtering, reads, creation, editing, password reset and enable/disable actions. Creation and reset require the administrator to enter a password on the own page or the deployer to configure `AGENTSQL_CHATBI_INITIAL_USER_PASSWORD`; they do not use a fixed public default password. The account index and management audit commit in one transaction, rolling back on audit failure. User editing, password reset and status changes likewise commit with their audit and revoke old tokens. Workspace read, creation, rename and empty-workspace deletion are available through the original API shapes and AgentSQL's own Users page. Rename updates member names; deletion refuses workspaces with members or data. Batch member grants, revocations and weight changes commit with their audit in one transaction. Member lists and candidate lookups have pagination and permission checks; the own Users page can change membership. SQLBot MCP HTTP helper routes cover token acquisition, session start, workspace and datasource listing, and questions. The MCP datasource list returns public metadata only. A session binds a datasource the current member may use before its first question; questions pass through the controlled gateway, masking, audit and durable-result gates. Negative tests cover cross-workspace access, token revocation and missing gateway audit. The original super-administrator's access to every imported workspace and the third-party assistant MCP route remain unfinished. User creation and reset still need original-client and deployment-config comparison; streamed text still needs event-by-event comparison. A current static route comparison finds 99 same-shaped registrations among 135 upstream method paths, leaving 36 unregistered by the native service. This is not evidence of complete functionality or zero-change replacement of a real business application.

Single and batch user deletion now remove the account index and private encrypted objects in the same transaction as the management audit. Removing the user record invalidates old tokens. An account with a managed file import or its datasource cannot be deleted until a separate gateway-resource retirement workflow completes.
The MCP model-list route returns only public model metadata after token and membership checks, never endpoint or key material. The original unauthenticated request remains incompatible and needs a secure identity adapter.

The original `mcp_model_list` body containing only `oid` is now accepted when the request also carries the existing `X-SQLBOT-TOKEN: Bearer` header. The server checks the live user and workspace membership again before responding. Anonymous requests without a header, cross-workspace access, revoked tokens and ambiguous body-plus-header credentials are denied. The original fully credential-free call remains a compatibility gap; it does not justify anonymous model enumeration.

Creating a workspace now adds the creator's administrator membership in the same transaction as the catalog and audit. Deleting a workspace with no other members or data removes that membership atomically. Members can switch their active workspace through the original endpoint. The current token's scope, next-login default and audit commit together. The original super-administrator's access to every imported workspace still requires separate acceptance.

AgentSQL's own Web page now lists joined workspaces in the account area and uses the same switch endpoint. After a successful switch it reloads the page, fetching datasources and history under the new scope. The switch control is hidden when the member has only one workspace.

System-variable management endpoints and AgentSQL's own bilingual page are in progress. Custom variables are encrypted per workspace; create, update and delete commit with the management audit. Administrators can page, filter and edit them, while ordinary members cannot read them. Variables are not yet applied to row permissions, and the page says that these settings do not change query access. This is not a complete releasable variable feature.

The current workspace model now has AgentSQL's own bilingual management page and API. An administrator can create the first default model in an empty workspace, read metadata without the key, then update the model ID, endpoint, output limit and key with a revision check; a blank key preserves the previous one. Creation and updates commit with the management audit, so a duplicate create, stale revision or audit failure rejects or rolls back the change. This still manages only one default model per workspace. SQLBot's global model catalog, multiple models, workspace mappings, arbitrary-configuration connection test and end-to-end real-model acceptance remain unfinished.

An administrator can run a bounded connectivity probe for that saved model from this page. The request accepts no client-supplied endpoint or key, calls only the model selected for the current workspace, and never sends generated test SQL to a database. A successful response reveals neither model output nor secrets. It establishes only that the model service responded at that time; SQLBot's create-time arbitrary-configuration probe, real-model Q&A and failure behavior still need separate acceptance.

The original account API Key list, create, enable/disable and delete endpoints and AgentSQL's own bilingual page are in progress. Each account may have at most five encrypted keys. Creation, status changes and deletion commit with management audit; deleting a user also removes keys and access indexes. `X-SQLBOT-ASK-TOKEN: sk <JWT>` currently reaches only bounded Q&A and datasource read routes, checking the HS256 signature, key status and current user on every request. It cannot call key management endpoints. The original client still needs request-by-request comparison of ASK claims, allowed routes, error shapes and real application integration; this is not a claim of complete API Key compatibility.

The original model administration page's list and detail read endpoints now expose the current workspace default model to administrators only. The list supports name filtering; detail reports whether a key exists without returning the key. Original first-create and existing-default-model edit routes are also available with workspace, supplier and configuration limits. AgentSQL does not yet have the original global multimodel catalog, model mappings or complete create/update/delete flows for that page. This remains a bounded stage of page compatibility work.

An original v1.10.2 browser check found that the model list needs its valid Generic OpenAI supplier ID 15 and LLM model-type ID 0; the previous values caused script errors in the card or edit form. Original first-create and edit submissions encrypt the endpoint and optional key with the same installation RSA public key used for login. The Go adapter creates only the first Generic OpenAI default model in the current workspace or edits its existing default model, preserving an omitted old key on edit and using encrypted storage, revision checks and management audit. Duplicate creation, plaintext endpoints, other suppliers and advanced arguments are rejected. The original post-save connectivity request probes only the saved model and never executes generated SQL; the empty ID posted after first-create also resolves only to the just-saved current-workspace model. On 2026-10-27, the original local page saved and reloaded an existing model name, and the local Qwen probe returned `Model reachable` within 60 seconds. In a separate isolated empty workspace, the unchanged original Add Model form created an HTTPS configuration and its card survived reload. A non-loopback HTTP endpoint was rejected by the security rule; the test HTTPS endpoint was intentionally unreachable in the subsequent probe. Unit tests cover denied users, invalid input, key preservation, duplicate creation and model failure. A global multimodel catalog, a second model, delete, default switching, original-client key rotation and the full real-model Q&A matrix remain unaccepted.

The original datasource page's `chooseTables` write endpoint now supports only claimed managed CSV/XLSX datasources. An administrator may select names imported from that file only while current gateway metadata still exposes them; the selection and management audit commit together. AgentSQL's own bilingual datasource page can display imported tables and edit the selection. Clearing the selection hides every table and blocks SQL reads for that datasource. Reselecting tables still requires current gateway authorization and audit on each read. Table annotations and table selection for database connections remain unfinished; this endpoint is not complete datasource management.

The original Q&A parameter page's read and multipart-save routes, together with AgentSQL's own bilingual Q&A settings page, now manage the assistant display name, reasoning display, SQL/log display, and zero to three context turns. Settings are encrypted and persist with management audit in the same transaction; the configured turn count changes the history actually sent to the model. Revoked administrators and audit failure close writes. The query row limit is always enforced and requests to disable it are rejected. Display flags control client presentation, not API-field access. The read-only original login-settings route now identifies account-password login and hides any shared initial password; the administrator default-password probe returns an empty value rather than publishing a fixed password to the browser. Complete original login and platform configuration, larger context windows and remaining settings flows still need implementation and acceptance.

On 2026-10-27, the unchanged SQLBot Community v1.10.2 frontend static assets and the current AgentSQL Go candidate API were served under one local test origin. In the original browser, an administrator logged in, changed the Q&A name and context-turn count on the parameter page, saved, reloaded and read the persisted values. In an isolated control store with a test initial-user password configured, the original user-management page hid the shared-password hint, created a user and showed that user in the list. Original proprietary frontend scripts were used only for local compatibility comparison and were not added to AgentSQL product assets. This evidence covers those workflows only; other original pages, password reset, account disablement, existing application integrations and complete unchanged replacement remain unaccepted.

The same isolated candidate served one real local Qwen question from the unchanged original Q&A page in the default workspace: “list regions and amounts, at most two rows.” The synthetic datasource returned `east/10` and `west/20` with gateway audit ID 735. After page reload and reopening the conversation, the original record-data route fetched the same two rows again under a new audit ID 749. This is evidence for one synthetic datasource, one question and one administrator only; complex questions, revocation, failures, additional charts and actual business replacement still need individual acceptance.

In the isolated original user-management page, an administrator disabled and re-enabled one local user. The old token returned 401 after disable and stayed invalid after re-enable. After changing that user's password to a separate test value, the original “restore initial password” button returned 200: the temporary password no longer logged in, the pre-reset token returned 401, and the locally configured initial-user password logged in again. This flow requires a deployer-configured initial-user password; the test value is not a public fixed password.

The original system-variable page created a text variable `test_region_filter=east`. Its edit request initially returned 422 because the browser sent a string ID. The Go adapter now accepts canonical decimal strings and JSON integers without a float conversion while rejecting noncanonical or out-of-range IDs. The unchanged page changed the value to `west`, which survived reload, then deleted it through the original string-ID array request (200); reload showed an empty list. Create, update and delete remain encrypted within the current workspace and commit with management audit. Variables are not yet resolved by row-permission evaluation, so this page flow does not prove an effective variable rule.

The original workspace Add Member dialog always requests candidate page `1/1000000`. The adapter accepts that exact request only on the candidate endpoint and rejects the response when the actual candidate count exceeds 10,000; normal member pages and other oversized parameters remain rejected. On 2026-10-27, the unchanged local page opened the dialog in an isolated workspace, added a test user as a regular member, changed the role to administrator, then removed the member. After reload and reselecting the workspace, its member count remained zero. Workspace service tests cover token invalidation on permission changes; more original-page roles and bulk actions still need separate acceptance.

The same original page renamed the isolated workspace and retained the new name after reload; it also created and deleted a separate empty workspace. Deletion of a workspace containing a test model returned 409 and preserved its data. The service now reports that the workspace still contains resources or members. Deletion after clearing linked resources, the cascading deletion promised by the original dialog, and real business-data migration remain unaccepted.

Although the original model card exposes Delete, AgentSQL currently has only one default model per workspace. The original page first shows a default-model restriction dialog and sends no delete request. The Go adapter still returns an explicit 409 for a direct delete request without removing the encrypted key or configuration. Unknown or cross-workspace model IDs return 404, and regular members cannot invoke the action. Second-model creation, default switching and nondefault deletion still need implementation for complete model-page compatibility.

The original card showed one authorized workspace, but its Authorized Workspaces dialog showed zero because the model-mapping read route was missing. The adapter now returns the current workspace as the original string-ID array to administrators. Repeating that same mapping is a no-op. The original Add dialog sends `POST /{id}/ws_mapping`, while removal sends `DELETE`: re-adding the current workspace is harmless, but adding another workspace or removing the sole mapping is explicitly rejected. A global model catalog and cross-workspace authorization remain unimplemented, so this single-workspace mapping is not complete authorization management.

The original Q&A results page used local Qwen to analyze the synthetic `east/10` and `west/20` rows. The original event stream produced an analysis child record and the page showed the text. After the first reload, the original page fetched only conversation metadata and did not request the child record, so the historical analysis text disappeared. The adapter now reexecutes a currently authorized and audited query only for analysis or prediction children, compares its result digest with the saved sample, and returns historical text only when they match. A changed result hides the old text. Focused tests cover matching and changed results. After rebuilding the local candidate, the unchanged browser reloaded the conversation and again displayed the historical analysis. Revocation checks still need completion. Model prose may be wrong and is not a database fact.

The unchanged original conversation list uses the rename response directly as its new title. The adapter previously returned the conversation ID, so the original page temporarily showed a numeric ID after saving. It now returns the stored title. In isolation, the unchanged original page showed the new title immediately after renaming and retained it after reload. A focused test also checks anonymous rejection and agreement between the response and persisted title.

The original prediction page requests the child record's `predict_data` even when no numeric prediction points exist. The original server returns an empty array in that case. The adapter previously returned 422 and caused a page error; the compatibility endpoint now returns `200` and an empty array only after a fresh authorized, digest-checked and audited child read. The unchanged page reloaded the same two-row sample and received the empty array without a prediction API console error. The native forecast endpoint still explicitly rejects an invalid series. The valid-series chart page needs separate acceptance.

On 2026-10-28, the unchanged original page in an isolated environment imported a four-row `month,amount` CSV, selected its managed table, asked local Qwen a question, and clicked Prediction. The compatibility endpoint returned `200` with three numeric points: `2026-05/50`, `2026-06/60`, and `2026-07/70`. The prediction prose remained visible after reloading and reopening the conversation, and the browser error log was empty. This verifies one minimal valid time series through the original entry point and data request, not other field types, chart interactions, or business application replacement. Two initial questions after import were denied by the gateway with a generic internal-error audit; restarting the isolated gateway restored execution. A second CSV was then imported and queried successfully without another restart, so the failure does not reproduce on every new table import. The initial cause is not yet established and remains a release blocker.

For that valid series, the local model prose once said that no extrapolation had been made, contradicting the three separately calculated future points. A valid series now gets bilingual explanatory prose and numeric points from the same authorized, masked and audited least-squares calculation, with an explicit unvalidated-results warning. A series without valid forecast points continues to use the local model for qualitative prose. The unchanged original page showed the future points and explanation again, retained them after reload, fetched prediction data with `200`, and had no browser errors. Model failures, more series shapes and full chart interactions still need acceptance.
