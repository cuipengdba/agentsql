# v4.4.0 Design: Management, Datasources and Integration Matrix

**Language:** [English](v4.4.0-design.md) | [Simplified Chinese](../v4.4.0-design.md)

Status: design in progress, unpublished. The fixed comparison is SQLBot Community v1.10.2 (`aa41fc1033bb974a703df9200a98ec8b9eec5f25`); AgentSQL uses its own Go service, Web pages and branding. A static comparison against v4.3.0 code finds 65 same-shaped registrations among 135 upstream method paths and 70 paths not registered by the native Q&A service; the AgentSQL gateway provides some integration paths separately. Route counts identify work, not behavioral compatibility.

## User goal and scope

v4.4.0 covers Community datasource, user, workspace, membership, model, system variable, permission rule, table relation, language and MCP management flows, plus the local data-migration and offline deployment matrix. Each flow requires the original client and AgentSQL's own page to complete the same user task. Full functionality and zero-change replacement of a real business application remain the final v4.5.0 gates.

| Workflow | Implementation contract | Release acceptance |
| --- | --- | --- |
| Datasource management | Own page and original API for connection, test, table selection, schema sync, table/field annotations, file import and deletion; confirm workspace, ownership and backend database support on every access | Compare the original and own pages operation by operation; reject or clearly fail cross-workspace IDs, changed connection parameters, database disconnections and managed-file faults |
| Users and workspaces | User search, creation, disablement, password rotation and language; workspace creation, edits, member grants and revocation; preserve original IDs and relationships during migration | Original and own administration pages complete CRUD and restart recovery; test non-admin, cross-scope, disabled-user and old-token denials |
| Models and variables | Workspace model list, default model, connectivity and audited changes; validate, persist and restore system variables by scope | Use a real local model for allowed and failure cases; public cloud shows labeled simulation only and never stores or calls a cloud model key |
| Permissions and table relations | Datasource rule groups, user grants, row/column permissions and table relations; Q&A, preview, chart, export, API, MCP and embedding use current authority | Revocation blocks old histories, charts and embeddings; audit failure, uncertain rules and connection loss fail closed |
| Integration and migration | Compare Community API/MCP identity, session, error and event shapes one by one; read-only preflight, isolated import, paired backup and restore | Original client completes selected flows without edits; offline installation, v4.3.0 upgrade, failure rollback, dual-architecture packages and signature verification |

## Security call chain

Browser, original API/MCP and embedded SDK requests enter the Go Q&A service. It verifies token, user and workspace state, then application or membership scope and current datasource/table/column/row rules. Metadata access and generated SQL pass through the AgentSQL controlled gateway; results are masked and durably audited. Failure of a required step releases no result. Client-supplied user, workspace, rule, model or connection values are request parameters, not authority. Management writes require revision control and transactional audit.

## Database and language boundaries

Record connection protocol, vendor version, TLS, metadata, least privilege, query, revocation and fault results for every datasource category in the fixed SQLBot Community baseline. Existing AgentSQL gateway database capabilities do not automatically establish complete Q&A service support; the v4.4.0 compatibility matrix lists only measured combinations. Check the original language entry points against the pinned baseline. Translation must cover own pages, errors, help and model prompts without changing source text, numbers or audit data when the language switches.

## Release blockers

Each workflow needs reproducible browser and API evidence, Go/Web/bilingual-document CI, negative security cases, a real local model and specified databases, offline installation, upgrade and paired restore. Signed artifacts, dual-architecture images, GitHub Release, website and public Demo align to one source commit. Unverified entrances cannot be marked supported with empty responses or simulated data. Full v4.5.0 page, integration and business-application replacement conclusions require separate acceptance.

## Current implementation record

The branch now has an independent account settings page, password changes and persisted language preference, plus an administrator user page with listing, filtering, reads, creation and enable/disable actions. Creation requires the administrator to enter an initial password on the own page or the deployer to configure `AGENTSQL_CHATBI_INITIAL_USER_PASSWORD`; it does not use a fixed public default password. The account index and management audit commit in one transaction, rolling back on audit failure. User status changes and management audits likewise commit together and revoke old tokens. Existing workspaces can be read, while batch member grants, revocations and weight changes commit with their audit in one transaction. Member lists and candidate lookups have pagination and permission checks; the own Users page can change membership. SQLBot MCP HTTP helper routes cover token acquisition, session start, workspace and datasource listing, and questions. The MCP datasource list returns public metadata only. A session binds a datasource the current member may use before its first question; questions pass through the controlled gateway, masking, audit and durable-result gates. Negative tests cover cross-workspace access, token revocation and missing gateway audit. User editing/deletion, workspace creation/editing/deletion, the original model-list and third-party assistant MCP routes remain unfinished. User creation still needs original-client and deployment-config comparison; streamed text still needs event-by-event comparison. A current static route comparison finds 83 same-shaped registrations among 135 upstream method paths, leaving 52 unregistered by the native service. This is not evidence of complete functionality or zero-change replacement of a real business application.
