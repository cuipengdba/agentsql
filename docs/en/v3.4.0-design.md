# v3.4.0 Kingbase and Vastbase depth design

**Language:** [English](v3.4.0-design.md) | [Simplified Chinese](../v3.4.0-design.md)

Status: candidate implementation complete; the actual enabled scope is in the [live acceptance](v3.4.0-acceptance.md). The pinned targets are the locally available KingbaseES V9R1C10 image in PG mode and Vastbase G100 V3.0 Build 9 (commit 30156) in PG mode. Their versions, licenses, modes, and topologies must be recorded again after startup. This evidence cannot be extended to other versions, Oracle compatibility mode, or clusters.

## User problem and current boundary

Kingbase currently connects through the PostgreSQL protocol path. Verified TLS, least privilege, MCP masking, and audit have evidence for one pinned instance. Vastbase has a separate read-only adapter that checks the G100 Build 9 identity, PG mode, and read-only state at startup. Types, plans, and query subsets still require specific proof for each server. Protocol similarity does not authorize reuse of PostgreSQL's native B2 binder. Column policies must continue to fail closed when column provenance cannot be proved.

## Implementation scope

1. **Queries and types:** Use matching synthetic tables on both pinned instances to check integer, exact numeric, text, date/time, Boolean, binary, and JSON types where the server supports them. Record discovery, samples, nulls, pagination, restricted `SELECT`, and unknown-type behavior. Unknown types, complex expressions, writes, and multiple statements must not be treated as safe reads.
2. **Column authorization:** Enable only a restricted `SELECT` subset where one base table and every used column can be proved. Projection, predicates, ordering, and pagination must use columns allowed by the current policy. Metadata lookup, authorization, and execution must share a read-only transaction with relation locking or equivalent catalog-race protection. Reject views, functions, derived columns, JOINs, subqueries, wildcards, and syntax with uncertain provenance initially. Do not reuse the PostgreSQL-only native B2 extension without vendor proof, or treat an offline preview as execution permission.
3. **Execution and cost:** Recognize only EXPLAIN nodes observed on each pinned build; reject unknown shapes, negative estimates, and overflow before execution. Preserve row, timeout, pool, concurrency, and read-only-account bounds. Return results only after masking and durable audit.
4. **Operations:** Verify wrong CAs and names, certificate and credential rotation, lost connections, cancellation, audit-store failure, and allowed/denied queries after recovery. Document connection settings, support tiers, upgrades, and rollback.

## Release gates

For each live server, real HTTP MCP must pass allowed queries, unauthorized columns and tables, write and multi-statement denials, masking, durable audit, and fail-closed faults. Run bounded load within the configured pool and report success and latency without claiming an SLA. Also complete a real-client check, prior-version upgrade and restore, Go/Web/bilingual-doc CI, signed dual-architecture assets, anonymous GHCR pull, website, and public Demo smoke tests. If column provenance cannot be proved for either vendor, keep that vendor's column-policy path closed and disclose the missing capability in the release notes.
