# Domestic database adaptation preliminary research

**Language:** [English](ecosystem-db-compat-research.md) | [Simplified Chinese](../ecosystem-db-compat-research.md)

> Document status: Pre-research and experimental protocol path testing, not compatibility certification or support statement. The actual measurement conclusions on 2026-10-01 only apply to the community version, topology and use cases listed below; commercial versions and unverified items still need to be confirmed by the manufacturer after providing a test environment, driver and documentation consistent with the target version.

AgentSQL's current full dialect paths are PostgreSQL and MySQL; there is also a restricted, fail-closed read-only path for SQL Server 2025. The latter is not full T-SQL support. This preliminary research is used to split other database access work and arrange the joint verification sequence, and should not be used as the external basis for "supported" or "adaptation completed". Even if a database claims to be compatible with PostgreSQL, MySQL, or Oracle, it cannot be directly deduced that its SQL dialect, system catalog, driver behavior, and security capabilities are exactly the same as those of the corresponding database.

## SQL Server 2025 Limited Capability Baseline (2026-10-05)

This repository treats `sqlserver` as an independent `DBType`, only accepts SQL Server 2025 (product major version 17), and the default port is 1433. The connection uses pure Go `github.com/microsoft/go-mssqldb`, and the normal build does not rely on CGO. The external caliber of this path must be "SQL Server 2025 limited read-only support" and cannot be abbreviated to "Full support for SQL Server/T-SQL".

| Ability | Current status | border |
| --- | --- | --- |
| Connection, pooling, ping, timeout, stable error classification | Realized | Start probe requirement `SERVERPROPERTY('ProductMajorVersion') = 17`; other major versions deny access |
| transmission encryption | force | Defaults to `strict` (TDS 8.0); compatibility mode maps to `encrypt=true` and authenticates certificates; clear text mode is not provided. `TrustServerCertificate` only allows explicit selection of compatibility mode, and only for controlled development environments |
| metadata discovery | Realized | Fixed parameterized query `sys.tables`, `sys.schemas`, `sys.columns`, `sys.types`; only returns visible metadata of the current account, fails to close when permissions are insufficient or the result shape is abnormal, and does not fall back to the spliced caller SQL |
| Sampling and business inquiries | restricted implementation | Only single, direct table reference, narrow `SELECT` without function/subquery/annotation/binding tags allowed; supports square bracket identifiers, `TOP` and limited `OFFSET/FETCH` |
| execution plan | restricted implementation | Use `SET SHOWPLAN_XML ON/OFF` to read the estimated plan, do not execute the target query; XML has size, depth and node limit, unknown format fails to close |
| DML, DDL, stored procedures, dynamic SQL, batch processing | Not supported | `INSERT/UPDATE/DELETE/MERGE`, `EXEC/EXECUTE`, `xp_cmdshell`, OLE automation, `OPENROWSET`/`OPENDATASOURCE`/`OPENQUERY`, `BULK`, `WAITFOR`, `DBCC`, `USE`, `SET` and multiple statements are denied; therefore there is no path for "UPDATE/DELETE without WHERE to be allowed" |
| B2/B5 and PostgreSQL native binder | Not supported | B2/B5 is still exclusive to PostgreSQL, does not disguise SQL Server as PostgreSQL, and does not reuse its catalog/OID/RBAC certificates |
| Level authorization | Do not declare | SQL Server paths currently use only generic static rules, table-level policies, and result-level controls; PostgreSQL B2 column-level attestation may not be claimed to apply to SQL Server |

`sys.*` was chosen instead of relying only on `INFORMATION_SCHEMA` because Microsoft clearly stated that INFORMATION_SCHEMA only represents a subset of metadata and does not guarantee coverage of all object metadata; the catalog view also follows the metadata visibility of SQL Server, and the caller can only see the security objects that it owns or has authorized permissions. Reference: [SQL Server 2025 New Features ](https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2025?view=sql-server-ver17), [`sys.columns`](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-columns-transact-sql?view=sql-server-ver17), [`INFORMATION_SCHEMA.TABLES` Limitation ](https://learn.microsoft.com/en-us/sql/relational-databases/system-information-schema-views/tables-transact-sql?view=sql-server-ver17).

TLS configuration is based on Microsoft Go driver documentation: `strict` uses TDS 8.0 and requires SQL Server 2022 or higher; `encrypt=true` will encrypt and verify the certificate; `TrustServerCertificate=true` skips certificate verification and is only suitable for testing. Reference: [Go Driver Encryption and Certificate ](https://learn.microsoft.com/en-us/sql/connect/golang/encryption-certificates?view=sql-server-ver17), [Go Driver Security Best Practices ](https://learn.microsoft.com/en-us/sql/connect/golang/security-best-practices?view=sql-server-ver17).

`SHOWPLAN_XML` returns the estimated plan without executing the statement, but the account still needs to have the required execution permissions on the referenced object and the `SHOWPLAN` permission on the related database. Production accounts should only be granted to business `SELECT`, necessary directory visibility and `SHOWPLAN`, explicitly denying `CONTROL SERVER`, `sysadmin`, `db_owner`, DDL/DML, stored procedure execution and external access capabilities. Reference: [SET SHOWPLAN_XML](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-showplan-xml-transact-sql?view=sql-server-ver17).

The environmental gating integration test is `TestSQLServer2025ExecutorE2E`. It is skipped by default; only connect to the real instance if `AGENTSQL_SQLSERVER_2025_E2E=1` and `AGENTSQL_SQLSERVER_HOST/PORT/DATABASE/USERNAME/PASSWORD` (optional TLS variables) are set. The test creates and drops fixed-prefix synthetic tables without downloading or automatically accepting SQL Server mirroring licenses.

### 0.4 OpenTenBase initialization, obstacles and reproducibility boundaries

Image `domainlau/opentenbase:v2.5.0` is actually measured as Ubuntu 22.04 installation package image: default user `opentenbase`, working directory `/var/lib/opentenbase`, including `gtm`, `initgtm`, `initdb`, `pg_ctl`, `pgxc_ctl`, `postgres`, `psql` have no automatic initialization entry, and the default command is `/bin/bash`. This round starts 1 GTM, 1 CN, and 1 DN in a single container: GTM 20001; CN 11000, pooler 11001; DN 21000, pooler 21001. This topology is for compatibility smoke purposes only and does not represent a recommendation for production deployment.

According to the official information, the OpenTenBase standard quickly starts using `opentenbase_ctl` to install GTM/CN/DN; the component documentation also gives the CN initialization method with `--master_gtm_nodename`, `--master_gtm_ip`, and `--master_gtm_port`. This round of mirroring does not have the `opentenbase_ctl` supporting entry, so minimal initialization is completed according to the component tool. Based on: [OpenTenBase Quick Start](https://docs.opentenbase.org/en/guide/01-quickstart/), [ Component Installation and Management ](https://docs.opentenbase.org/guide/05-component/), [v2.5.0 Release Notes ](https://docs.opentenbase.org/en/release/v2-5-0/).

The key steps and actual differences are as follows:

1. After mounting the data volume, first set the directory owner to UID/GID 1000 in the container; otherwise, the original text of `initgtm` / `initdb` is `could not create directory ... Permission denied`.
2. `initgtm -Z gtm` initializes and starts GTM. `gtm_ctl -w` still stops at `waiting for server to start` after it has been started. This round will continue after three confirmations of process, port and GTM log. You cannot only rely on the wrapper waiting state.
3. `initdb` failed for the first time without transmitting the GTM master node parameters. The original text included `FATAL: syntax error at or near "("` and `create gtm node (null) with (type='gtm', host='(null)',port=(null), primary=1);`. After adding `--master_gtm_nodename=gtm --master_gtm_ip=127.0.0.1 --master_gtm_port=20001`, CN/DN is initialized successfully.
4. When the startup parameters are directly added to `gtm_host`, it fails. The original text is `FATAL: unrecognized configuration parameter "gtm_host"`; after removing the runtime parameters and using the persistent GTM information of `initdb`, the startup is successful.
5. In the bidirectional registration node between CN and DN, CN creates `DEFAULT NODE GROUP` and `SHARDING GROUP`, and then creates the synthesis table of `DISTRIBUTE BY SHARD(id)`. The actual measured `version()` is `PostgreSQL 10.0 OpenTenBase V2 ... 64-bit`, and the CN direct connection query is successful; the `EXPLAIN (FORMAT JSON)` command can return the text with `Remote Fast Query Execution` as the root node, but the second batch of reviews confirmed that the text lacks a comma between `"Node/s": "dn001"` and `"Remote plan"`, and is not legal JSON.
6. Mirror the initial HBA with only local trusts. The original text of the gateway’s first connection is `FATAL: no pg_hba.conf entry for host "172.17.0.1", user "opentenbase", database "postgres", SSL off`. This round does not open the entire network segment, but creates a minimal read-only test role, and only adds the `md5` rule of `/32` for the Docker host address, target library, and this role.
7. A storm occurred when the audit/maintenance log directory was missing during the initial startup. The original text was `could not open audit log file "log/audit/audit-Thursday-06.log": No such file or directory` and `could not open audit log file "pg_log/maintain/maintain-Thursday-06.trace": No such file or directory`. After creating the CN/DN corresponding directory and reloading it, it was repeatedly pulled up and stopped. Subsequently, it was still observed that the missing log of the 2PC cleanup function in the image should be continued in the official topology.

It is allowed that the failure of the query is not caused by the database account, PG protocol or failure to read the query results: the same read-only account can return 2 rows from the CN direct connection, and can still return after turning on `default_transaction_read_only=on`; when the second batch uses the same pgx v5.9.2, 1 MiB front-end frame limit and operating parameters as AgentSQL, both `Ping` and direct `Query` also return 2 rows. The root cause has been located in pre-query plan evaluation: the `EXPLAIN (FORMAT JSON)` text returned by OpenTenBase is missing a comma, and AgentSQL's fixed PostgreSQL JSON plan parsing fails. The original error at the actuator level is `parse PostgreSQL explain result: decode JSON plan: invalid character '"' after object key:value pair`, and the outer layer of the gateway still only exposes `AUTH_DATABASE_ERROR` according to the security design. AgentSQL is in B2 `feature-off`, so this problem has nothing to do with B2; until the compatible branch is implemented and the regression is completed, the status remains "to be further adapted" and must not be written as actual test passed.

### 0.5 Commercial Version Protocol Mapping Scheme

The repository still does not use vendor aliases to pretend to be compatible dialects: `Datasource.DBType`, parser, executor and discovery are all registered according to explicit dialects; in addition to existing dialects, the new addition in this round is the independent `sqlserver`, instead of mapping it or other vendors to `postgres` / `mysql`. B2 is still only detecting the exact `DBType == "postgres"`. Therefore, aliases such as `kingbase`, `highgo`, and `tdsql` were not added; adding only aliases would cover up differences in system directories, versions, types, and security capabilities, and form false support claims.

#### 0.6.3 OpenTenBase root cause recurrence and recommended changes

When restoring a single machine GTM/CN/DN, GTM must be explicitly started with 20001, and DN must be explicitly started with 21000, pooler 21001; otherwise, CN/DN will appear `GTM error, could not obtain global timestamp` or fall to the default 5432. After recovery, AgentSQL Ping 4 ms, discovery succeeded (audit ID 5), R006 rejection succeeded (audit ID 13), and allowed query still failed with `AUTH_DATABASE_ERROR` (audit ID 14, audit code `GATEWAY_INTERNAL`).

Independent reproduction rules out PG connection and normal query read issues: pgx v5.9.2 Under the 1 MiB bounded frontend of `default_transaction_read_only=on`, `statement_timeout=5000` and AgentSQL, `Ping` succeeds with field OID `23/1043/1043/1043` and both rows can be read in full. When calling the existing executor of the repository directly, `Query` also returns `rows=2, err=<nil>`; the failure only occurs in the preceding `Explain`:

```text
otb-v06 explain: *fmt.wrapError: parse PostgreSQL explain result: decode JSON plan: invalid character '"' after object key:value pair
otb-v06 query: rows=2 err=<nil>: <nil>
```

The key original text in the text returned by the database is:

```text
"Node/s": "dn001"
```

## 2. AgentSQL access extension point

The repository currently does not have plug-in dialect interfaces centralized under a single `internal/dbext` directory. Database capabilities are distributed at multiple levels. Adding dialect cannot just add an enumeration to the data source type or map the compatible library to `postgres` / `mysql`. It is recommended to abstract and stabilize the contract first, and then access it through the following path:

1. **data source model and management plane**: The data source in `internal/model` is identified with `DBType` type; the management API, persistence verification, console form and configuration currently revolve around `postgres` / `mysql`. New databases need to define stable dialect IDs, default ports, connection parameters, credentials and TLS boundaries, and ensure compatibility with old data.
2. **Drivers and connection pools**：`internal/authorizedexecute/internal/businessdb`of`Executor` / `Session` / `WriteTx`is the main execution contract,`openExecutor`Explicit dispatch by dialect; the SQL Server branch only implements connections, pings, SHOWPLAN, queries, and restricted read-only sessions, not write transactions. Each new dialect must declare connection, session, query, write, transaction, timeout cancellation, row limit and safe error mapping capabilities item by item; the protocol compatibility library must also verify connection pooling and cancellation semantics.
3. **SQL parsing and standardization**: `internal/parser.NewParser` Register parser by dialect. SQL Server uses a narrow, fail-closed subset of T-SQL SELECTs that supports bracket identifiers, `TOP`, and common table aliases, but does not treat stored procedures, dynamic SQL, batch/external data sources, or DML as supported syntax. When adding a new dialect, you need to decide whether to reuse existing AST transformations, add a compatibility layer, or introduce an independent parser; you must use the real dialect corpus to verify single statement constraints, object extraction, statement classification, dangerous functions, comments, and column lineage, and continue to fail-closed when parsing is uncertain.
4. **rules and dynamic evaluation**: `internal/engine` only accepts the canonical AST of registered dialects, and the rules also include dialect-specific capabilities. SQL Server reuses general static rules and uses restricted `SHOWPLAN_XML` dynamic evidence; the estimated number of rows, transaction status, and risk management commands need to be reviewed one by one and cannot be released by default because the rules are not recognized.
5. **Discovery and metadata reading**: `internal/controlledread` Generate identifiers, catalog queries, and sampling SQL for each supported dialect. SQL Server uses `sys.tables` / `sys.schemas` / `sys.columns` / `sys.types` and `SELECT TOP`; the new dialect still needs to adapt catalog/schema meaning, basic table filtering, type discovery, sampling queries and security failure when insufficient permissions.
6. **type system and result processing**: It is necessary to establish a mapping of database types to AgentSQL nine types of masking types, covering numerical values, date and time, binary, JSON, large objects, custom types and `NULL`, while verifying column names, source tables/column metadata, character sets and time zones. The existing fail-closed semantics should be maintained when column ownership cannot be reliably determined.
7. **Authorization, masking and auditing**: Table-level/column-level policy matching, mask/hash/block/range, audit fields and error masking must be included in dialect regression. Database-native column permissions, views, row-level security, or masking capabilities can serve as defense-in-depth, but cannot replace AgentSQL's application-layer decision-making evidence chain without design.

### B2 current boundary

The code confirms that `internal/bootstrap/b2_runtime.go` only performs B2 probing on the data source of `DBType == "postgres"`; all non-PostgreSQL data sources, including MySQL, will enter `unsupported_datasources` due to `B2_DATASOURCE_DIALECT_UNSUPPORTED`. Therefore, even if any MySQL-compatible database can reuse connections and parsers, it cannot claim to have obtained B2 column-level authorization capabilities; its column-level authorization closed loop needs to be independently designed, implemented, and verified. A PG-compatible database cannot just modify `DBType` to disguise it as PostgreSQL. It still needs to verify the catalog, binder, type and fault closure semantics.

## 5. Risks and Constraints

- **Promotion boundary**: Databases that have not completed adaptation and acceptance can only write "planning", "pre-research" or "under evaluation", but cannot write "supported", "natively compatible" or imply that they have obtained manufacturer certification. Community version and commercial version, stand-alone and distributed version, and different compatibility modes shall not replace each other's conclusions.
- **protocol compatibility boundary**: The network protocol connectable is not fully compatible with SQL dialects, transactions, system catalogs, types, error codes, cancellation semantics and `EXPLAIN`. Simply reusing the PG/MySQL driver or parser may cause incorrect release, and the security gateway must be fail-closed.
- **License and Distribution**: Vendor databases, drivers, images, and test licenses may be closed source or restrict redistribution. It is only verified in the official environment, mirror or customer authorized environment licensed by the manufacturer; whether the driver can be distributed with AgentSQL, statically linked or used for CI must be reviewed on a case-by-case basis.
- **Environmental authenticity**: Conclusions from community images, compatibility modes, or older versions cannot be automatically extrapolated to customer production versions. All projects that have not obtained the target version environment are marked as "pending environment verification by the manufacturer", and fictitious performance, compatibility rate or pass rate are not recorded.
- **Differences in security capabilities**: The names of database native column-level authorization, views, RLS, auditing, or masking are similar, but the semantics and evidence chain may be different. The federation solution needs to clarify which ones are executed by AgentSQL, which ones are executed by the database, and the boundaries when connecting directly by bypassing the gateway.
- **Performance and Stability**: Driver connection pooling, timeout cancellation, long transactions, failover, encoding and large object processing may affect security decisions and resource release. After the minimum case is passed, stress, failure and upgrade regression are still required, and functional fumigation cannot be used as a substitute for production suitability assessment.
