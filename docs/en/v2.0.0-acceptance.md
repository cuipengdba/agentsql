# AgentSQL v2.0.0 candidate environment acceptance

**Language:** [English](v2.0.0-acceptance.md) | [Simplified Chinese](../v2.0.0-acceptance.md)

Status: Feature candidate has completed two-node walkthrough. Formal sealing CI, signed release assets, GHCR, official website and public website Live Demo have also been seen as [. Official release evidence ](v2.0.0-release-evidence.md); the candidate data in this document does not automatically expand the scope of production support.

Test environment: 2026-10-18 to 2026-10-19, kind v0.33.0 on Windows host, Kubernetes v1.37.0, 1 control node, 2 Ready worker nodes. Metadata, audit, and read-only business libraries are all isolated PostgreSQL 18 containers; the business database only has synthetic `public.customers` and unauthorized `public.internal_notes`. Dual gateways use independent RWO PVCs, the same 32-byte key, PostgreSQL shard storage, and a minimum-privilege running account. The test network was not configured with TLS, nor did it simulate PostgreSQL's own primary and secondary failures.

| Acceptance items | Candidate environment actual test |
| --- | --- |
| Baseline, migration and backup | Start dual nodes from the official `v1.9.0` image; metadata 21, audit 6. The complete set of `pg_dump -Fc` backups was restored in two independent PostgreSQL instances, and the v1.9.0 and v2.0.0 candidate binaries respectively executed the dual database `migrate --check`, both of which were `current`. v2.0.0 independent migration job and read-only schema job passed. |
| Two-node configuration | Pre-deployment check returns `KUBERNETES_PREFLIGHT=PASS namespace=agentsql nodes=2`. The two Pods are distributed on different working nodes, have independent PVCs and different B2 instance IDs; the binary digests of the same version are consistent, and the B2 protocol is 3 active. |
| Concurrent start | v1.9.0 An RBAC unique key race condition occurs during the first dual Pod initialization; a bounded retry is added to the candidate version. After the database was restored and restarted at the same time, a race condition in the B2 control fence ETag was also found; the candidate version only reread the startup conflict and retried in a bounded manner. After the repair, both Pods were ready at the same time, and continued incompatibility remained downgraded. |
| Management-side PostgreSQL column binding | The candidate version creates a new column policy through the API and then calls `bind-postgres`. Both the error object and multi-statement SQL return 409; the correct single-table closed binding mode registers 3 columns, 6 output/reference usage permissions, the policy is revised to 2, and the binding status is `healthy`; the old ETag returns 412. Real SQL execution is only triggered by subsequent MCP requests. Rebuild a Pod after registration, B2 is still active, allow/deny passes with audit ID 54/55. |
| Two-node MCP secure link | The two nodes of the candidate version each perform allowed query, unauthorized table R010 rejection and mobile phone number masking. The audit database persistent record ID 49–52: `allow,deny,allow,deny`, and each time the allowed response desensitizes 2 cells. Stateless MCP responses do not send a session ID. |
| Real MCP client | MCP Inspector 0.16.8 and Dify MCPClient 1.17.1 respectively perform single-row permission query, mobile phone number masking and unauthorized table R010 rejection through the candidate gateway. Independent Audit Library Record ID 88–91: `allow,deny,allow,deny`. The client runs in an isolated host and container and accesses the kind Pod forwarding port through a temporary Host header mapping; this mapping is not written into the production configuration. |
| Synthetic short-term capacity and audit consistency | Each of the two nodes received 8 allowed queries with concurrency level 4, 16/16 returned `allow`, each masked 2 cells, a total of 1.88 seconds, and the observed throughput was 8.53 QPS, p50 437.0 ms, p95 547.0 ms. Responding audit IDs 72–87 were all unique; the independent audit library yielded 16/16 unique records, all with decision `allow`. The original record is saved on the acceptance host `D:\CodexLS\outputs\agentsql-v200\capacity-*.log`. This is a single short-term synthetic observation, not a sustained load or production capacity commitment. |
| Single node failure | After cordoning a worker node and stopping its Pod, EndpointSlice only retains another Ready Pod; with Service's permission/R010 denial, masking and audit, it continues to pass (ID 19/20). After restoring the node, the original Pod is ready again with the original PVC. |
| Depend on failure shutdown | Controlled query returns `error` and does not deliver results when stopping standalone audit library; after recovery allow/deny again and write audit ID 22/23. When stopping the metadata library, initialization returns HTTP 401, and the B2 lease is downgraded; after restoring the library, rebuild the two Pods, and the two nodes are ready again. |
| Identity and tenants | After rotating the Agent Key test, the old Key received HTTP 401 on both nodes; the new Key passed the secure link on both nodes (Audit ID 43–46). The administrator of another tenant reads the original tenant data source and returns 404, and its Agent borrows the MCP query from the original data source and does not get the data. |
| Upgrade and rollback | B2 strictly compares binary digests, so a rolling update mixing v1.9.0/v2.0.0 blocks new Pods. The manifests now use `OnDelete` and a maintenance window: stop both replicas and wait for leases to expire. After rollback to the official v1.9.0 image, both Pods passed the security chain (audit IDs 35–38); switching back to the v2.0.0 candidate passed again (IDs 41/42). |

Boundary: Fixed two gateways and specified PG18/kind topology; business database is synthetic data, no evidence of real customer concurrent load, production network, external TLS or PostgreSQL HA. B5 cross-request transactions, status sessions, and event resumption are turned off in this dual-gateway configuration; QPS is a per-node budget, not a global strongly consistent quota. Management-side column registration in PostgreSQL native extended mode is still not supported, and the registration API only covers a single ordinary table in closed binding mode.
