# AgentSQL v4.16.0 · Row and column permissions, masking, and concurrent isolation

**Languages** [Chinese](../v4.16.0-design.md) · [English](v4.16.0-design.md)

This release targets a complete PostgreSQL flow in which AgentSQL's native Q&A and standalone MCP Server security gateway enforce row restrictions, column permissions, and result masking. It adds Q5 and Q6 to acceptance against the fixed SQLBot Community v1.10.3 Q&A matrix. The planned score is 16/25 (64%) after both new cases and the previous cases pass. [Scoring contract](sqlbot-community-chatbi-score-v1103.md)

## Authorization boundaries

The current user, workspace, and personal data-source binding determine the scope of a question. The model reads the authorized schema and generates SQL. The gateway binds the actual database objects, checks current column permissions, executes the controlled query, and masks and audits the result before release. Acceptance uses active B2 PostgreSQL column authorization and isolated synthetic records.

Tests observe changes to ChatBI row rules and gateway column and masking policies independently. A restrictive change is checked against in-flight responses, history, exports, and reads after restart. Two ordinary users' simultaneous requests are checked against their respective results, conversations, and audits.

## Acceptance scenarios

| Scenario | Acceptance criteria |
| --- | --- |
| Q5 Row and column permissions and masking | A real model questions synthetic orders. The answer contains only the current region and permitted columns. Email addresses are masked by the active rule. Check in-flight revocation and the rejection of stale results through history, CSV, and Excel. |
| Q6 Concurrent questions and isolation | Two ordinary users with different rights ask concurrently through the fixed original client. Verify each user's results, history, and current access. Revoke one user's rights and check that the other request remains within its own authorization. Repeat after restart. |

Record the database and model versions, active authorization mode, entry points exercised, audit IDs, and observed latency. Final acceptance uses the signed artifact from the exact release commit.
