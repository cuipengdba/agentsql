Traffic auditing covers allow, deny, and fail decisions entering the SQL pipeline. The MCP tool layer's preemptive rejection of missing parameters, unauthorized data sources, or incorrect tool usage may return before entering the pipeline and may not result in persistent traffic auditing; this boundary also applies to old and new entrances, see the access guide for details.
After the task key passes the MCP protocol, authentication and tool parameter verification and enters the `query` processor, it will be sent to the SQL pipeline; erroneous SQL, unauthorized or non-existent data sources will leave traces according to the authorized identity. Rejections at the protocol or authentication stage (such as incorrect version headers, malformed requests, oversized request bodies, or revoked keys) that occur before the pipeline are included in this persistent traffic auditing guarantee.
The creation and revocation of temporary authorization and management audit on the management side currently cannot be submitted atomically across repositories; when the creation of the audit fails, the key will not be returned and the revocation will be compensated. If the revocation of the audit fails, 500 may be returned, but the revocation itself has taken effect. Please refer to the task authorization document for processing methods.

## Upgrade Notes

1. Stop the old service, back up the control library and the paired `AGENTSQL_SECRET`; deploy the PostgreSQL branch database to back up the metadata and audit libraries at the same time, and record consistent recovery points.
2. Use the v0.7.0 `agentsqlctl migrate --check` to be deployed to check the status of the migration and verify the target version and database connection. `--check` DDL is not executed.
3. Execute `agentsqlctl migrate` with migration owner in the upgrade window. To maintain the production deployment of `store.auto_migrate: false`, the migration must be completed before starting the new version of the gateway.
4. Check `/healthz`, `/readyz`, old MCP entrance and new entrance; use real test Agent to verify allowed query, unauthorized denial, masking, audit association and temporary authorization revocation.
5. If the migration fails or needs to be rolled back, first deactivate the new version, and then restore the complete set of database backups and pairing keys before the upgrade. The SQLite merge library can be returned to the accepted v0.6.0; the PostgreSQL metadata/audit sub-library has been maintained and built in an isolated environment with v0.6.1 to complete the dual-database rollback drill, and its [ official signature asset ](https://github.com/cuipengdba/agentsql/releases/tag/v0.6.1) has been released. v0.7.0 The isolation upgrade and rollback retest of the official package must be completed before release, and the results are subject to the GitHub Release text. Specific production deployments must independently verify backup and recovery in the target environment, and isolation drills cannot be regarded as customer environment results. The original v0.6.0 branch service has a startup defect and cannot be used as an available fallback target for this topology; do not let old programs read the migrated new schema.
