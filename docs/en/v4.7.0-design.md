# AgentSQL v4.7.0 data permission contract

> In development. The final supported scope is determined by the exact release commit, signed assets, and acceptance evidence.

## Scope

v4.7.0 extends the common data-permission enforcement chain of AgentSQL's independent Q&A agent and MCP Server security gateway. It covers active row and column rules for multiple explicitly listed users, nonempty group and item `white_list_user` fields, and role-qualified explicit user sets. The unmodified SQLBot Community v1.10.3 client is a protocol reference; current server identity, workspace, binding, and controlled gateway remain the authority.

An isolated black-box test of the original PostgreSQL preview found that group `user_list` membership triggered row and column limits. An `auth_target_id` without group users did not. Adding the member to a group or item allowlist did not exempt the member. Original disabled groups and items also behaved differently from AgentSQL drafts. These observations cover that preview route only. AgentSQL never treats the allowlist as a row or column bypass.

## Bounded active rules

- Group `user_list` is an explicit set of current workspace users, at most 100. With no explicit item target, the effective row and column rules apply to every listed user.
- A nonempty active group or item `white_list_user` may contain only users already listed in the group. It is encrypted metadata, returned through the original API shape and included in the policy revision. It never expands authorization or exempts a user from a rule.
- `auth_target_type=role` accepts only AgentSQL built-in workspace role ID `1` (workspace administrator, `weight=1`) or `2` (ordinary member, `weight=0`) with an explicit group user list. Current membership is checked for every listed user on activation and for the requester during execution. A new member of the role who is not listed is denied data access until the administrator updates and preflights the rule. A listed user's role change also closes. This is a **role-qualified explicit user set**, not automatic expansion of arbitrary original SQLBot role IDs.
- A single-user `auth_target_type=user` still requires the group's sole user to match the target. Explicit single-user items inside multi-user groups, unknown roles, out-of-group allowlist IDs, and rules that cannot be compiled safely remain rejected. Datasources continue to use operator-registered authorized gateway aliases.

## Per-entry security acceptance

On the final exact commit and signed package, verify row and column limits using a current authorized PostgreSQL synthetic table, local real model, matching ChatBI/Gateway binaries, and original clients across preview, Q&A page, MCP SDK, basic/advanced assistants, Type 4 embed, history, and CSV/Excel export. Cover two ordinary members, role changes, allowlist revisions, a new unlisted role member, disabled items/groups, revocation during model and gateway work, and storage/audit failures. Record HTTP status, returned SQL/data, controlled gateway audit, and query counts. A failure must not release stale SQL or results.

AgentSQL-created `enable=false` groups remain inert drafts. They cannot be used as a direct import of original permission records, where disabled groups still affected preview. A future import must explicitly convert or reject that difference; v4.7.0 makes no direct original permission-database migration claim. Other databases, arbitrary original role IDs, and unlisted client paths do not gain support through this version.

## Release gate

Release requires all five exact CI checks, independent public-key verification of 17 production-signed assets and the signed outer offline bundle, disconnected real-systemd fresh install/v4.6 upgrade/failure rollback on AMD64 and QEMU ARM64, anonymous GHCR pull, and public website/Demo smoke tests. The Demo's model is explicitly simulated. QEMU ARM64 is not physical ARM hardware. The user's real business system has not been validated; no 100% compatibility or zero-change cutover claim is made.
