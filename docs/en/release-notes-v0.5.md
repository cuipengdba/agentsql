### Known boundaries and non-commitments

- DM/Oracle parser only covers the v0.5 controlled SELECT profile listed in the document; `*` is only bound to the physical source table, the parser has no catalog, and cannot make up column-by-column names. This capability does not equal a full SQL grammar or access to the column-level authorization/masking pipeline.
- YashanDB's `NewYashanParser()` has been connected to the standard `NewParser` route; the three audits of narrow SELECT, column lineage, R010, mobile phone number masking and test fixture of the designated real database and independent client have been passed. HTTP/MCP, persistence audit and the combination of minimum privilege account and pipeline have not been tested. The NoSQL 21 registry is at the connection level, and the HBase registry default `16020` is not a ZooKeeper bootstrap port available for the current adapter.
- KingbaseES V9 green is limited to V9R1C10, PG mode, read-only controlled base closed loop of single-instance synthesis table. Actual license expiration date not confirmed (server only reports 180 days and date fields with unspecified meaning); V9 Oracle mode, native Kingbase driver, V8, multi-row data/deep paging, JOIN, aggregates/functions, complex expressions, type OID, system catalog, EXPLAIN, TLS/encryption, HA/failover, backup and recovery, B2 column-level authorization, multi-role concurrency, production load untested; explicit `GRANT CREATE SESSION` Grammar rejected, conversational ability verified by `LOGIN` + `CONNECT`. Commercial versions such as GaussDB and TDSQL still need to be finalized in the target environment. HighGo 9.0.10 Enterprise Edition only turns green within the limits of the above table, and continues to fail to close at untested boundaries.
- The R005 production dynamic alarm has closed the loop, but the capability boundaries must still be accurately stated: pre-execution hits for unbounded queries rely on controlled EXPLAIN; the actual `row_limit` truncation will supplement `R005` in the universal execution and PostgreSQL column-level authorization paths. Responses return structured hits via `assessment.hits`, persistent audits are saved via `rule_hits`; unknown EXPLAIN or audit facts continue to fail-closed. `row_limit` can be configured in the data source management portal, and the default value is 1000; the rules page does not provide an independent R005 threshold editor.
- RBAC is still the MVP: console business metadata has been isolated by tenant, TOTP MFA, OIDC and LDAP/AD have been delivered, but login rate limiting and locking, and the production compatibility matrix of external identity systems are still follow-up boundaries; the Agent tenant propagation of the MCP execution data path has not yet been completed. Management-side local and external user token reuse, persistent server-side revocation and refresh token rotation: refresh tokens are only stored in SHA-256 hash and rotated every time they are refreshed. Reusing rotated/revoked tokens will revoke the entire refresh family; when the status is unreadable, access verification, refresh and logout are all fail-closed.
- MCP transport session is not saved across processes, and old sessions before service restart cannot be restored seamlessly; persistent SSE disconnection replay and `Mcp-Session-Expired: 1` → re-initialize path after restart have been provided. Doubao and Claude Desktop/Inspector real clients are still waiting for joint debugging between accounts and specified versions.
- "Protocol Path Measurement" does not cover the full SQL dialect, production topology, HA/failover, TLS/authentication matrix, performance SLAs, or vendor support responsibilities.

- Caliber: `TestParseProjectionLineageP99Budget/postgres` measures complete `Parser.Parse`, typical SQL is 8 `UNION ALL` branches, 8 columns per branch, 2,000 samples per round; includes `pg_query`, JSON AST decoding, Normalize pre-scan and lineage post-processing, and does not include the closure DML execution link.

- Root cause: Typical SQL has no literal, and `pg_query.Normalize` will not actually be executed; before optimization, a total of 4 `pg_query` front-end calls are executed each time, including sentence splitting, ParseToJSON, Normalize pre-scan and comment scan. In the CPU profile, the total of two Scans is about 20.1%, the two JSON decodings are about 30.2%, the lineage is about 10.3%, the CGO flattening time is about 18.5%, and there is no independent type inference stage.

The existing `set_arms_8` (8 branches, 1 column per branch) benchmark improved from 720,686–756,478 ns/op, 110,278–110,279 B/op, 1,255 allocs/op to 495,068–544,081 ns/op, 86,421 B/op, 1,139 allocs/op.
- Conclusion: The final 5 rounds of P50 were 1.702–1.861 ms, P90 was 3.146–3.289 ms, but P99 was 5.576/4.906/4.744/5.485/5.643 ms, and only 2/5 passed. The main body latency is reduced by approximately 27%–33%, and the tail is still affected by C parser/scan, JSON mass allocation, and GC/scheduling; the 5 ms release day gate is retained and is not relaxed or marked as up to standard.
- All the function packages of the full warehouse parallel `go test -short ./... -count=1` passed, but the performance gate failed due to CPU competition (19.518/12.546 ms for MySQL/PostgreSQL P99), so the command was overall FAIL; the release judgment still only uses an exclusive rerun without parallel load, and the full warehouse result cannot be recorded as passed.
