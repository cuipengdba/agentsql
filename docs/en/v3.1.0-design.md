# AgentSQL v3.1.0 design: SQLBot business integration

**Language:** [Simplified Chinese](../v3.1.0-design.md) | [English](v3.1.0-design.md)

Status: implementation and acceptance in progress. The acceptance record determines the released scope.

## User outcome

Administrators map SQLBot workspaces, datasources and people to AgentSQL, then use an actual model for natural-language questions, masked tables and selected charts. Rejections provide actionable diagnostics and request references. Users explicitly submit and resume requests requiring approval.

## Required delivery

- Pin SQLBot v1.10.2 source and image baselines; reject installation when a version or file hash differs.
- Complete PostgreSQL business flows without promoting database support levels. MySQL integration belongs to v3.2.0.
- Tenant-scoped mapping management, configuration export, diagnostics, disabling, deletion and connector credential rotation, with Chinese and English UI.
- Map each SQLBot user to an existing AgentSQL person and read-only Agent. Issue short-lived, purpose-scoped identity tokens and check live bindings, user permissions and Agent state on every request.
- Filter table and field metadata through the current user's gateway permissions before it enters model context. Never fall back to direct database access.
- Do not automatically rewrite or retry SQL after security rejection. Users explicitly request read-only approval; approved execution retains the original person, Agent, datasource and sealed SQL, with a single execution claim.
- Deliver the complete PostgreSQL approval flow only with B2 explicitly disabled. With B2 column authorization enabled, approval requests must fail closed and must never downgrade authorization automatically.
- Acceptance with a real model, real SQLBot and real PostgreSQL synthetic data, including cross-workspace/user attempts, revocation, audit failure, credential rotation and approval replay.

## Trust and execution

```text
SQLBot ordinary signed-in user
  → server-authenticated current_user, explicitly propagated across LLM threads
  → exact local workspace / datasource / user binding
  → dedicated connector credential calls AgentSQL resolve
  → current binding + live user RBAC + current read-only Agent
  → two-minute purpose-scoped SQLBot identity token
  → Agent Key + user token + current binding revision checked per request
  → controlled reads / read-only approvals on the specified PostgreSQL datasource
  → existing authorization, masking and durable audit
  → SQLBot table or a verified chart
```

The connector credential authorizes the trusted SQLBot server to represent the external user in that binding. Creating, editing or rotating a binding requires policy, user and datasource management permissions. A browser or model cannot self-assert the external user ID. Embedded assistant and ask-token paths are outside this release's user-level acceptance scope.

Integration tokens use a separate signing purpose, do not fabricate console login sessions and cannot authenticate management API calls. Binding edits and connector rotation increment the revision and invalidate issued tokens on subsequent requests. Agent Keys retain the existing Agent credential lifecycle and remain in SQLBot server environment variables; exported configuration contains variable names only. Revoking the Agent Key stops all access by that Agent.

Scoped tokens can call only reading, schema discovery and read-only approval tools. They cannot access B5, write tools, other datasources or SSE replay. MCP transport sessions also bind the mapping ID and revision. The configured schema filters discovery; existing policies and the execution pipeline remain authoritative for SQL object access.

## Storage and upgrades

Add tenant-scoped `sqlbot_bindings` metadata and transactional management audit. Store only connector credential digests, never SQLBot passwords, model secrets or plaintext Agent Keys. Combined schema moves from 23 to 24, separate metadata from 22 to 23, and audit remains 6. Back up metadata, audit, configuration and keys before upgrading. Rollback restores the matched backup; an older binary must not open the newer schema directly.

## Release gates

1. Management permissions, tenant isolation, validation, secret handling and stale-revision tests pass.
2. Ordinary requests, model workers, metadata and approvals carry the same verified SQLBot user. Missing context fails closed.
3. A real model generates SQL from natural language, followed by gateway execution, masking and a selected chart. Fixed-SQL simulated services do not qualify.
4. Legacy v1 adapter configuration remains covered, with its original workspace-level boundary documented.
5. Fresh installation, v3.0.2 upgrade, combined/separate stores and backup recovery pass, along with Go, Web, Python, documentation and commit-specific CI checks.
6. Publish only after signed dual-architecture assets, images, website, Demo and public smoke tests pass.

Customer pilots are scheduled after the user supplies an actual customer and authorization. Only v3.1.0 is being implemented.
