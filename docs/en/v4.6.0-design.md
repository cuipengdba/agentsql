# AgentSQL v4.6.0 Design and Acceptance Contract

> This is a development-branch contract. Only exact-commit acceptance evidence and the formal release notes define support.

## Scope

v4.6.0 adds SQLBot Community v1.10.3 Type 1 advanced assistants and split third-party frontend/backend integration to AgentSQL's independent Q&A and MCP Server security gateway. The unchanged original assistant client is the target. An external catalog supplies display names and IDs only; operator-registered AgentSQL gateway aliases own all database connections and execution.

Active role, multiple-user, and nonempty-allowlist rules remain in v4.7.0. Remaining Community pages/APIs and arbitrary connection creation/editing remain in v4.8.0.

## Observed protocol and trust boundary

An isolated black-box probe of the pinned `dataease/sqlbot:v1.10.3` image confirmed Type 1 configuration CRUD. The unchanged `assistant.js` obtains a virtual assistant token through the public-key and `/system/assistant/info/{id}` bootstrap, then requests the default model and `/system/assistant/ds`. The browser receives `certificate` in a host message and sends `btoa(encodeURIComponent(certificate))` as `X-SQLBOT-ASSISTANT-CERTIFICATE`. With no host credential, the original catalog request fails. The public-key bootstrap signature is not proof of an end user's identity. This original-product probe is not AgentSQL acceptance.

AgentSQL must treat the bootstrap token as application and origin context without data authority. A request gains data authority only when the host credential matches an operator-registered catalog endpoint and credential fingerprint, a real active non-admin user and workspace, and external-ID-to-current-gateway-alias mappings. Origin checks supplement, rather than replace, that credential. Every data path and asynchronous response must recheck identity, app and catalog revisions, binding, and table/column/row policy. Failed checks cannot expose prior SQL, data, history, or exports. Database credentials in the catalog response must never become connection configuration. HTTPS requires chain, hostname, and pinned leaf-certificate verification. Plain HTTP needs explicit isolated-test approval.

The operator's private `assistant_catalogs` registration names the Type 1 application ID in `assistant`. Its `configuration.endpoint` must exactly match the registered endpoint. Bootstrap issuance fails if registration is absent or more than one active registration exists. The public bootstrap token cannot call data routes by itself; the original host certificate string only selects an HMAC-keyed private registration. The catalog's external ID is mapped to an existing authorized local gateway alias before it reaches the browser, and all catalog connection parameters are discarded. Removing an entry affects the next catalog refresh; **immediate revocation requires disabling the registration, application, user, or gateway binding**, which is rechecked during execution and before release.

## Production deployment boundary

The offline package includes a separate `agentsql-chatbi-assistant.service` for Type 1, disabled by default. It shares the main service's encrypted store, secret, model, and controlled gateway configuration, but serves only the assistant iframe and scoped API on `127.0.0.1:8002`; administrative login and APIs are unavailable there. After installation, the operator registers a real non-admin user, workspace, authorized local datasource aliases, Type 1 application, and private `assistant_catalogs` mappings before explicitly starting this service. A reverse proxy must place the assistant listener on a different HTTPS browser origin from the admin site, restrict upstream paths to this listener, and provide TLS. The loopback port must not be exposed directly. An upgrade preserves an enabled service's state and checks its health; failure rollback restores its unit and service state.

The host site sends the certificate message under the original protocol. The certificate identifies only a privately registered catalog credential; database hosts, usernames, or passwords supplied by the browser cannot create an AgentSQL connection. Production catalog endpoints require HTTPS, an allowed network range, and a pinned leaf-certificate SHA-256. `allow_http` is for explicitly isolated tests only. Disabling the private registration is an immediate Type 1 revocation operation; removing an individual catalog entry takes effect on the next refresh and must not be presented as immediate revocation.

First install and configure the local model, an ordinary member, and that member's existing gateway binding using the [native Q&A guide](CHATBI.md). Create a Type 1 application in administration and record its ID. Keep the private registration file in a restricted operations directory. The certificate and external catalog authorization must match exactly. `datasource` is an **existing** AgentSQL gateway alias, not an external database connection. Replace the endpoint, certificate pin, network range, and IDs with real values in this field example:

```json
{
  "assistant_catalogs": [{
    "assistant": "123", "endpoint": "https://catalog.example.invalid/v1/sources",
    "authorization": "[{\"key\":\"X-Catalog-Token\",\"value\":\"REPLACE_PRIVATE_TOKEN\",\"target\":\"header\"}]",
    "workspace": "1", "user": "456",
    "sources": [{"catalog_id": "81", "datasource": "10"}],
    "allowed_cidrs": ["203.0.113.15/32"], "tls_cert_sha256": "REPLACE_WITH_64_HEX_DIGITS"
  }]
}
```

```sh
agentsql chatbi configure --config /etc/agentsql/chatbi.yaml --from /root/assistant-catalog.private.json
sudo systemctl enable --now agentsql-chatbi-assistant
sudo systemctl is-active agentsql-chatbi-assistant
```

Point the reverse proxy at local `127.0.0.1:8002` on a different HTTPS hostname from administration. The host page loads the original `assistant.js` and passes the same private certificate under its original message protocol. Verify catalog selection, Q&A, audit, and revocation against an authorized synthetic database before using real data. Back up `/etc/agentsql` and `/var/lib/agentsql` before upgrade, and verify the signed package and rollback procedure from the formal release notes.

## Delivery sequence

1. Record the original Type 1 browser wire protocol, host messages, and catalog response shape.
2. Add a short-lived, data-free Type 1 bootstrap token and host-credential validation; absent credentials allow only nonsensitive bootstrap responses.
3. Bind each Type 1 app to an operator catalog and real user. Map catalog IDs to currently authorized gateway aliases at the boundary; use existing controlled ChatBI execution, model leases, and durable audit.
4. On the same exact commit, accept the unchanged client with a synthetic catalog, real local model and database. Test wrong credentials, forged origins, catalog changes, user/alias/row/column revocation, model/database/audit/storage faults, history and exports. Record CPU, memory, and cold/warm first-question times without an SLA claim.
5. Require all five CI checks, exact-commit production build and signatures independently verified with the trusted public key, plus offline real-systemd fresh install, v4.5 upgrade, and injected-failure rollback on AMD64 and QEMU ARM64. Then publish GitHub Release, GHCR, website, and clearly simulated Demo; anonymously download and smoke-test the public result.

## Release language

State only the app types, catalog shape, model, database, entry points, and architectures actually verified. QEMU ARM64 is not physical ARM hardware. This release has not been validated in the user's real business system; do not claim 100% compatibility or zero-change migration.
