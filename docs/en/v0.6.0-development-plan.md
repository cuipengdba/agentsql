# v0.6.0 Development and Acceptance Plan

**Language:** [English](v0.6.0-development-plan.md) | [Simplified Chinese](../v0.6.0-development-plan.md)

Status: Candidate for acceptance (2026-10-14). This document describes goals and acceptance thresholds and does not imply that the functionality has been released or certified by the manufacturer.

The current working tree `feature/v0.6.0` already has user/role/tenant console and access wizard, management API unauthorized protection, [ normal SQL approval single execution ](v0.6.0-approval-contract.md), and verified [ restricted read-only adaptation ](vastbase-g100-v060.md)'s driver, pipeline and MCP in a real G100 Build 9 PG mode instance. The v0.6.0 version number, documentation and official website static candidates are ready; public release must still pass all acceptance thresholds.

## target scenario

The enterprise administrator connects an AI assistant to the existing database: creates data sources and agents, grants minimum query permissions, initiates MCP queries in Dify, confirms masking and traceable auditing. Alternatively, use the MCP Inspector graphical interface to directly call the same tool to inspect protocols, rejects and audits. Administrators can manage human users, roles, and tenants in the console, and approval operations have clear execution semantics.

v0.5.1 already has PostgreSQL/MySQL master, MCP stdio/HTTP, policy and auditing, and human user/role/tenant APIs. v0.6.0 The number of registered data sources, PG protocol compatibility, or approval records cannot be mistaken for complete production support for all databases.

## Delivery order and passing conditions

1. **Governance console and backend authorization**: Users and roles can be created and edited within the visible tenant; the initial administrator can manage the tenant; the caller cannot obtain permissions that the caller does not have through role assignment or inheritance; cross-tenant access to the management API is still denied. Front-end construction and API regression passed.
2. **First time access wizard**: Press Data Source → Agent → Minimum Permission → MCP Client → Audit Guide to display the real configuration status and failure handling, and does not claim that the demonstration platform replaces the real client. Both empty instances and configured instances must be passed through.
3. **Approval execution closed loop**: The approval object is bound to the tenant, Agent, data source configuration summary, standardized SQL/original text and application reason, with expiration time and single consumption status. Currently, ordinary SQL MCP tools do not have parameter arrays, and parameterized approval is designed separately. Re-check identities, permissions, rules and database connections during execution; reject substitutions, expirations, duplications and dependency failures; the final state of controlled execution and audit placement can be traced. The semantics of ordinary approval and B5 approval are verified separately.
4. **Vastbase G100**: Select a clear product/version and PG compatibility mode, add independent `db_type` and bounded read-only adaptation. Use the target instance to verify connection, discovery, parameter binding, table authorization, masking, persistent auditing, write/DDL/malformed SQL/timeout/broken database rejection. If there is no target instance and license, it can only be marked as "Under implementation, not accepted by the real database".
5. **client and upgrade**: Dify and MCP Inspector each complete a real tool call, rejection and audit association; upgrade and rollback from v0.5.1, retaining metadata and keys; release candidate builds, installation packages, images and documents are consistent. The user agreed on 2026-10-14 to replace Claude Desktop with Inspector that does not require an account as the acceptance target of this version; Claude Desktop UI compatibility still needs to be verified with accounts and real environments.

Dameng DM8, KingbaseES KingbaseES's multi-row/JOIN/exception branch extensions are enhancements of this version; the YashanDB independent client's verification of HTTP/MCP depends on the resource. Do not expand the scope of support when there is no genuine evidence. The real customer pilot waits for users to find customers before scheduling.

## Release threshold

- Critical security use cases have evidence of "request rejection with no side effects to the database" and execution and audit records can be correlated.
- The real database report states the product, version, mode, driver, account permissions, topology, data set and untested items; ordinary PostgreSQL cannot replace Vastbase acceptance.
- Go and web tests, front-end embedded products, installation and upgrade rollbacks, and two actual MCP clients all passed.
- README, support matrix, changelog, version numbers, website, and release assets are consistent at the time of official release.
