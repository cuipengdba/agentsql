# AgentSQL v4.13.0 candidate acceptance and release limits

**Languages:** [Chinese](../v4.13.0-acceptance.md) | [English](v4.13.0-acceptance.md)

This records project self-tests of one exact production-signed candidate, not third-party certification. Public downloads, accepted image digests, website and explicitly simulated-model Demo checks are recorded in the [v4.13.0 Release](https://github.com/cuipengdba/agentsql/releases/tag/v4.13.0). Candidate acceptance does not by itself complete public delivery.

AgentSQL combines an independent AI data Q&A agent with an independent MCP Server security gateway. This version improves projections of currently authorized results. SQLBot is an optional client, not a native Q&A runtime dependency.

## Real model, gateway and database

- The same final signed ELF runs ChatBI and Gateway with fixed real ONNX, actual Qwen3-4B and PostgreSQL **17.11**. The fixture has 128 explicitly authorized synthetic tables; these questions explicitly name the three-row `public.systemvar_rows` table.
- ChatBI 2 CPU / 4 GiB, Gateway 2 CPU / 2 GiB, PostgreSQL 2 CPU / 2 GiB, Qwen 4 CPU / 8 GiB. Metadata and audit use native Linux ext4 on a task-owned D-drive SSD virtual disk. Service and fault-injection tools are verified to access the same database inodes.

## Results and security behavior

The original client actually expands both measures into six plotting records with two legend entries; its default column presentation is stacked. The native UI draws six grouped bars. Both clients show two line series and six points. Native table, column, horizontal-bar, line and valid one-measure pie selections use the current result without a new controlled query. Reopening reauthorizes and requeries through the gateway, restoring the question-selected default.

Real Qwen/PostgreSQL cases cover all-zero values, a positive pie, a negative pie falling back to a table and HTML-looking labels rendered as text. **The current gateway represents SQL NULL and empty database strings as empty strings. Such unprovable numeric fields conservatively stay in a table, never zero. Typed JSON-null line gaps have deterministic renderer coverage only; this real gateway positive path is not claimed.** An initial fixture incorrectly expected a line; that failed assertion remains recorded, followed by raw-table and missing-cell checks under the actual data contract.

Plots use at most the first 20 authorized result rows and four measures. Strict numeric/precision boundaries, untrusted labels, excessive selections and typed missing-point handling also have deterministic tests. Real integration demonstrates two measures, not arbitrary charts or scripts.

The final package passes:

- A newly active rule redacts old history SQL/data; the record-data route returns `200` with `data:null`, while CSV/XLSX return `404`. The old native chart disappears without another data query. A new question sees east only and both correct measures.
- Both browser clients reopen history before/after a service restart; actual CSV/XLSX files parse to three original rows, with formula-looking strings kept literal.
- Rule changes during export-receipt commit, receipt-write failures and gateway audit-write failures release no file; recovery restores valid downloads. No visible columns, disabled membership, cross-user/workspace access, in-flight deletion and binding retirement remain closed.
- Real follow-up Q&A retains the previous west filter. Original Python SDK nonstreaming/streaming questions and invalid-token refusal pass. Basic and Type 4 original-browser embeds pass real Q&A and revocation. Model interruption releases no result or new data query; recovery answers correctly.
- After binding retirement and a ChatBI restart, fresh login still cannot read old history/files or continue the old conversation; no new gateway query occurs.

Automation initially encountered a CDP event-stream-body limitation, missing asynchronous waits, duplicate history names and an incorrect legacy status-code expectation. Failures and corrected reruns remain separate. Original-client requests, responses and data were not rewritten to obtain a pass.

## Offline installation, upgrade and rollback

AMD64 and QEMU ARM64 Debian 12 PID1-systemd containers with `--network none` each pass signed-package installation, upgrade from formal v4.12 and healthy rollback after injected first-start failure: **6/6**. Checks include both main units active/enabled, the separate assistant disabled by default and then enableable, versions/health, model hash, SQLite marker/integrity and old-file hashes after rollback. **QEMU is not physical ARM hardware.**

Initial tests on the Docker H-drive overlay hit a 30-second OpenSSL timeout and an old-service audit-commit timeout; neither counts as a pass. A new task-only D SSD virtual disk with native ext4 then hosted complete fresh-container reruns of all six cases, with signature/audit/query deadlines unchanged. Docker/WSL and other services were not restarted.

## Container delivery method

Images package independently verified production-native ELF/CLI/Yashan-library bytes on a fixed Debian runtime with the repository Dockerfile's user, permissions, configuration, entrypoint and health settings. [Actual recipe](../assets/release-v4.13.0/Dockerfile.signed-native) SHA-256: `58e24578a358169a2cd500a3f6d4dabcfa146918b65a871f1fa5f1455016941c`. This avoids duplicate ARM Go compilation; it is not a claimed successful fresh source build through the root Dockerfile. Published images must also be anonymously pulled for both architectures, compared with signed native ELF/CLI bytes and checked in real containers. Accepted digests and post-publication checks are in the Release.
