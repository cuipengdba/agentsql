# AgentSQL v2.7.0 Design: ClickHouse Query Management

**Language:** [English](v2.7.0-design.md) | [Simplified Chinese](../v2.7.0-design.md)

Status: Implementing. The target instance is ClickHouse 26.8.31.2 LTS, single node native TLS port. This design does not claim full production support for ClickHouse.

## User tasks and boundaries

The AI ​​assistant needs to read a small number of columns from the authorized analysis table, and each read is subject to Agent identity, table/column authorization, database least privileges, resource budget, masking, and persistent auditing. The existing ClickHouse adapter only provides administrator native command preview and cannot be used as a query entry for Agent MCP.

| Delivery path | constraint |
| --- | --- |
| MCP `query_analytics` | Enter data source ID, a single table in the current database, 1–16 explicit columns, 1–8 string equality conditions, 1–100 row limit; no SQL text is accepted. Exact table authorization and explicit column authorization are required, and filtering columns must also be authorized. |
| Compatible with old configurations | Existing ClickHouse management previews still register with 9000 as the default port; new controlled query configurations pre-populate native TLS port 9440 in the console. The old plaintext configuration does not gain Agent query capabilities. |
| Database execution | Creates a new strict TLS, authenticated, read-only connection using the current data source configuration; only allowed instance versions and MergeTree single tables are specified. After verifying the table engine and column type, the server constructs a parameterized SELECT; rejects views, distributed, dictionaries, table functions, JOIN, aggregation, writing and cross-database access. Roles should have limits of at least `readonly=1`, execution time, read lines/bytes, memory, output lines, and threads. A single request from the gateway can take up to 2 seconds, and the return value can be up to 1 MiB. |
| safety chain | Re-verify the ownership of Agent/tenant and data source, and parse the current policy one by one; access ClickHouse only after the persistent preflight audit is successful. The number of result columns and rows is strictly verified and masked by source column; the results are delivered only after the final state audit is successful. Failure or cancellation records an error final state, and fails to close when auditing is unavailable. |
| Client and Delivery | MCP Inspector, Dify MCPClient true allow/deny calls; upgrade and paired recovery from v2.6.0 official package; CI, dual-architecture signature, GHCR, official website and Live Demo item-by-item acceptance. The public network Demo maintains the synthetic PostgreSQL scenario. |

Call chain: `HTTP MCP 身份 → Agent/租户 → 数据源 → 精确表/列策略 → 输入校验 → 持久预检审计 → TLS/只读角色/元数据 → 参数化有界 SELECT → 结果结构和资源上限 → 脱敏 → 持久终态审计 → MCP 响应`.

Negative use cases include cross-agent/tenant, revocation, broad authorization, unauthorized projection/filtering columns, SQL/identifier injection, view and distributed engine, dangerous functions, account writing, wrong certificates, read timeout/cancellation, business database failure, preflight/final state audit failure, and return structure exception. All tests use only synthetic data; no target versions or standalone passes are extrapolated to clustered, replicated, high-concurrency, and production workloads.

Reference: [ClickHouse Go driver ](https://clickhouse.com/integrations/go), [Agentic Analytics roles and read-only settings ](https://clickhouse.com/blog/how-to-set-up-clickhouse-for-agentic-analytics), [ClickHouse TLS configuration ](https://github.com/ClickHouse/clickhouse-docs/blob/main/docs/guides/sre/tls/configuring-tls.md).
