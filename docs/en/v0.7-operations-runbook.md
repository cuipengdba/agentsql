# v0.7 Operation and Maintenance Fault Location Manual

**Language:** [English](v0.7-operations-runbook.md) | [Simplified Chinese](../v0.7-operations-runbook.md)


> Historical archive: This file records the operation and maintenance process of v0.7 at that time. For daily operation and maintenance of current v3.0.x, please use [ current operation and maintenance manual ](OPERATIONS.md).
This article applies to the local acceptance of v0.7.0, as well as post-deployment control plane upgrade, MCP access and audit dependency failures. All checks should be performed in authorized testing or maintenance windows; record command exit codes, time, actual submission and deployment topology, and do not paste API Key, DSN, SQL original text or database password in work orders or logs. The issued assets and online results should be checked in the GitHub Release text and release evidence according to the gates listed in [ acceptance record ](v0.7-acceptance.md).

## Migration preflight failed

First stop writing to the old instance and back up metadata, audit storage and its paired `AGENTSQL_SECRET`. Run with the same configuration and environment variables as the service:

```bash
agentsqlctl migrate --check --config /etc/agentsql/config.yaml
```

| exit code | meaning | Process |
| --- | --- | --- |
| 0 | All configured migration flows are `current` | Check the output for `role`, `driver`, `current` and `latest` and continue with the pre-boot check. |
| 2 | At least one migration flow is `pending` | Keep the new instance stopped, explicitly execute `agentsqlctl migrate` as migration owner, and rerun the preflight. |
| 1 | Configuration, connection, version history, or output errors | Pinpoint specific errors. Don't start it as "pending migration". |

Merged storage only outputs one metadata line; sub-database deployment must see both metadata and audit lines. When the SQLite path does not exist or the file exists but does not have `schema_migrations`, preflight will not create the library table; the first installation requires explicit migration first. If the database version is higher than the current binary, the version history is discontinuous, or only one of the two databases is successfully migrated, the service should be kept stopped and processed according to the backup and recovery plan. Do not just replace the old binary and try to downgrade.

Check `/healthz` and `/readyz` respectively after startup. The former can only prove that the process is alive; the latter needs to check the metadata/audit connection and B2/B5/masking status when returning 503. The rollback should restore the pre-upgrade paired database backups, corresponding keys, and legacy programs; there is no automatic down migration of the project. For complete permissions and backup steps, see [ Deployment Guide ](DEPLOY.md).

## Audit timed out or unavailable

If the MCP tool returns `AUDIT_UNAVAILABLE`, `AUDIT_OVERLOADED`, or `/readyz` returns 503, first record the request time, audit ID (if any), error code, error stage, and deployment instance, and then check the audit storage connection, disk space, number of database connections, and write latency. Do not turn off auditing or expand permissions to recover requests when the audit library is unavailable; the gateway will reject the results according to the failure shutdown contract.

For requests that have submitted write operations and returned `COMMIT_OUTCOME_UNKNOWN`, **should not automatically retry**. First check the actual status of the business database and audit records before deciding on manual remediation. Ordinary read-only requests can be retried with a new request ID after dependency recovery; confirm that the original request is not still running before retrying.

After dependencies are restored, initiate a read-only request that is allowed and a request that should be denied from the least privilege test Agent, verifying response decisions, tenants, agents, data sources, and persistent auditing. Just looking at `/healthz` or database pings is not enough to prove audit link recovery.

## MCP protocol rejected

First confirm the path and protocol used by the client:

| path | Agreements and Behavior | Common troubleshooting points |
| --- | --- | --- |
| `/mcp` | Existing stateful Streamable HTTP; retains session ID after client initialization | Subsequent requests carry `Mcp-Session-Id`, the Agent Bearer, and the negotiated `MCP-Protocol-Version`. |
| `/mcp/2026-07-28` | New version of stateless paths; independent authentication for each request | Each POST carries Agent Bearer, `MCP-Protocol-Version: 2026-07-28`, `Mcp-Method`, `Mcp-Name` when applicable, and declares the same version agreement in `params._meta`. |

Missing, duplicate, or mismatched protocol metadata for the new version of the path will return HTTP 400 before the tool is called; cross-origin requests will be rejected. Version mismatch of the old path returns `MCP_PROTOCOL_UNSUPPORTED` according to the existing JSON-RPC contract. `401` First check the Agent Key status and validity period; `429` means that the Agent has reached the current limit and should not be bypassed by changing the path. Do not use the administrator login token as the Agent Key, and do not let the client silently roll back between the two paths.

After the investigation is completed, use the same Agent to perform tool discovery, allow query, unauthorized denial and audit verification on the actual target client. The SDK or native HTTP single test is not equal to the actual test of clients such as Dify and Inspector. For specific request examples, see [MCP Access Guide ](INTEGRATIONS.md).
