# AgentSQL v3.2.0 Design: Controlled Analytics and Column Authorization

**Language / 语言:** [English](v3.2.0-design.md) | [简体中文](../v3.2.0-design.md)

Status: in development. These are delivery targets, not verified support claims.

## User problem and scope

The v3.1.0 personal SQLBot integration covers PostgreSQL only. A read-approval request fails closed when PostgreSQL B2 column authorization is enabled. v3.2.0 aims to combine these paths without weakening identity, permission, masking or durable audit controls, and to extend the same personal boundary to a specified MySQL read-only scenario.

| Deliverable | Design constraint | Acceptance evidence |
| --- | --- | --- |
| PostgreSQL B2 with read approval | A request seals the SQL, person, Agent, datasource and expiry without reading business data. Execution repeats a fresh B2 snapshot, database object binding, plan limits, masking and durable audit. Neither requesting nor approving bypasses column authorization. | No business read before approval; an authorized column succeeds after approval; an unauthorized column fails. Policy change, person revocation, B2 lease loss, audit failure and replay all fail closed. |
| SQLBot MySQL | Pin SQLBot v1.10.2. Map the server-authenticated user to one specified MySQL datasource and a dedicated read-only Agent. Use the actual dialect for SQL classification, schema discovery and result handling. Reject self-reported identity and direct database fallback. | Real SQLBot, model and specified MySQL version produce a business table and supported numeric chart; cross-user/source, mixed read/write and side-effecting functions are rejected. |
| PostgreSQL/MySQL permission depth | Define provable column boundaries for joins, subqueries, wildcards, expressions, aggregation and views. Parser acceptance does not replace database binding proof. | Negative cases, live object changes and narrowed privileges are retested; syntax without proof is rejected explicitly. |
| Policy impact preview | Show affected Agents, datasources, objects and authorized columns in a read-only management preview tied to the current policy revision. Mark uncertain impact rather than asserting certainty. | Tenant isolation, stale-preview invalidation, and no policy write or business-row access. |
| Derived-result protection | Derived expressions, filtering and ordering based on restricted columns require underlying authorization proof. Charts, export and cache must not reintroduce unmasked values. | Restricted derivations are rejected or bounded and masked; charts and errors expose no raw value; audit failure withholds the result. |

## Security path

```text
Signed-in SQLBot user → server identity context → exact tenant binding and revision
  → short-lived person token + independent read-only Agent Key → MCP datasource scope
  → current person permissions, Agent, policy and database object binding
  → B2 snapshot / specified MySQL authorization → read-only query
  → masking → durable audit → result

Read approval: original user request → sealed SQL/identity/source and request audit
  → administrator approval → one claim by original user
  → rerun the entire live security path → execution and linked audit
```

The request may say “accepted, to be validated again at execution”; it must not claim that B2 binding has already passed. If any stage cannot prove the current user, authorized columns, read-only behavior, audit or execution outcome, it stops and records failure. It never falls back to the old table-only path.

## Upgrade and support boundary

Reuse the existing binding and approval tables where possible. If fields or revisions change, rehearse upgrades and paired recovery for combined SQLite/PostgreSQL and split metadata/audit topologies. Database support remains tied to a specified version, driver, TLS mode, topology and tested scenarios. One synthetic MySQL or PostgreSQL instance does not establish full production support.

The release requires Go/Web/Python tests, real SQLBot and both real databases, revocation and audit negative cases, upgrade/recovery from the prior release, green CI for the release commit, signed dual-architecture assets, GHCR, website and public Demo acceptance.
