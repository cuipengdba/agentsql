# v1.7.0 Dameng and KingbaseES deployment boundary deepening: design and verification threshold

**Language:** [English](v1.7.0-dm-kingbase-depth-design.md) | [Simplified Chinese](../v1.7.0-dm-kingbase-depth-design.md)

Status: Under development. This document corresponds to the Dameng and KingbaseES goals of v1.7.0 in the identified v1.6.0–v3.0.0 roadmap. The HighGo specified instance adaptation that has been merged into the main branch is an additional capability and does not replace the acceptance threshold of this document.

## Secure connection

| Database path | current facts | The threshold for improving this ability |
| --- | --- | --- |
| Dameng DM8 Pack3, native Go driver | The existing TLS handshake for `github.com/godoes/gorm-dameng/dm8` calls `security.NewTLSFromTCP`, which implementation sets `InsecureSkipVerify: true`; AgentSQL currently rejects explicit TLS options. The manufacturer's documentation distinguishes between encryption only, one-way authentication and two-way authentication. | Find a driver or wiring method with clear license and redistribution conditions that can actually verify the identity of the server; use the specified authentic library to prove that the correct certificate passed, incorrect CA/hostname rejection, and recovery after rotation. The Dameng TLS option is not enabled before completion, and the secure connection is not declared to be passed. |
| KingbaseES KingbaseES V9R1C10, PG mode | The specified instance is currently connected via the `postgres` protocol path; the KingbaseES official manual supports `sslmode=verify-ca` / `verify-full` and server certificate configuration. | Enable SSL on the isolated instance, use the root of trust and exact hostname to do authentic database lookups, reject incorrect roots/hostnames, rotate certificates and review new connections to the connection pool; check authorization, masking and auditing on the AgentSQL MCP link. |

## Query and permissions

Only expand the SELECT subset that is certified by both the vendor's real database and the controlled parser. Every paging, JOIN, expression, and metadata read must have object authorization, column origin, masking, negative syntax, and least privilege account evidence. Expressions that do not complete column source certification remain rejected; KingbaseES shall not automatically inherit full PostgreSQL B2/B5 capabilities because it adopts the PG protocol.

## Failover and load

The active and standby acceptance needs to be carried out in an independent test topology, recording the version, license, synchronization method, switch command, client reconnection, request final status and audit ID. Timeouts, cancellations, and undetermined execution final states during switching do not deliver partial results. Stopping/restarting a single instance can only prove fault recovery and cannot replace the acceptance of the active and standby instances. Multi-Agent read-only workloads give concurrency count, query shape, duration, P50/P95/P99 latency, error rate, CPU/memory, and audit backlog; this data only describes the test machine and does not extrapolate to production capacity.

## Publishing rules

This version first delivers `verify-full`, certificate rotation and account password rotation that have been proven in the KingbaseES V9R1C10 PG mode real database, and retains the incorporated HighGo limited read-only capability. Dameng can verify that TLS and the formal active-standby switching between the two databases require driver and licensing/topology conditions, and the acceptance is postponed and remains "unverified"; its support level will not be upgraded with this version number. The final Release, support matrix, official website and Demo of v1.7.0 can only contain accurate versions and topologies that have passed actual testing. Each version still needs to complete CI, upgrade recovery, dual-architecture signature assets, GHCR anonymous pull and public network smoke testing.
