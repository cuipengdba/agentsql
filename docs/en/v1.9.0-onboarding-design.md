# AgentSQL v1.9.0 access experience design

**Language:** [English](v1.9.0-onboarding-design.md) | [Simplified Chinese](../v1.9.0-onboarding-design.md)

Status: Design finalized, not yet released. The target user is an administrator connecting Dify self-hosted or MCP Inspector to AgentSQL for the first time. The current console already has data source/Agent/policy count, connection pre-check, independent SQL policy pre-check and error code description; however, the client configuration is scattered in the document. After selecting the Agent and data source, the target SQL cannot be interpreted in the same process and the corresponding audit can be found. v1.9.0 solves this period of access work without changing the authorization conclusion of the gateway.

## User tasks and expected results

1. The administrator selects the agent and data source of this tenant and completes status, connection, and policy existence checks.
2. Select Dify 1.17.1 or MCP Inspector 0.16.8, fill in the AgentSQL root address reachable by the client, and copy the URL/request header description without the real key. Dify uses `/mcp` and explicit `MCP-Protocol-Version: 2025-06-18`; Inspector uses the same entry but does not manually add version headers repeatedly.
3. Enter a clear SQL and see the offline policy explanation: when explicitly denied, the object/policy ID/static rule is listed; in other cases, only "Cannot confirm permission yet" is displayed, which guides the real client to initiate allow and deny requests.
4. After obtaining the audit ID from the client, go directly to the audit details and check the agent, data source, decision, rule, masking and error stage; if the audit ID cannot be obtained, troubleshoot according to authentication, protocol, connection, execution or audit dependency.

## must be delivered

- Reuse the same Agent/data source selection in the access wizard, add client configuration instructions, offline SQL interpretation and audit ID positioning, without repeatedly creating permissions or executing SQL.
- The client configuration only contains the `<Agent API Key>` placeholder; the console does not request, display, copy, save, or write the actual Key in the URL. Address input is only saved in page memory; URLs containing usernames, passwords, query strings, or fragments are rejected.
- Reuse existing `POST /api/v1/policies/preflight`. This API only reads policy snapshots and parses SQL, does not access the business database, and outputs `deny` or `unknown`; the UI does not turn `unknown` into allowed, and does not interpret connection ping or "with policy" as execution permission.
- `127.0.0.1` in the Dify container points to Dify itself; if loopback is filled in, a clear warning will be given. Inspector's manual repeated addition of the MCP version header will cause errors, and the configuration instructions must be displayed separately.
- The remote plaintext HTTP will transmit the Agent Key; the wizard needs to prompt to use HTTPS or isolate the intranet. The local loopback drill does not display remote alarms.
- Retain the original Agent identity, tenant, authorization, execution, masking, approval, persistent auditing, and fail-closed contracts.

## Not in this edition

Agent Keys are not automatically generated or echoed, connections are not created on the client on behalf of users, SQL is not executed directly for offline preflight, `/mcp/2026-07-28` or OAuth client authentication scope is not expanded, and existing specified instance database support is not upgraded to full production support. Real customers have not yet been found, so we do not claim the external user task completion rate; first record the steps, time and failure points of the internal guidance training.

## Acceptance

1. The console gives accurate actions for empty status, no permissions, invalid Agent, no policy, broken database, offline explicit rejection, offline unknown, protocol version incompatibility and audit dependency failure; old results will no longer be displayed after switching Agent/data source or SQL.
2. The configuration description shows that the URL/request header is accurate after switching between Dify and Inspector, and the copied text always does not contain the real Key; the wrong address does not generate usable configuration.
3. Dify 1.17.1 and MCP Inspector 0.16.8 respectively complete allow/deny calls, check masking and persistent audit IDs; internal task drill records from blank configuration to first audit are not equivalent to real user research.
4. Still follow the [ each version delivery process ](RELEASE_ROUTINE.md) to complete the version closure CI, dual-architecture signature assets, upgrade recovery from v1.8.0, GHCR, official website, Live Demo and public network re-inspection.
