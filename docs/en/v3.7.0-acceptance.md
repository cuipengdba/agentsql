# AgentSQL v3.7.0 Acceptance Record

**Language:** [English](v3.7.0-acceptance.md) | [Simplified Chinese](../v3.7.0-acceptance.md)

Status: candidate acceptance; formal release gates remain open. Results below use isolated Docker topologies and synthetic data on 2026-10-24, not customer production.

| Item | Environment and result |
| --- | --- |
| MongoDB replica set | `mongo:7.0` served 7.0.45 in an authenticated, TLS three-member `rs0`, with a read-only user, 1,500 synthetic records, and the `customer_id_1` index. Exact indexed reads passed after election moved the primary to mongo2. Removing the index, using an unapproved filter, or using the wrong CA caused denial. Image digest: `sha256:c53852c00c23ca9f23fc39690350ffa9a80e3642fe8f96879726d8da0abe80a7`. |
| Redis/Valkey Sentinel | Redis 8.2.9 and Valkey 8.1.10 each used two data nodes, three Sentinels, TLS, separate Sentinel ACLs, and read-only data ACLs. Bounded Hash reads passed after promotion to redis2/valkey2. Wrong CA, missing fields, wrong types, oversized values, and data ACL revocation were denied. Redis digest: `sha256:66b7f4c2f3c6ef1b298bbd7b13c806bc6f71e61f1136a4f58710daf2cb053b21`; Valkey digest: `sha256:640c5e62cea04b6d6f2084232651d0cc70362d31f4f805e7be94dbed6855e8f2`. |
| MCP clients | MCP Inspector 0.16.8 and Dify 1.17.1's own MCPClient made real allow/deny calls for MongoDB, Redis, and Valkey. Masked phone values and durable audit IDs were verified; raw phone values were not delivered. |
| Failure closure | With an independent PostgreSQL 18.6 audit store paused, MongoDB HTTP MCP withheld values; after recovery it allowed the read and persisted its audit. Stopping all three business nodes withheld values; a new primary restored reads. Preflight and terminal audit writes have a two-second bound. |
| PostgreSQL migration | Isolated postgres:18 instances passed migration and existing-data tests for combined metadata 27, separated metadata 25, and audit-only 7. |
| Upgrade/restore | The official v3.6.0 amd64 archive, SHA-256 `de5d4fb296af890562d59518c5f165e0062fef9de0c9af1a24b2deb699826c6a`, started SQLite schema 26. A synthetic-data backup had SHA-256 `55784df0d46a8fce952ca00ab8193b16fb00b864a24a096d27b916da29c8437a`. The v3.7.0 candidate started and migrated to 27, defaulting the existing datasource's `read_control_json` to `{}`. Restoring the backup allowed the official v3.6.0 binary to start again on schema 26. |

## Remaining gates

- Signed assets, multiarch GHCR, formal GitHub Release, website and public Demo updates, and independent public smoke checks remain open.
- The above topologies cover isolated synthetic tests only. MongoDB sharding, Redis/Valkey Cluster, and customer production workloads were not tested.
