# AgentSQL v3.5.0 Three-Gateway Acceptance Record

**Language:** [Chinese](../v3.5.0-acceptance.md) | [English](v3.5.0-acceptance.md)

Status: candidate acceptance in progress. Signed release assets, public images, website, and public Demo require separate post-release checks.

## Isolated environment and scope

The local rig used kind v0.33.0 and Kubernetes v1.35.8, with one control plane and three worker nodes. After the first automatic cluster bootstrap timed out, the control plane was completed manually using the kubeadm and CNI manifests supplied by the pinned kind image. Three AgentSQL Pods ran on separate workers with independent RWO PVCs and stable instance IDs. Shared metadata, separate audit, and synthetic business data used a local PostgreSQL 18 test container; no customer data was involved. The published manifest keeps MCP HTTP stateless and B5 sessions and transactions disabled.

## Verified paths

| Area | Observed result |
| --- | --- |
| Install and migration | Separate PostgreSQL metadata/audit migration and read-only checks passed at versions 23/7. Preflight confirmed three Ready workers. The Pods had distinct instance IDs, each retained across restarts on its own PVC. |
| Cross-gateway requests | One administrator token worked on another gateway, and MCP initialization succeeded on all three. An allowed query, unpermitted-column denial, and email masking passed against synthetic PostgreSQL data. Allowed and denied calls produced durable audit records. |
| Cross-gateway audit SSE | Node 1 observed allow and deny events created by nodes 0/2. Node 2 accepted the tenant-local `Last-Event-ID` preceding an event from node 0 and delivered the next frame. A second tenant saw no default-tenant history; a foreign-tenant cursor returned HTTP 400. |
| Single-node failure | After one worker stopped, the Service removed that Pod. The remaining gateways continued allow, deny, masking, and SSE. The original Pod returned to Ready after node recovery. |
| Audit database failure | With new audit connections blocked and existing ones terminated, queries failed closed and a new SSE request returned HTTP 503. Allowed queries succeeded again after database recovery. |
| Metadata failure | After an outage longer than the runtime lease, `/readyz` returned 503 and MCP did not return an allow. Following database restoration and the documented rebuild of all three Pods, readiness, stable instance IDs, authorization, masking, and durable audit passed again. |
| Bounded concurrency | Across three nodes, 36 concurrent requests yielded 25 allows, 9 denials, and 2 errors. All 25 allowed results had matching durable audit IDs; P50 was 821ms and P95 1070ms. With one node stopped, 24 requests yielded 10 allows, 2 denials, and 12 errors; all 10 allows had audit IDs, with P50 1473ms and P95 2561ms. These local samples are not a production SLA. |
| Upgrade and rollback | In an isolated namespace, two v3.4.1 replicas became Ready and administrator login passed. After a full stop and paired metadata/audit backup, the v3.5.0 migration reached versions 23/7 and three candidate Pods became Ready. After another full stop and paired restore, versions returned to 23/6; two v3.4.1 replicas again became Ready, with administrator login and schema check passing. This does not claim a mixed-version B2 rolling upgrade. |

## Pending release acceptance

A temporary B5 session-enabled trial exposed a mismatch between the tenant used to seal a standard Agent session and the tenant persisted by the repository, causing a valid signed continuation to be denied. The identity source has been fixed and a regression test added. Owner continuation, misrouting, stale epoch, bad proof, and close must be repeated with the corrected build. The official three-replica sample continues to disable B5 and stateful HTTP sessions; it does not claim seamless cross-instance transaction migration.

The Kubernetes checks above used local synthetic data and a candidate image. The control plane restarted under local resource pressure during a parallel image build. Before release, the final commit requires CI and critical-path repetition, followed by signed-asset, anonymous-pull, website, and public Demo checks. The Demo's actual deployment topology must be stated separately.
