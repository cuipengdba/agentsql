# v4.5.0 Installable Offline Bundle Design and Verification

[Chinese](../v4.5.0-offline-delivery.md) | [English](v4.5.0-offline-delivery.md)

Status: candidate design; no formal v4.5.0 offline bundle has been built or published.

`scripts/assemble-offline-release.py --installable` assembles a transport archive from the 15 signed, verified formal release assets. It contains `assets/`, a version file, `install-offline.py` and the read-only database preflight `check-postgres-binder.sh`. Assembly neither downloads software nor installs it on the assembly machine. The offline installer privately stages the assets, then checks the fixed inventory, release key, three Ed25519 signatures and file hashes. Only then does it extract `agentsqlctl` from the authenticated package for full release verification. After every check passes, it calls the verified local `install.sh --from` to install the gateway and Q&A service. Installation uses no network access.

For the formal release, assemble the archive from the same source commit as the 15 assets and an independently retained trusted public key, then publish the archive and its SHA-256. After downloading and unpacking, a user can install with one command:

```bash
sudo python3 agentsql-v4.5.0-offline/install-offline.py install
```

The default command checks the AgentSQL release-key file against the SHA-256 pinned in the script (`83d507dd59659aff490725184b2e65a5c1036181fc79c350028905df723a1542`). To authenticate the publisher with a key obtained outside the archive, use:

```bash
sudo python3 agentsql-v4.5.0-offline/install-offline.py install --trusted-public-key ./trusted-release-key.json
```

Use `upgrade` instead of `install` for an upgrade, or add `--verify-only` for a read-only verification. The target needs supported Linux amd64/arm64 with glibc, Python 3, OpenSSL 3 and adequate private staging and backup space. The installer handles signed assets and a local package; database connections, a real model and business-system cutover still require separate setup and acceptance. `--no-start` is only an isolated preinstallation check and does not establish successful systemd startup.

The same assembly and installation logic was rehearsed locally with all 15 formal v4.3.0 assets in `--network none` containers: verification passed with an independently saved key and with the pinned bundled key, a modified `provenance.json` was rejected, and a `--no-start` installation produced the gateway binary, Q&A binary and Q&A store. This validates the script against an existing formal package. Final v4.5.0 signed assets, actual dual-architecture installation, upgrade/rollback, service startup and the download entry point remain release gates.

The Q&A service installer now includes configuration and credential files created on first installation in startup-failure rollback. An injected first-start failure in a `--network none` container left no configuration, credentials, binary, unit or database behind. Normal offline preinstallation, login under the actual unprivileged account, and startup-failure rollback of an existing installation then passed. This is a bounded service-script fault injection, not final v4.5.0 offline-bundle upgrade and rollback acceptance.

PostgreSQL Q&A also depends on the native `agentsql_binder` extension on the database server and schema-usage and function-execution privileges on `agentsql_catalog` for the runtime reader. The current 15-asset one-command application bundle neither includes nor installs that database extension. On 2026-10-28, a local real-model aggregate question closed with `AUTH_BINDER_MODE_REQUIRED` until the reader received the minimal grants shown in `deploy/quickstart/postgres/02_readonly.sh`. For v4.5.0 to meet a genuinely usable offline-install claim, trusted offline delivery and installation of the database extension, or a clearly defined external-database preconfiguration flow, must pass disconnected checks for extension version, runtime-role privileges, aggregate Q&A and audit. The existing rehearsal proves application-service installation only.

The separate extension installer previously imported `DEV-ONLY-public-key.asc` directly from the extension package directory, allowing that directory to authenticate itself. It now requires `--trusted-public-key` obtained independently outside the package directory and rejects a missing key, a bundled key, or a symlink resolving back into the package before reading packages or invoking a package manager. A disconnected local container passed focused negative tests. Extension packages still carry development signatures only; a formal publisher key, signed packages and complete disconnected installation acceptance remain open. This change closes only the automatic trust of a bundled development key.

The preflight connects using libpq's `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE` and `PGPASSFILE` environment settings. Run it as the actual runtime reader, or use `--runtime-role ROLE` with an installation account allowed to switch roles. It only reads extension version, schema and function privileges, and capability identity; it does not install the extension or change the database. Isolated PostgreSQL 16 checks returned `POSTGRES_BINDER=PASS` with a ready reader, and distinct failures for a missing extension, missing schema usage, missing function execution and an invalid role name.

The function-privilege check now counts only native functions owned by the `agentsql_binder` extension. In an isolated database, the runtime role lost execute privilege on the extension's `prepare(text,text)` but gained execute privilege on a separate SQL function named `prepare(integer)`. The previous preflight incorrectly returned `PASS`; the corrected preflight returned `FUNCTION_EXECUTE_MISSING`. The ready reader still returned `PASS`. The test database and role were removed.
