# AgentSQL v1.7.0 Design: HighGo HighGo specified instance deep adaptation

**Language:** [English](v1.7.0-design.md) | [Simplified Chinese](../v1.7.0-design.md)

Status: Under design and development. The baseline is released v1.6.0; targets in this document are subject to final live library, client, and release acceptance results.

## User issues and scope

The existing HighGo 9.0.10 Enterprise Edition PG mode verification passes `db_type=postgres`'s synthetic table query, masking, R006 and auditing, but this will mistakenly place HighGo within the capabilities of PostgreSQL; timeouts, cancellations, permission revocations, disconnections and audit library failures do not form complete evidence of the manufacturer. This version provides an independent `highgo` data source type and read-only execution path, and only declares **HighGo 9.0.10 Enterprise Edition, PG mode, single instance, synthetic data and restricted SELECT subset**.

## Product and technology decisions

| Project | v1.7.0 Decision | Acceptance basis |
| --- | --- | --- |
| Registration and Identity | `highgo` is an independent type, with default port 5866; the console and compatibility matrix show the specific version, mode and untested items | Users are no longer required to configure HighGo as `postgres`; old PostgreSQL data sources will not be automatically migrated |
| Protocols and drivers | Currently using the pgx/v5 PostgreSQL wire protocol, but via a standalone HighGo executor; this is a driver choice and does not inherit PostgreSQL's B2, B5, DML or production support claims | The real database version handshake and PG mode check pass; the ordinary PostgreSQL server refuses to access as HighGo |
| Server verification | Query `pg_catalog.highgo_version()` when connecting, requiring V9.0 Enterprise Edition 9.0.10; read internal parameters `ivorysql.database_mode=pg` and read-only transaction status; close the connection if verification fails | 2026-10-18 The local official package isolation instance returns `HighGo数据库管理系统V9.0-企业版-9.0.10`, `pg`; other versions and modes are rejected |
| SQL subset | Single, explicit schema, single table, direct column projection, non-constant WHERE, read-only SELECT of LIMIT; do not allow CTE, JOIN, function, aggregation, sorting, lock, write, unknown syntax | Parsing, authorization and execution respectively reject out-of-bounds shapes; the database account is protected with minimum SELECT permissions. |
| Inquiry and Audit | Use an independent read-only pool, server statement timeout, client cancellation, post-row collection context review and persistent audit barrier; audit failure must not return results | Real database lock waiting, cancellation, audit database shutdown and masked query rerun after recovery |
| Discovery and Strategy | Only uses censored PG catalog metadata paths; HighGo does not enable the PostgreSQL B2 column-level binder or B5 write transactions | Table authorization, rule denial, sensitive column masking and audit traceability; unauthorized discovery, column policy and write failure closure |

Secure link: Real MCP client → Agent Key/Tenant identity → Data source and object authorization → HighGo restricted parsing → Minimum privilege read-only connection and server identity verification → Time-limited query → Result source and masking → Persistent audit success → Deliver results. If any link cannot be proven, fixed errors and audit status will be returned, and the original sensitive row will not be delivered.

## acceptance matrix

1. Isolate the official HighGo 9.0.10 Enterprise Edition image and mount the license read-only; record the installation package, image, authorization expiration date, PG mode and real port. The least privileged account only allows synthetic table SELECT, and writing returns permission denial.
2. Run the MCP Inspector CLI and Dify MCPClient for the independent `highgo` type to allow, rule deny, unauthorized deny, mobile phone number masking and persistent audit; Dify visual workflow is not counted in SDK acceptance.
3. Revoke table permissions on the real database, disconnect the business database, lock wait timeout, client cancellation and independent audit database failure, and then restore each item; check not delivering partial results, database-side active query reset to zero, audit code, post-recovery mask and minimum permissions.
4. Negative unit and integration tests cover fake PostgreSQL servers, non-PG mode, different versions, writes, functions, JOINs, no WHERE/LIMIT, unauthorized tables, column-level policies, and high-risk SQL. Remain unverified when permissions or targets are missing, and do not use simulation results to replace real database conclusions.
5. SQLite and PostgreSQL metadata/audit upgrade and complete recovery from v1.6.0 official package and accepted data; CI of sealed SHA, dual-architecture signature assets, GHCR anonymous pull, official website and Live Demo public network smoke test are executed according to each version delivery process.

## Support boundaries and fallback

Does not cover HighGo Oracle/MySQL compatibility mode, legacy versions, distributed topologies, TLS, connection pool failover, extension types, B2 column-level bindings, B5 write transactions, production workloads, or vendor certifications. If handshake, read-only query, fault shutdown or any required link of the real client fails, the historical verification record of the original `postgres` protocol path will be retained, but the new support statement of `highgo` will not be opened; the package, mirror and backup that fall back to v1.6.0 will be officially released.
