# AgentSQL v4.10.0 Query Expressions and Conversation Lifecycle

> Development contract. A target scenario earns no pass until all positive and negative acceptance cases pass on the same exact signed package; this document does not state that the version is released.

## User problem and scope

AgentSQL is an independent AI data Q&A agent and an independent MCP Server database security gateway. SQLBot Community v1.10.3 is only a pinned optional client. v4.9.0 fixed a short writer-lock identity-audit timeout during authorized vector prewarming and established a strict **2/25** baseline under the fixed scenario contract. Earlier slices demonstrated parts of follow-up questions, restarted history, exports, and embedding, but did not meet each scenario's full contract on one signed package. v4.10.0 focuses on a reviewable user flow for filtering, grouping, ordering, and limiting natural-language queries, then continuing, reopening, exporting, and embedding the conversation.

The candidate scoring items are Q2, H1, H2, H3, and I3. If all pass, the target is **7/25**, not a claimed score in advance. All other scenarios retain zero; an API response, loaded page, older signed package, or simulated model does not pass. v4.10.0 does not expand claims for arbitrary database connection creation, cloud models, external directories, or untested SQL dialects. The user's real business system has not been validated.

## Implementation and security contract

| Path | Required result | Security negative case |
| --- | --- | --- |
| Q2 single-table expressions | The unchanged original Q&A page and AgentSQL's own page use the same controlled gateway, real model, and PostgreSQL. Fixed synthetic data verifies SQL, values, and ordering for filtering, grouping, ordering, and limiting | Unauthorized columns or tables, excessive limits, non-read-only model SQL, and changed row/column rules are denied before results; controlled audit matches execution |
| H1 contextual follow-up | The second question in the same conversation correctly refers to an authorized table, predicate, or time range from the first; valid context survives reopening | Another user cannot read the conversation; revoked SQL, fields, and results cannot enter model context |
| H2 restarted history | The unchanged original page reopens history after ChatBI restarts, displaying SQL and results under the current identity, binding, and row/column rules | Revocation, disablement, deletion, or binding change hides old values through cache, detail, and follow-up paths |
| H3 history export | Current authorized history exports as CSV and original XLSX from the unchanged page or its original API; file rows and values agree | Both old exports are denied after revocation with no new controlled gateway query; an export-audit write failure cannot release a file |
| I3 basic and page embedding | Unchanged original basic assistant and Type 4 page embedding each complete a real question, refreshed history, and origin enforcement | Wrong Origin, forged messages, disabled guest access, and datasource revocation cannot yield a token or old result and cannot create another gateway query |

Identity, workspace, and datasource binding come from current server-side records. Model SQL, historical SQL, export content, and embedded messages are not authorization sources. Recheck current grants before execution and delivery, and close on audit-commit failure. Existing Type 1, advanced embedding, arbitrary role expansion, and cloud-model claims do not grow through this score.

## Release gates

1. All five GitHub CI jobs match one final commit. Changed behavior has deterministic positive and negative tests; unchanged original-client tests with a real model, database, and gateway retain raw logs and the exact commit.
2. Record pass or zero, positive and negative evidence, and limits for all 25 frozen scenarios without changing the denominator. Any unauthorized access, lost audit, or stale result leak blocks release even if the score target is met.
3. Build the expected production dual-architecture assets and outer offline archive from the final source, verify with an independent trusted public key, then use the exact signed assets for offline real-systemd new installation, official v4.9.0 upgrade, and injected startup-failure rollback on AMD64 and QEMU ARM64, checking services, model, metadata, and old files.
4. Merge, publish the GitHub Release, verify anonymous multi-architecture GHCR download, deploy the website and Demo with a clearly identified simulated model, run public allow/deny/masking/audit smoke tests, and leave canonical main clean and equal to origin/main.

Release notes must not claim 100% SQLBot compatibility, zero-change cutover, ARM hardware testing, or a production SLA. If the score target is missed while in-scope behavior remains safe, publish the actual score and failed items; do not weaken scoring conditions to manufacture a pass.
