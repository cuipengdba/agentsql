# AgentSQL v4.0.0 offline delivery and maintenance guide

**Language:** [Simplified Chinese](../v4.0.0-delivery.md) | [English](v4.0.0-delivery.md)

This guide covers administrator delivery and maintenance. Database support levels follow the [capability and evidence table](nosql-support.md) and versioned acceptance reports; maintenance tooling does not promote connection previews to production support.

## 1. Prepare trusted tooling and key material

Obtain `agentsqlctl` with the verification command from trusted installation media. When first introducing the v4.0.0 tool, independently verify signatures with `scripts/releasesign/main.go` from reviewed source before trusting packaged binaries; an unverified binary cannot establish its own trust. Confirm the official Ed25519 key ID through an independent channel rather than trusting only a key downloaded beside the package. See [release assets](RELEASE_ASSETS.md) for the inventory.

## 2. Verify the complete asset directory

```sh
agentsqlctl release verify --directory ./release-assets --public-key ./trusted-release-key.json --version v4.0.0
```

The directory must contain exactly the 15 official assets, with the trusted key file outside it. Fixed JSON output identifies the version, source commit, key ID, asset count and signature count. Acceptance requires exit 0 and `status=verified`. The tool does not access the network, extract, install or execute scripts; signature verification does not replace business acceptance. Keep the input directory read-only and reverify after offline transport.

## 3. Assemble an offline transport archive

```sh
python3 scripts/assemble-offline-release.py --directory ./release-assets --public-key ./trusted-release-key.json --version v4.0.0 --ctl /trusted/agentsqlctl --output ./agentsql-v4.0.0-offline.tar.gz
```

The script creates private staging below the output directory, copies and verifies assets, then creates a transport-only tar.gz. The output must not exist; no dependencies are downloaded or software installed. The outer archive is not an additional official signed asset; its 15 original signed assets are the verification targets. Deliver the trusted key independently and repeat the previous step after unpacking in the isolated environment. Requires Python 3.9+, an already trusted `agentsqlctl` and sufficient disk space.

## 4. Install offline and stop writes for upgrades

```sh
bash ./release-assets/install.sh install --from ./release-assets/agentsql-v4.0.0-linux-amd64.tar.gz
```

Select the amd64 or arm64 package for the CPU. Initial installation prerequisites, directory permissions, systemd and SECRET configuration follow the [deployment guide](DEPLOY.md). Existing instances use the installer's upgrade workflow after stopping writes and taking paired backups as described in [upgrade and rollback](v4.0.0-upgrade.md). `upgrade apply --dry-run` remains read-only and neither replaces binaries nor creates real backups.

## 5. Export minimal diagnostics

```sh
agentsqlctl support-bundle --config ./config.yaml --output ./support-new.json --timeout 10s
```

Output is limited to 256 KiB and contains tool version, generation time, OS/architecture, metadata/audit schema readiness and built-in static capability evidence. It excludes configuration text, paths, hostnames, DSNs, SECRET, environment dumps, SQL, logs, business rows and user lists. The capability table is not a scan of configured datasources. Inspection is read-only but connects to the configured stores; use an account with minimal query permissions.

| Exit code | Meaning | Action |
| --- | --- | --- |
| 0 | Checks ready | Correlate with current symptoms and business acceptance. |
| 2 | Migrations pending | Stop writes, take paired backups, then use a migration owner. |
| 1 | Inspection or output blocked | Follow the report's fixed action; without valid JSON, check permissions and retry with a new path. |

Existing output files and symlinks are refused. Configuration is limited to 1 MiB and inspection timeout to one minute; diagnostics do not create databases or instance ID files. Administrators should review output before sharing. This release does not transmit files or collect telemetry automatically.

## 6. Maintenance and issue intake

Record the running version, release commit, asset hashes, OS/architecture, exact database product/version/topology, reproduction steps and fixed-field diagnostics. Customer SQL, data, keys or logs require separate sanitization and authorization if needed for investigation; the default bundle excludes them. No paid maintenance term or SLA is implied. Follow the repository SECURITY policy for security reports and never paste secrets into public issues.
