# AgentSQL v2.7.0 设计：ClickHouse 查询治理

状态：实施中。目标实例为 ClickHouse 26.8.31.2 LTS、单节点原生 TLS 端口。此设计不宣称 ClickHouse 的完整生产支持。

## 用户任务和边界

AI 助手需要从已授权分析表读取少量列，并且每次读取受 Agent 身份、表/列授权、数据库最小权限、资源预算、脱敏和持久审计共同约束。现有 ClickHouse 适配器仅提供管理员原生命令预览，不能作为 Agent MCP 的查询入口。

| 交付路径 | 约束 |
| --- | --- |
| MCP `query_analytics` | 输入数据源 ID、当前数据库中的单张表、1–16 个显式列、1–8 个字符串等值条件、1–100 行上限；不接受 SQL 文本。必须有精确表授权和显式列授权，过滤列也要授权。 |
| 旧配置兼容 | 现有 ClickHouse 管理预览仍以 9000 为注册默认端口；新建受控查询配置在控制台预填原生 TLS 端口 9440。旧明文配置不获得 Agent 查询能力。 |
| 数据库执行 | 使用当前数据源配置新建严格 TLS、已认证的只读连接；只允许指定实例版本和 MergeTree 单表。校验表引擎及列类型后由服务端构造参数化 SELECT；拒绝视图、Distributed、字典、表函数、JOIN、聚合、写入与跨库访问。角色至少应限制 `readonly=1`、执行时间、读行/字节、内存、输出行与线程。网关单次请求最多 2 秒，返回值最多 1 MiB。 |
| 安全链 | 重新验证 Agent/租户与数据源归属，逐次解析当前策略；持久预检审计成功后才访问 ClickHouse。结果列和行数严格校验，按来源列脱敏；终态审计成功后才交付结果。失败或取消记错误终态，审计不可用时失败关闭。 |
| 客户端与交付 | MCP Inspector、Dify MCPClient 真实允许/拒绝调用；从 v2.6.0 正式包升级和成对恢复；CI、双架构签名、GHCR、官网与 Live Demo 逐项验收。公网 Demo 保持合成 PostgreSQL 场景。 |

调用链：`HTTP MCP 身份 → Agent/租户 → 数据源 → 精确表/列策略 → 输入校验 → 持久预检审计 → TLS/只读角色/元数据 → 参数化有界 SELECT → 结果结构和资源上限 → 脱敏 → 持久终态审计 → MCP 响应`。

负向用例包括跨 Agent/租户、撤权、宽泛授权、未授权投影/过滤列、SQL/标识符注入、视图和 Distributed 引擎、危险函数、账号写入、错误证书、读超时/取消、业务库故障、预检/终态审计故障以及返回结构异常。所有测试只使用合成数据；不把目标版本或单机通过外推到集群、复制、高并发和生产负载。

参考：[ClickHouse Go 驱动](https://clickhouse.com/integrations/go)、[Agentic Analytics 的角色和只读设置](https://clickhouse.com/blog/how-to-set-up-clickhouse-for-agentic-analytics)、[ClickHouse TLS 配置](https://github.com/ClickHouse/clickhouse-docs/blob/main/docs/guides/sre/tls/configuring-tls.md)。
