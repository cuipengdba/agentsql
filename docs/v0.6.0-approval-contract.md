# v0.6.0 普通 SQL 审批执行合同（设计中）

状态：设计稿，尚未实现；现有 `request_approval` 和管理端“通过”仅持久化审批决策，不执行该 SQL。

## 现状与风险

- `pipeline.approve` 只保存 Agent ID、SQL 原文、评估原因以及待审批审计 ID；未保存数据源、调用者提交的 reason、参数、有效期。
- `DecidePending` 只把 `pending` 改为 `approved/rejected`，不会执行请求。现有 `reason` 还会被审批备注覆盖，申请理由与审批意见混在一个字段。
- MCP `get_approval_result` 只返回决策状态。让 Agent 重发原 SQL 不能被当作“执行已批准请求”：原请求内容、数据源、策略版本和副作用均无法与批准记录锁定。

## 目标状态机

```text
pending ──approve──> approved ──原子认领──> claimed ──执行/审计──> completed
   │                    │                       ├─确定失败──> failed
   ├─reject──> rejected └─过期──> expired          └─结果不确定──> unknown
   └─过期──> expired
```

只有 `approved` 可认领，认领动作在元数据事务中以 `tenant_id + approval_id + status + expires_at` 做原子条件更新；重复请求、并发请求和进程重启后的 `claimed` 一律不得自动重试。`unknown` 要保留供人工核查，不把网络超时解释为“数据库未写入”。

## 封存与重新校验

审批记录封存租户、Agent、数据源、原始 SQL、规范化 SQL 摘要、请求参数及类型、请求理由、创建与过期时间、审计关联。审批人 ID、审批意见和决策时间分别存储，不覆盖申请理由。旧版没有这些字段的审批记录保持可查看，但不可进入新执行路径。

执行工具只接收审批 ID，不接收可替换的 SQL、数据源或参数。执行前重新验证：当前 Agent Key 与租户、Agent 未被停用、数据源未更换、授权未撤销、SQL 解析与绑定、风险规则、数据库账号只具备所需权限。任何一项不确定即关闭。审批不能绕过 `deny` 或改变只读/写入级别；仅能让经重新评估仍落在“需要审批”的同一封存请求继续。B5 计划事务的审批消费保持现有独立合同，不与普通 SQL 审批号互用。

## 审计与测试

申请、审批、认领、执行结果分别写可关联事件；申请审计 ID 和执行审计 ID 不混用。元数据与审计分库时采用已有“审计先写”约束；遇到不可确认的持久化结果进入 `unknown`，不放宽重试。

至少验证：换 Agent/租户、换数据源、换 SQL/参数、超时、撤销权限、审批重放、双并发认领、进程重启、数据库断线、审计故障，以及拒绝后数据库实际无副作用。需要 PostgreSQL/MySQL 真库测试；其他方言不得因普通链路通过自动获得写入承诺。
