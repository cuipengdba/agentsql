# AgentSQL 敏感列发现指南

AgentSQL 的敏感列发现面向 DBA 和安全管理员。它对管理员明确指定的少量基础表执行一次受控、同步、只读的检查，结合列名和可选样本找出疑似敏感列，并可为当前确实支持的类别生成默认不生效的脱敏规则草稿。

> **重要：发现结果是启发式建议，不是数据分类结论或合规证明。** 它可能误报，也可能漏报。生成草稿前必须由了解数据用途的管理员核对列的业务含义；启用规则前还要验证作用域和脱敏效果。

## 功能定位与非目标

敏感列发现只用于辅助已有数据源的脱敏配置：

- 读取明确指定表的列元数据，只对列名命中的候选列做可选采样。
- 发现请求同步返回，不创建异步任务，也不持久化一份可反复查询的发现结果。
- 六类发现项都可以一键生成 `enabled=false` 的 `mask` 规则草稿；草稿不会自动参与运行时脱敏。
- 发现使用数据源中已经保存的数据库账号，不要求为 MCP Agent 增加权限，也不新增 MCP 工具。

它不是自动脱敏、完整 DLP 或合规判定工具，不会修改业务表中的数据，不会自动启用规则，也不提供“留空即扫描全库/全部表”的模式。它不会从自然语言推导或生成业务 SQL；受控只读服务只生成固定的元数据查询和形如 `SELECT <候选列> FROM <限定表> LIMIT <上限>` 的采样语句，并在执行前校验只读语句结构。

普通脱敏规则还支持管理员手工配置 `hash`、`block`，以及仅搭配这两种算法的通用敏感值 `generic`；它们都不进入发现流程。discovery/advisor 始终只产出六类 `mask` 推荐，apply 也只接受这些推荐组合；提交 `hash`、`block` 或 `generic` 会被拒绝。

## 发现类别与识别依据

当前固定支持六类发现，并可为六类全部生成 `mask` 草稿。列名会按 snake case、camel case、短横线和空格切分，只匹配完整 token 或已知短语，不做任意子串匹配。`data_type` 会随结果返回，供管理员核对，但当前分类器不把数据库类型作为独立判定信号。

| 类别 | API 值 | 典型列名信号 | 样本校验概要 | 可一键生成草稿 | 当前算法 |
| --- | --- | --- | --- | --- | --- |
| 手机号 | `phone` | `mobile`、`phone`、`phone_number`；中等信号 `tel` | 可选 `+86`，校验中国大陆 11 位号段 | 是 | `phone` + `mask` |
| 邮箱 | `email` | `email`、`email_address`；中等信号 `mail` | 完整邮箱格式 | 是 | `email` + `mask` |
| 身份证 | `idcard` | `id_card`、`idcard`、`identity_number`；中等信号 `identity` | 18 位校验真实生日与校验位；15 位校验旧证日期 | 是 | `idcard` + `mask` |
| 银行卡 | `bankcard` | `bank_card`、`bank_account`；中等信号 `card_no` | 允许 ASCII 空格/连字符；正规化后 13–19 位并通过 Luhn | 是 | `bankcard` + `mask` |
| IP 地址 | `ip` | `ip`、`ip_address`、`client_ip` | 用 `net/netip` 校验 IPv4、IPv6、`inet` 或 `cidr` | 是 | `ip` + `mask` |
| 出生日期 | `birthdate` | `birth_date`、`date_of_birth`、`dob`、`birthday`；中等信号 `birth` | 校验真实日历、非未来日期且年龄为 0–120 岁 | 是 | `birthdate` + `mask` |

六类发现项都会返回同类别的推荐规则和 `algo=mask`，正常情况下 `applicable=true`，可在控制台勾选后生成草稿。姓名和地址当前不发现，裸 `name`、`address`、`username` 也不会成为候选。

## 六类 `mask` 运行时遮蔽样式

启用规则后，AgentSQL 在查询结果层按列应用下列确定性部分遮蔽。输入会先去除首尾空白；表中星号数量是固定算法的一部分。

| 类别 | 原始值 | 遮蔽值 | 规则摘要 |
| --- | --- | --- | --- |
| 手机号 `phone` | `13812345678` | `138****5678` | 11 位手机号保留前 3、后 4，中间固定 4 颗星 |
| 邮箱 `email` | `alice@example.com` | `a***@example.com` | local 部分只保留首字符并追加 3 颗星，域名保留 |
| 身份证 `idcard`（18 位） | `110105199001011234` | `110105********1234` | 前 6 + 8 颗星 + 后 4；末位 `x` 统一输出为 `X` |
| 身份证 `idcard`（15 位） | `130503670401001` | `130503******001` | 前 6 + 6 颗星 + 后 3 |
| 银行卡 `bankcard` | `4111 1111-1111 1111` | `411111******1111` | 去除 ASCII 空格/连字符后，保留前 6 位 BIN 与后 4 位；中间星号数为总位数减 10 |
| IP 地址 `ip`（IPv4） | `192.168.1.2` | `192.168.*.*` | 保留前两段，即 `/16` 粒度 |
| IP 地址 `ip`（IPv6） | `2001:0db8:85a3::1` | `2001:0db8:****` | 保留前 32 bit 的两个 hextet，并输出为固定四位小写 |
| 出生日期 `birthdate` | `1990-01-02`、`1990/01/02`、`19900102`、`1990-01-02T00:00:00Z` | 均为 `1990-**-**` | 保留四位年份，月日打码，并丢弃时间与时区 |

出生日期还接受 `1990/01/02`、`19900102`、RFC3339/RFC3339Nano 及 SQL timestamp；例如 `1990-01-02T00:00:00Z` 也输出 `1990-**-**`，时间和时区后缀不会保留。银行卡仅做形态正规化，不在遮蔽阶段执行 Luhn 校验；长度须为 13–19 位。PostgreSQL `inet`/`cidr` 返回的 `/32`、`/128`、`/24` 等前缀会在遮蔽前去除；带 zone 的 IPv6、域名和 `host:port` 不作为 IP 地址接受。

> **风险提示：部分遮蔽不等于匿名化。** 手机号仍保留前 3 后 4，身份证仍保留前 6 后 4，银行卡仍保留 BIN 与后 4，IP 保留网段，出生日期仍保留年份。这些取舍服务于运维可读性、统计和排障，不构成不可逆匿名化，也不替代存储层保护。需要不可逆哈希指纹或固定 `***` 的整值阻断时，可在「脱敏规则」页手工配置 `hash` 或 `block`；二者都不会由发现流程推荐。只有 `range` 仍是规划中、当前不可执行的算法。

## 严格发现、宽松遮蔽

发现与运行时遮蔽承担不同职责，策略差异是有意设计：

- **严格发现**回答“这一列是不是敏感列”。分类器对身份证校验真实生日和校验位，对银行卡执行 Luhn，对 IP 使用 `net/netip`，对出生日期验证真实日历并检查 0–120 岁及未来日期。策略偏向宁可不报，也不以弱证据误导管理员。
- **宽松遮蔽**执行管理员已经启用的保护意图。运行时只判断并正规化对应类型的形态，不重复执行身份证校验位、银行卡 Luhn 或年龄校验；形态可识别就按上表遮蔽。
- 某列已启用对应类型规则后，非空值若无法按该类型形态正规化，输出固定常量 `[REDACTED]`，绝不回传原值。空字符串、SQL `NULL` 和 `<nil>` 哨兵保持原样，不计入 `MaskedCells`。

真实数据库驱动的返回形态已纳入两层处理。例如 MySQL DSN 启用 `parseTime` 后，DATE 可能经 stringifier 成为 `2026-09-17T00:00:00Z`；PostgreSQL `date` 也可能成为 RFC3339Nano，而 `inet`/`cidr` 可能分别返回 `192.0.2.10/32`、`198.51.100.0/24`。发现和遮蔽均兼容这些形态。

## 置信度与人工复核

样本证据会排除 `NULL` 和空白值。至少有 3 个有效样本才形成支持或矛盾证据；有效样本中至少 80% 通过对应格式校验视为“支持”，低于 50% 视为“矛盾”。

| 条件 | 结果 |
| --- | --- |
| 开启采样，强列名信号且样本支持 | 高 |
| 开启采样，强列名信号但有效样本不足，或支持率为 50%–不足 80% | 中 |
| 开启采样，强列名信号与样本矛盾 | 不返回该发现项 |
| 开启采样，中等列名信号且样本支持 | 中 |
| 开启采样，中等列名信号但样本不支持 | 不返回该发现项 |
| 关闭采样，强列名信号 | 中 |
| 关闭采样，中等列名信号 | 低 |

没有列名候选时不会为了“试试看”读取样本，也不会只凭样本内容发现一列。整体策略偏向宁可漏报、避免误报，但无法消除误报或漏报；例如名称看似手机号的商品编码列仍需要人工判断。

## 扫描范围与固定上限

当前必须显式指定 1–20 个 `{schema, table}`。空数组、重复表、仅给 schema 或超过 20 个表都会失败；没有“留空扫描全部表”的行为。只扫描数据库元数据中确认的 `BASE TABLE`，不扫描视图、物化视图或外部表。

> **500 是元数据列总数上限，不是表数上限。** 一次请求所列各表合计超过 500 列时会整体失败，必须拆分表范围；系统不会静默截取前 500 张表或前 500 列继续运行。

所有上限都是服务端固定值，当前没有对应配置项或环境变量：

| 项目 | 默认值 | 硬上限或行为 |
| --- | ---: | --- |
| 显式表数 | 必填 | 1–20 |
| 元数据总列数 | — | 500 |
| 候选列数 | — | 50 |
| 每条采样 SQL 的候选列数 | — | 10，超出时按同一表分批 |
| `sample_rows` | 10 | 20；开启采样时只能为 1–20 |
| 单条语句超时 | 2 秒 | 若数据源 `stmt_timeout_ms` 更小，则使用更小值 |
| 整体发现 deadline | 12 秒 | 超时不返回部分结果 |
| 采样值总数 | 默认行数下最多 500 | 1,000；按返回单元格计数，包括空单元格 |
| 限流与并发 | — | 同一管理员为 1 QPS；同一“管理员 + 数据源”并发 1，同一数据源并发 1，全局并发 2 |

每条采样 SQL 最多返回 `sample_rows` 行。实现没有另设“所有批次返回行数之和”常量；总量由每条最多 20 行、每条最多 10 个候选列、候选列最多 50 个以及最多 1,000 个采样单元格共同约束。

关闭采样后，系统只读取列元数据，业务数据读取量为零；`sample_rows` 不应随请求发送，置信度最高为中。

## 权限、可见性与最小权限建议

发现复用数据源已保存的数据库账号。它不复用 MCP Agent 的对象授权策略，因此不需要额外开放 MCP 权限；数据库账号本身必须能读取所列基础表的元数据，并在启用采样时能 `SELECT` 候选列。应使用独立、最小权限、只读账号，不要使用 PostgreSQL superuser、数据库 owner 或 MySQL `root`。

权限错误按发生阶段区分：

- 建立连接或 `Ping` 阶段的未知数据库、无权进入数据库、认证失败和网络失败，执行器统一归类为“数据源不可达”，不向客户端泄漏驱动错误。当前发现管理 API 会再把这类未细分内部错误收敛为 `500 DISCOVERY_INTERNAL` 和“敏感发现失败”；可先在数据源页执行“测试连接”排查。
- 连接已经建立后，查询期 PostgreSQL SQLSTATE `42501`，以及 MySQL `1044`、`1142`、`1143`、`1227`，映射为 `403 DISCOVERY_PERMISSION_DENIED`，页面提示“数据源账号无权读取部分对象”。
- 元数据接口可能对无权对象静默隐藏结果。为避免把“看不见”误判为“没有敏感列”，任一指定表缺失或不可见都会以 `403 DISCOVERY_SCOPE_NOT_VISIBLE` 整体失败，不会跳过该表继续返回部分结果。

PostgreSQL 范围限定在当前数据库，并排除 `pg_catalog` 和 `information_schema`；MySQL 的 `schema` 必须等于数据源配置的 `database`。

## 样本数据安全

采样值只在当前请求的进程内存中传递给分类器：

- 不写入控制面数据库或发现结果表。
- 不写入管理审计正文；审计只记录明确表范围、开关、行数和聚合计数。
- 不通过 SSE 实时事件或 Webhook、Syslog 通知外发。
- 不写入发现响应，不返回页面；页面只能看到列级元数据、信号名和匹配/有效样本计数。
- 请求结束后释放相关引用，不保留供后续请求查询的样本预览。

Go 字符串和数据库驱动缓冲区不提供密码学级安全擦除，因此不能承诺样本字节在进程内存中被可靠清零。高敏环境应关闭“样本校验”，只使用列名启发式，并通过数据库账号权限进一步缩小可见范围。

## 生成草稿与规则作用域

apply 只接受六类发现类别各自对应的 `mask` 组合，例如 `idcard/idcard/mask`；类别与敏感类型必须相同。提交 `algo=hash`、`algo=block`、`sensitive_type=generic` 或其他非推荐组合会以 HTTP `422`、`DISCOVERY_NOT_APPLICABLE` 拒绝且不创建草稿。新建规则由服务端强制设置：

- `enabled=false`：草稿默认不生效。
- `table_name=""`：发现结果中的 schema 和表名只是来源，不是运行时匹配范围。
- 唯一作用域为“数据源 + 规范化列名”，即具体 `datasource_id` 加去除首尾空白并转为小写的 `column_name`。

这意味着启用 `phone` 列的草稿后，同一数据源查询结果中的同名列会统一匹配，不区分 schema 或表。当前不支持“表.列”级脱敏规则。必须进入「脱敏规则」页，核对数据源、规范化列名、敏感类型、算法和同名列影响范围后再手动启用。`enabled=false` 草稿本身不会脱敏任何结果。

apply 是幂等的，响应将项目分入以下数组：

| 结果 | 含义 | 处理建议 |
| --- | --- | --- |
| `created` | 新建了一条数据源级、未启用的草稿 | 到「脱敏规则」页核对后启用 |
| `existing` | 同一数据源和规范化列名已有相同类型、相同算法的规则，不重复创建；已有规则可启用或未启用 | 查看现有规则状态和内容 |
| `covered_by_global` | 已有启用的全局同名列规则，默认不创建数据源级覆盖 | 核对全局规则的类型、算法和影响范围 |
| `conflicts` | 同一数据源和规范化列名已有不同类型或算法的规则 | 返回 `409 MASK_RULE_CONFLICT`；先处理现有规则。批次中出现冲突时不创建该批次计划的新草稿 |
| `ambiguous` | 同一请求中多个表的同名列被归为不同类别 | 不创建该列草稿；缩小到单表重新发现并人工确认 |

一次 apply 最多 50 个项目。不同表的同名列若类别、类型和算法一致，会聚合为一条规则；不能把多张表的来源误解为多条表级规则。

## 控制台操作步骤

1. 以管理员登录控制台，进入「数据源」。
2. 在目标数据源的操作中打开「敏感发现」。
3. 点击「添加表」，填写 1–20 个完整的 schema 和基础表名。
4. 按环境决定是否开启“样本校验”；开启时选择 1–20 行，默认 10 行。高敏环境关闭采样。
5. 点击「开始发现」，查看类别、置信度、证据和是否可一键脱敏。
6. 人工核对列用途与推荐类型；手机号、邮箱、身份证、银行卡、IP 地址、出生日期六类均可勾选。
7. 点击「生成脱敏草稿」。遇到冲突或歧义时按页面提示缩小范围或核对现有规则。
8. 前往「脱敏规则」页，再次核对数据源、规范化列名、类型、算法和同名列影响范围，确认后手动启用。

该流程是管理面操作，复用数据源账号，不要求修改 MCP 客户端、Agent API Key 或 Agent 授权策略。发现能力本身也不会作为 MCP 工具暴露。

## 管理 API

两个端点都需要管理员 Bearer token，属于管理操作，并分别写入 `discover` 和 `discover.apply` 管理审计。无有效管理员鉴权时返回 `401`。请求体使用严格 JSON：未知字段和尾随 JSON 返回 `400`，最大为 `1 MiB`。

### 发起发现

`POST /api/v1/datasources/{id}/discover`

```json
{
  "tables": [
    {"schema": "public", "table": "customers"}
  ],
  "sampling": true,
  "sample_rows": 10,
  "categories": ["phone", "email", "idcard", "bankcard", "ip", "birthdate"]
}
```

- `tables`：必填，1–20 个不重复的 `{schema, table}`。
- `sampling`：可选，默认 `true`。
- `sample_rows`：采样开启时可选，默认 10；显式传值只能为 1–20。`sampling=false` 时不得同时传该字段。
- `categories`：可选；省略或空数组表示全部六类。

成功响应的 `data` 包含：

- `scope`：实际数据源、表、采样开关、采样行数和类别。
- `stats`：请求/扫描表数、读取列数、候选列数、采样列/值数和发现项数。
- `limits`：当前固定上限。
- `findings[]`：`schema`、`table`、`column`、`data_type`、`category`、`signals`、`confidence`、`sampled`、`matched_samples`、`eligible_samples`、`recommended_rule`、`applicable`、`existing_rule` 和可选 `reason`。其中不含原始样本值。

### 生成草稿

`POST /api/v1/datasources/{id}/discover/apply`

```json
{
  "items": [
    {
      "schema": "public",
      "table": "customers",
      "column": "phone",
      "category": "phone",
      "sensitive_type": "phone",
      "algo": "mask"
    }
  ]
}
```

`items` 必须为 1–50 项。六类均可提交，但 `category` 与 `sensitive_type` 必须相同，`algo` 必须为 `mask`；例如 `birthdate/birthdate/mask`。`hash`、`block` 与 `generic` 只能在普通脱敏规则中手工配置，提交到 apply 会返回 `422 DISCOVERY_NOT_APPLICABLE`。请求 DTO 不接受 `enabled`、样本值或自由信号字段。成功响应的 `data` 包含 `created`、`existing`、`covered_by_global`、`conflicts`、`ambiguous` 五个数组及 `counts` 汇总。

### HTTP 状态码

| HTTP 状态码 | 稳定错误码或场景 | 含义 | 处理建议 |
| ---: | --- | --- | --- |
| `200` | 成功；也可能只包含 `existing`、`covered_by_global` 或 `ambiguous` | 请求已处理 | 检查响应分类和计数，不要只看 HTTP 成功 |
| `400` | `INVALID_JSON` | JSON 非法、未知字段或尾随 JSON | 按 DTO 修正请求；不要传 `enabled` |
| `401` | 管理员 Bearer 无效 | 未通过管理鉴权 | 重新登录或更新管理员 token |
| `403` | `DISCOVERY_PERMISSION_DENIED` | 连接成功，但元数据或采样查询权限不足 | 为数据源只读账号补最小必要权限 |
| `403` | `DISCOVERY_SCOPE_NOT_VISIBLE` | 指定表缺失或对账号不可见，整体 fail-closed | 核对 schema、表名和可见性，不会静默跳过 |
| `404` | 数据源不存在 | 路径中的数据源 ID 无效 | 刷新数据源列表并核对 ID |
| `409` | `MASK_RULE_CONFLICT` | 同名列已有不同类型或算法的规则 | 到「脱敏规则」页处理冲突；响应可含分组结果 |
| `413` | `REQUEST_TOO_LARGE` | JSON 请求体超过 `1 MiB`；不是“21 个表”的逻辑范围码 | 缩小请求体；表数、列数等逻辑超限见 `422` |
| `422` | `DISCOVERY_SCOPE_LIMIT`、`DISCOVERY_CANDIDATE_LIMIT`、`DISCOVERY_SAMPLE_LIMIT` 等 | 空范围、表/列/候选/采样超限，或参数、类别非法 | 拆分表范围、减少采样行数或修正参数 |
| `422` | `DISCOVERY_NOT_APPLICABLE` | 类别、敏感类型或算法不是当前 discovery apply 可接受的组合 | 提交同类别的六类敏感类型，并使用 `mask` |
| `429` | `DISCOVERY_RATE_LIMITED` | 1 QPS 或并发配额被占用 | 等待当前请求完成后重试 |
| `500` | `DISCOVERY_INTERNAL` | 包括当前 API 未进一步区分的连接/Ping“数据源不可达”等内部失败 | 先测试连接；再检查服务端日志和数据源配置 |
| `503` | `DISCOVERY_UNAVAILABLE` | 受控发现服务未就绪 | 检查服务启动和依赖注入状态后重试 |
| `503` | `AUDIT_UNAVAILABLE` | 审计不可用；成功结果会被丢弃，apply 持久化也会 fail-closed | 恢复 metadata/audit 控制面后重试 |
| `504` | `DISCOVERY_TIMEOUT` | 服务端单语句或整体 deadline 超时 | 缩小范围、降低采样行数或关闭采样 |

服务端当前不主动返回 `408`。控制台会把反向代理的 `408`、客户端 15 秒超时和 `504` 统一显示为超时，并给出相同的缩小范围建议。

发现审计只写固定白名单统计，不写样本。apply 审计记录请求数、`created`、`existing`、`conflict`、`ambiguous` 计数和规范化列 key；通知投影不外发这些管理详情。

## 配置与部署

敏感列发现本身没有新增 YAML 配置项或环境变量。它沿用现有管理员鉴权、`AGENTSQL_SECRET` 解密后的数据源凭据、metadata/audit 控制面和数据源 `stmt_timeout_ms`，但会把发现单语句超时收紧到不超过 2 秒。手工配置 `hash` 规则所需的 `redaction.hash_key` / `AGENTSQL_REDACTION_HASH_KEY` 不属于发现流程，见[部署指南](DEPLOY.md#脱敏哈希密钥管理)；`block` 无需任何密钥或配置。控制面迁移和备份要求仍以部署指南为准。

若管理审计不可用，发现不会把结果返回给调用方；apply 也不会把“未审计的成功”当作正常完成。metadata 与 audit 分库时采用审计优先的 fail-closed 流程，极端情况下可能留下已写审计但元数据草稿未创建的记录，重试时应以 apply 响应和「脱敏规则」页为准。

## 从早期版本升级

六类脱敏不引入新的数据库迁移。`mask_rules.sensitive_type` 与 `mask_rules.algo` 原本就是自由文本字段；早前版本提供的 `0003_discovery_drafts.sql` 已增加 `enabled` 列和作用域唯一索引，本次无需新增或重跑专用迁移。

兼容性行为有一处需要升级前核对：如果曾绕过管理 API，直接向 `mask_rules` 写入 `sensitive_type` 为 `idcard`、`bankcard`、`ip` 或 `birthdate` 且已启用的规则，这些规则在早期版本中不受支持、加载会失败；升级后它们会被正常加载并立即参与运行时脱敏。请在升级前查询并复核这四类历史直写规则的 `datasource_id`、规范化列名、类型、算法和 `enabled` 状态。`phone`、`email` 的既有行为不变。

同时盘点存量 `algo=hash` 规则：若其中存在 enabled 规则，升级启动前必须安全注入至少 32 字节的哈希密钥，否则服务会 fail-fast；只有 disabled `hash` 草稿时可无 key 启动。`block` 不参与该启动门禁，无 key 也可正常运行。密钥轮换会改变全部指纹，详情见部署指南。

## 限制与后续规划

以下能力均为规划中，当前版本不支持：

- `range` 算法。`hash` 与 `block` 已可在普通脱敏规则中手工配置，但发现流程不会推荐、生成或应用它们。
- “表.列”级规则和表感知脱敏优先级。
- 姓名、地址等更多敏感类型的发现与遮蔽。
- 异步、定时或大范围发现任务，以及跨请求进度、取消和重试。
- 发现结果导出。
- 与合规策略、自动分级或处置流程联动。

## 已知限制

- 必须显式指定 1–20 个基础表；不支持 schema-wide、全库、全部表或视图扫描。
- 一次请求最多读取 500 个元数据列、识别 50 个候选列、处理 1,000 个采样单元格；超限整体失败，不返回部分结果。
- 识别依赖固定列名与格式启发式，可能误报或漏报；数据库类型当前只供展示，不参与分类。
- 关闭采样时只看列名，置信度最高为中；开启采样也只抽取表中无排序保证的前若干行。
- 六类均可发现并生成 `mask` 草稿；姓名和地址当前不发现。`hash`、`block` 与 `generic` 仅能在普通脱敏规则中手工配置；`block` 已可运行，只有 `range` 仍不可执行。
- 草稿默认不生效，必须人工核对并启用；发现不会自动修改业务数据。
- 规则按“数据源 + 规范化列名”匹配，同名列统一生效；不支持“表.列”级规则。
- 样本不持久化、不返回、不进入审计正文或通知，但进程内存不做密码学级安全擦除。
- 功能仅在管理 API/控制台提供，不是 MCP 工具，也不受 MCP Agent 授权策略限制。
- 发现是同步操作，整体 deadline 为 12 秒；不支持异步任务、结果导出或合规结论。
