v4.0.0

Database security gateway for AI agents

AgentSQL (Chinese name: Zhidun) is a database security gateway and MCP Server for AI Agents. PostgreSQL/MySQL requests issued by the model go through identity authentication, SQL parsing, static and dynamic risk checks, four-state decision-making and controlled execution before reaching the database; the results are masked according to the configuration, and a persistent audit is left at the application layer.

v4.0.0 adds offline signature verification, transport archives, cross-version upgrade procedures and minimal read-only diagnostics. Database capabilities remain bounded by their published evidence. The public Demo uses synthetic PostgreSQL/MySQL data.

Check it out on GitHub Quick Start v4.0.0 Release Notes

Starting from v0.5.0 Apache-2.0 Open Source · Go single binary delivery (glibc/cgo build) · Self-hosted · No third-party telemetry dependencies

It's not BI, it's not an ORM or Text2SQL, it's a default-deny security gate between the model and the database.

Requests only enter the execution phase if allowed by the policy

Why you need a safety gate

Make the model’s database access constrained, explainable, and traceable

The SQL generated by the model is non-deterministic. AgentSQL puts identity, permissions, syntax, risk and execution control in one request link to reduce the following common risks.

01

Dangerous statement

Illusions may result in dangerous writing methods such as UPDATE / DELETE that lack WHERE; whether to intercept depends on the enabled rules, policies and Agent capability configuration.

02

Unauthorized access

The model may query unauthorized tables or columns and needs to be judged based on Agent, data source, object and column permissions before execution.

03

Sensitive data returned

Fields such as mobile phone number and email address may enter the model context in plain text and need to be coded according to the configuration before the results are returned.

04

It is difficult to assign blame afterwards

In the absence of request identity, SQL, rule hits, and decision records, it is difficult to restore why an access was allowed or denied.

Common Line of Defense:The security gateway cannot replace the minimum permissions, read-only accounts, security views and network isolation on the database side.

six-segment link

From identity to traces, tightening access step by step

QPS/connection limit is controlled by entrance and rules.

  1. 01

    Authentication

    Verify API Key, load Agent, data source and policy, and close if failed.

  2. 02

    parse

    AST is built according to PostgreSQL/MySQL dialect, and exceptions such as malformation/multiple statements are rejected according to rules.

  3. 03

    Security check

    Do a static check that does not touch the library first. Only when the static check is not rejected, establish a controlled connection and do dynamic checks such as read-only EXPLAIN/metadata.

  4. 04

    decision making

    press deny > approve > warn > allow is aggregated into release/alarm/interception/transfer to manual.

  5. 05

    Execution and masking

    Only allow/warn is executed to limit the connection, timeout and number of result rows, and the results are coded by column before returning.

  6. 06

    leave traces

    The allow/warn/deny/approve/error decision that enters the SQL pipeline is synchronously written into the application layer audit. Audit failures are fail-closed by design; tool layer pre-denials may not have persistent traffic auditing.

Real-time big screen

Put risk changes into observable views

Recent risk events are pushed in real time via authenticated SSE (/api/v1/stream), and polling is performed when disconnection occurs; KPIs, trends and distributions support manual and automatic refresh in about 30 seconds; Prometheus indicators can be connected to existing monitoring.

Audit and traces

Review the complete evidence chain from the decision list

Provides application layer audit list, combination filtering, evidence chain viewing and JSONL export to facilitate traceability and security analysis; PDF compliance report is in the roadmap. It is not a regulatory-level WORM, and it cannot prevent the database owner/superuser from directly changing the underlying data.

Core features

Full path for controlled database access

MCP dual entrance

Preserving stdio with stateful Streamable HTTP /mcp;Add independent MCP 2026-07-28 stateless HTTP entry /mcp/2026-07-28, re-authenticate each request. The new portal does not currently provide the B5 cross-request tool.

Deny by default

Combine API Key, Agent capability level, object/column authorization and AST rules; fail-closed by design when exceptions or key dependencies fail.

controlled literacy

Provides read-only protection, dangerous SQL interception, EXPLAIN risk, timeout, connection/QPS/result row limit and manual approval.

Result masking

The mobile phone number/email address is basically coded based on column name matching, which is not a complete DLP; the data source password is stored in AES-256-GCM encryption using a 32-byte key.

control surface

Default zero configuration SQLite, optional PostgreSQL 15+; PG18 is the baseline. Supports single database or independent metadata/audit dual databases and SQLite→PG migration. The independent audit database is an optional layout rather than the default.

Observables and consoles

Provides Prometheus metrics, health/readiness probes, Grafana dashboards, and an embedded web console.

Task-level temporary read-only authorization

The applicant submits an Agent, a data source and a simple SELECT that completely matches; another authorized user of the same tenant checks and approves. After approval, the applicant can receive a key for up to 24 hours at a time. Key can be revoked, and original object permissions, rules, masking and auditing are still in effect.

Access wizard

In the same process, select the Agent and data source, check the connection, generate Dify/Inspector keyless access instructions, interpret the target SQL offline, and locate the record with the audit ID of the real call. Preflight does not execute Agent SQL.

Version check before upgrade

agentsqlctl migrate --check Read-only reporting controls the schema status of the control library; production upgrades still require backing up the database and pairing keys, and then the migration account explicitly performs the migration.

Security

Clarify the scope of capabilities and then design defense in depth

The following restrictions should be evaluated in conjunction with database permissions, network policies, backup and operational controls.

  • Connection rangeOnly connections through the gateway are protected. Directly connected owner/superuser/DBA are not within the scope.
  • Result maskingMask results using verified column provenance, conservatively blocking values when provenance cannot be proven. This is not complete DLP.
  • Application auditThe audit leaves traces at the application layer, non-regulatory level WORM, and does not protect against high-privileged DBAs.
  • JOIN authorizationTable authorization always applies. Supported PostgreSQL B2 paths also verify provable projection-column provenance and reject unproven cases; this does not extend to every dialect.
  • Wildcard permissions* / schema.* These are broad grants and require care. Applicable table/column policies, rules and database privileges still constrain actual results.
  • Column name lookbackVerified expression, aggregate, CAST, set-operation and CTE paths track protected sources. Unknown view or function internals are not fully proven; non-null values whose safety cannot be established are conservatively blocked.
  • SQL/Transaction BoundariesB2 column-level authorization for PostgreSQL, old /mcp The portal's B5 cross-request logical session and scheduled transactions are enabled by factory default; the new stateless portal does not provide B5 tools. MySQL does not enter the B2 PostgreSQL path and does not support B5 cross-request transactions. Only one top-level SQL is still allowed per operation, subject to preflight plans and session security boundaries.
  • mission authority boundariesTemporary Key only applies to a simple SELECT that matches exactly; it does not grant permission to write or bypass Agents, objects, rules, and database accounts.
  • Approval boundariesSQL will not be automatically executed when the approval is passed; the original Agent can be called with the approval order number within the validity period execute_approved Once. Re-verify identities, policies and data sources before execution, and will not automatically retry when rejected or the result is unknown.
  • Demo environmentThe public Demo uses only synthetic data and read-only or controlled scenarios. It does not connect to real business databases.
  • Deployment boundariesThe read-only two-gateway topology, OAuth/OIDC and tenant governance have acceptance evidence in specified environments. Arbitrary replica counts, HA for stateful transactions and unverified vendor production support are not promised.

FAQ

FAQ

How does it relate to MCP?

It is itself an MCP Server; MCP is the standard protocol for model communication with external tools/data.

Can't the model be connected to the database without MCP?

Yes, applications can also use self-developed APIs, database agents or server-side managed credentials to connect; AgentSQL provides a unified identity, policy, controlled execution and audit entrance for MCP, not the only connection method.

Is it BI/ORM/Text2SQL?

None; it is not responsible for the business experience of natural language generated SQL, nor does it replace ORM, and is responsible for safe execution and traces.

How is the performance?

Static determination is at the millisecond level; in the benchmark of in-memory fake executor, 20 workers / 200,000 samples, stripping the real database network and execution time, the gateway CPU path P99 is about 1.81 ms. This number is not the end-to-end query delay. The real delay depends on the connection, EXPLAIN, database execution and audit storage.
