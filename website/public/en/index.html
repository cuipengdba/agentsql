A database security gateway for AI agents

AgentSQL is a self-hosted MCP server and database security gateway. Before an agent's request reaches a supported database, AgentSQL authenticates the caller, checks permissions and SQL risk, makes an allow/warn/deny/approve decision, controls execution, masks configured result columns, and records an application-level audit.

v3.0.1 adds Chinese/English switching to the website and Web console and makes the console's left menu scroll within short viewports. It retains the v3.0.0 capability catalog and read-only delivery diagnostics. Registration in the catalog does not mean full production support; every real read still goes through identity, permissions, rules, masking, and audit checks.

Why a gateway?

Make agent database access controllable, explainable, and traceable

01

Risky SQL

Generated SQL can contain unsafe writes, including UPDATE or DELETE without WHERE. Whether it is blocked depends on enabled rules, policy, and agent capability.

02

Unauthorized access

Check the agent, data source, object, and column permissions before execution.

03

Sensitive results

Configured masking can obscure selected phone and email fields before the result enters model context.

04

Missing evidence

Keep the identity, SQL, rule matches, decision, and execution status needed to explain a request.

Defense in depth: The gateway does not replace database privileges or network controls.

Six stages

From identity to audit

  1. 01

    Authenticate

    Validate the API key and load the agent, data source, and policy. Fail closed when required checks fail.

  2. 02

    Parse

    Build a dialect-aware SQL AST. Rules reject malformed or multi-statement requests.

  3. 03

    Inspect

    Run static checks first. Where allowed, use a controlled connection for read-only EXPLAIN or metadata checks.

  4. 04

    Decide

    Combine decisions in deny > approve > warn > allow order.

  5. 05

    Execute and mask

    Execute only allow/warn decisions, with limits on connections, time, and rows; mask configured result columns.

  6. 06

    Audit

    Persist decisions in the SQL pipeline. Audit failure closes that path; some earlier tool-level rejections may not have a persistent traffic audit record.

Capabilities

Controlled access from MCP to audit

MCP transports

Local stdio, stateful Streamable HTTP at /mcp, and a separate stateless MCP 2026-07-28 endpoint at /mcp/2026-07-28. The new endpoint reauthenticates each request and does not expose cross-request B5 tools.

Default-deny controls

API keys, agent capability tiers, object and column permissions, SQL AST rules, and fail-closed behavior for critical failures.

Execution limits

Read-only protection, hazardous SQL checks, EXPLAIN risk checks, timeouts, connection/QPS/result limits, and human approval.

Data protection

Configurable column masking is basic protection, not complete DLP. Data-source passwords are encrypted with AES-256-GCM.

Control plane

SQLite by default; optional PostgreSQL 15+ control plane with single- or split-database layouts. PostgreSQL 18 is the baseline.

Operations

Web console, Prometheus metrics, health/readiness probes, Grafana dashboard, task-scoped temporary read grants, onboarding guide, and a read-only migration check.

Compatibility

Versioned, evidence-based support

The v3.0.1 catalog registers 30 databases in eight families; KingbaseES V9 appears separately for a specified PG-protocol instance. Each adapter has its own tested versions, modes, operations, and failure behavior. Catalog registration alone is not a production-support claim.

Core SQL paths

PostgreSQL and MySQL use the main SQL gateway with distinct dialect, permission, and column-binding rules. The README and release evidence state the tested boundaries.

Specified-instance paths

Vastbase, HighGo, openGauss, Oracle Free, SQL Server 2025 Developer, Yashan, and other adapters have narrower version- and scenario-specific acceptance evidence.

Non-SQL paths

MongoDB, Redis/Valkey, ClickHouse, and Milvus expose restricted read tools with explicit object and field scope; they are not general-purpose database proxies.

Security limits

Use database controls alongside the gateway

Masking is not complete DLP or anonymization. Application-level audit is not a regulatory WORM log. A database owner or superuser can still alter underlying data. Direct connections bypass AgentSQL. Use least-privilege database accounts, safe views, network isolation, backups, and independent audit controls as appropriate.

FAQ

Common questions

Is AgentSQL itself an MCP server?

Yes. It exposes database tools through supported MCP transports.

Does it generate SQL from natural language?

No. It checks and controls database requests; it is not a BI tool, ORM, or Text2SQL product.

Does it support every registered database in production?

No. Check the specific version, operation, transport, and acceptance evidence for each adapter.
